5022 fix(method-override): add duplex option when body is a ReadableStream created=2026-06-12T06:28:17Z updated=2026-07-13T00:28:53Z
The `query` override branch passes `c.req.raw.body` (a `ReadableStream`) directly to `new Request()` without setting `duplex: 'half'`. The Fetch spec requires this option whenever the request body is a stream, and undici (the native fetch implementation in Node.js) enforces it with:

```
TypeError: RequestInit: duplex option is required when sending a body.
```

This means any HTML form that submits to a route using query-based method override will get a 500, because forms always send a body.

The `form` and `header` branches are not affected. They consume the body into `FormData` or `URLSearchParams` before constructing the new request, so the stream is already resolved by the time `new Request()` is called.

The fix spreads `{ duplex: 'half' }` into the `RequestInit` only when `body` is non-null, and casts to `RequestInit` because the TypeScript lib types do not yet include `duplex`.

Added a regression test: a `POST ?_method=DELETE` with a `application/x-www-form-urlencoded` body. The existing test for the query branch only used a bodyless POST.

Fixes part of #5010.

### What version of Hono are you using?

4.12.8

### What runtime/platform is your app running on? (with version if possible)

Node.js v22 (also reproducible on any runtime)

### What steps can reproduce the bug?

Calling `parseBody()` followed by `text()` or `json()` on the same request throws `TypeError: bodyCache[anyCachedKey].then is not a function`.

This happens when `Content-Type` is **not** `multipart/form-data` or `application/x-www-form-urlencoded` (e.g., `application/json` or no Content-Type header).

**Root cause:**
`parseBody()` stores a resolved plain object in `bodyCache.parsedBody` (via `??= await parseBody(...)`). When Content-Type is not a form type, `parseBody()` returns `{}` immediately without going through `formData()`, so `parsedBody` is the only key in `bodyCache`.

`#cachedBody()` then picks it up via `Object.keys(bodyCache)[0]` and calls `.then()` on it, assuming every cache entry is a `Promise`.

When Content-Type **is** a form type, `parseBody()` internally calls `request.formData()` which goes through `#cachedBody('formData')`, caching a `Promise` under `bodyCache.formData` first — so `Object.keys()[0]` is `'formData'` and `.then()` succeeds.

**Reproduction:**

```typescript
import { HonoRequest } from 'hono/request'

const req = new HonoRequest(
  new Request('http://localhost', {
    method: 'POST',
    body: JSON.stringify({ event: 'push' }),
    headers: { 'Content-Type': 'application/json' },
  })
)
await req.parseBody()  // returns {}, caches plain object in bodyCache.parsedBody
await req.text()       // TypeError: bodyCache[anyCachedKey].then is not a function
```

### What is the expected behavior?

`text()` should return the raw request body text regardless of whether `parseBody()` was called first.

### What do you see instead?

`TypeError: bodyCache[anyCachedKey].then is not a function`

### Additional information

**Use case:** A middleware that tries to extract form data if present (without checking Content-Type upfront), then a downstream handler needs the raw body for signature verification:

```typescript
app.use('*', async (c, next) => {
  const body = await c.req.parseBody()
  if (Object.keys(body).length > 0) {
    c.set('formData', body)
  }
  await next()
})

app.post('/webhook', async (c) => {
  const raw = await c.req.text()  // TypeError — even though parseBody() returned {}
  verify(raw, c.req.header('X-Signature'))
})
```

487 [BREAKING] fix: make that `c.req.parseBody` parses only `FormData` created=2022-08-27T02:36:26Z updated=2022-09-28T17:42:01Z
Make that `c.req.parseBody` parses only FormData and does not parse JSON, text, and arrayBuffer. This fix includes breaking changes.

Before this PR, this function returns the parsed body according to Content-Type, despite the type of body. And, it will be `any`:

```ts
parseBody<T = any>(r: Request | Response): Promise<T>
```

Even though the user was expecting a `Record<string, string>`, this may return `Object`. This behavior could potentially cause a security vulnerability. See #484

```ts
const data = c.req.json()
```

`parseBody` will only return `Record<string, string | File>`.

```ts
parseBody(r: Request | Response): Promise<Record<string, string | File>>
```

484 Should `parseBody` only parse FormData? created=2022-08-26T04:56:51Z updated=2022-08-27T02:38:49Z
Currently, `req.parseBody()` parses any objects according to content type.

<https://github.com/honojs/hono/blob/main/src/utils/body.ts>

But, I think it would be better just to restrict it to FormData / `req.formData()`.

The first reason, the type we receive will be obscured; thus, it will be `any`. `parseBody` definition is below:

```ts
parseBody<T = any>(r: Request | Response): Promise<T>
```

If it only parses FormData, it will be restricted:

```ts
Record<string, string | File>
```

The second reason, it has the possibility of opening Security Vulnerability because we receive unexpected values. "*Plack*" rejected the PR for the same reason: <https://github.com/plack/Plack/pull/678>.

Consider the following code referred from the PR comment:

```ts
app.post('/foo', async (c) => {
  const body = await c.req.parseBody()
  const id = body.itemId
  const item = shopQuery(id)
  // ~> ['SELECT * FROM shop_item WHERE item_id = ?', id]
  // ...
```

In this case, `body.itemId` is expected `string` but, if receive Request that the body is JSON like below:

```ts
new Request(JSON.stringify({
  itemId: [1, 2, 3],
}), {
  headers: {
    'Content-Type': 'application/json',
  },
})
```

`body.itemId` will be `[1, 2, 3]`. If `shopQuery` behaves differently when it receives a string than when it receives an array, this could be a problem.

```ts
// ~> ['SELECT * FROM shop_item WHERE item_id IN (?,?,?)', id ]
```

This would not happen if `shopQuery` does the type check on the input value, but it would be better to reduce the possibility of this happening. Fortunately, the Request object has a `req.json()`, `req.text()`,  and an `req.arrayBuffer()` method in addition to the `req.formData`. Users can explicitly body parse using those methods. So, `parseBody` should support only FormData. This fix includes breaking changes, but I think we should do it.

The current implementation will treat all middleware calls as intersecting and ensure that ALL the data validates currently before passing the request through to the route handler:

```ts

  '/',
  zValidator('query', z.object({ q: z.string().optional() })),

);
```

The more appropriate expectation for `body` data in this case would be to validate either `json` OR `form` data based on the incoming content type. This is a valid way to discriminate incoming data, and it would be great for the native hono validation to support it.

     const data = c.req.valid('form');

  body,
})

```

The form-based override should fire for any `Content-Type` whose media type is `application/x-www-form-urlencoded`, regardless of parameters like `charset`. The request above should be routed to the DELETE handler and return 200.

### What do you see instead?

The override does not fire. The request is handled as the original POST. In the repro above, since there is no POST handler for `/posts`, the request falls through to a 404.

### Additional information

### Root cause

In [`src/middleware/method-override/index.ts`](https://github.com/honojs/hono/blob/main/src/middleware/method-override/index.ts#L92), the URL-encoded branch uses strict string equality:

```

So `application/x-www-form-urlencoded;charset=UTF-8` fails the check.

The `multipart/form-data` branch in the same function (line 74) already uses `startsWith`, and the rest of the codebase consistently tolerates media-type parameters:

- [`src/utils/body.ts` L105](https://github.com/honojs/hono/blob/main/src/utils/body.ts#L105) uses `contentType?.startsWith('application/x-www-form-urlencoded')`
- [`src/validator/validator.ts` L26](https://github.com/honojs/hono/blob/main/src/validator/validator.ts#L26) uses a regex that accepts parameters
- [`src/middleware/csrf/index.ts` L30](https://github.com/honojs/hono/blob/main/src/middleware/csrf/index.ts#L30) uses a regex that accepts parameters

The same class of bug was previously fixed in the validator middleware in #3297 (`URL Encoded Data could not be validated if the Content-Type included charset`).

Change line 92 to `startsWith`, matching the multipart branch above it and `utils/body.ts`:

955 Simplify Middleware role created=2023-03-05T14:07:15Z updated=2023-03-16T15:18:05Z
Currently the middleware can return a Response, but what about making it unable to return?

```ts
type MiddlewareHandler = (c: Context, next: Next) => Promise<void>
```

The reason the Middleware Handler is able to return a Response is because Basic Auth Middleware and others needed to return a response immediately.

```ts
app.use('*', async (c, next) => {
  // authentication process
  if (unauthorized) {
    return authResponse
  }
  await next()
})
```

But now that we have `HTTPException`, `return` is not necessary.

```ts
app.use('*', async (c, next) => {
  // authentication process
  if (unauthorized) {
    throw new HTTPException(401, {
      res: authResponse,
    })
  }
  await next()
})
```

If we want to change the Response in the Middleware, assign it to `c.res`. Here is a practical example:

```ts
app.use('*', async (c, next) => {
  await next()

  class HeaderElementHandler {
    element(element: Element) {
      element.append('<b>Hono</b>', { html: true })
    }
  }

  const rewriter = new HTMLRewriter().on('*', new HeaderElementHandler())
  if (c.res.headers.get('content-type')?.startsWith('text/html')) {
    c.res = rewriter.transform(c.res)
  }
})
```

The beauty of Hono is that Middleware and Handler are treated in the same way, but there are differences. I thought that being able to do a lot of things is good, but by making it more limited, it makes it easier to explain "what Middleware is?". Then this way can clarify the role with Handler. Or perhaps we could make the implementation of `compose.ts` simpler.
