# M2: `Overwrite` returns `never` when its second type is `never`, though the comment the change adds says otherwise

Pull request: trpc/trpc #5017. Base `2abb2d5c` (v10.43.2), head `7dc04a7e` (v10.43.3). Cut-off: the last push, 2023-11-09T22:08:09Z. Candidate covered: `NC-9c5ccb05dac1`. Probes: [`../probes/M2/`](../probes/M2/).

## Problem

The pull request adds a doc comment to the type helper `Overwrite`: "Overwrite properties in `TType` with properties in `TWith` / Only overwrites properties when both types are objects / Otherwise it will overwrite the entire TType with TWith, / unless TWith is never." (line breaks shown as /) The candidate says the helper returns `never` when `TWith` is `never`, so `TType` is not kept, and that through the procedure builder a `never` next input or context replaces the previous one.

What the runs show (all *run*, identical at base and head, knowable at the cut-off):

- `Overwrite<{ a: string }, never>`, `Overwrite<string, never>` and `Overwrite<undefined, never>` are all `never` (`m2-01`). The helper before the change gave `never` too.
- **Context.** A middleware that hands on a context typed `never` (`opts.next({ ctx: neverCtx() })`, where `neverCtx(): never`) leaves the resolver's `ctx` typed `never`. Reading `ctx.user` fails with TS2339 "Property 'user' does not exist on type 'never'." (`m2-05`).
- **Input through `unstable_concat`.** An object input joined with a procedure whose input is `z.never()` gives the resolver an `input` typed `undefined`, not `never`, and the caller's input `void | undefined`. Reading `input.a` fails with TS18048 "'input' is possibly 'undefined'." (`m2-02`). The helper's `never` becomes `undefined` in `ResolveOptions` (`utils.ts` lines 73 to 75: `TParams['_input_out'] extends UnsetMarker ? undefined : …`; `never` passes that check) (*read*).
- **Input through a reusable middleware** declared with `input: never`: `.use(mw)` after an object input is refused with TS2345, ending "Type '{ a: string; }' is not assignable to type 'never'." (`m2-03`).
- A procedure whose only input is `z.never()`, with or without a middleware, gives the resolver `undefined` (`m2-08`).
- With one case added in front of the helper (`m2-never-check`: `[TWith] extends [never] ? TType : …`), the context case and the concat case compile, and the resolver's `input` is `{ a: string; }` (`results/table.md`).

So the comment's sentence is untrue at the head, and the helper behaves for `never` as it did before the change.

## What changed

The pull request rewrote the helper and added the comment (*read*, head lines 4 to 30, with the unchanged copy left out):

```ts
/**
 * @internal
 * Overwrite properties in `TType` with properties in `TWith`
 * Only overwrites properties when both types are objects
 * Otherwise it will overwrite the entire TType with TWith,
 * unless TWith is never.
 */
export type Overwrite<TType, TWith> = TType extends object
  ? TWith extends object
    ? // Both TType and TWith are objects: overwrite key-by-key
      { /* the key-by-key copy, head lines 14 to 20, left out here */ }
    : TWith extends any
    ? // TWith is not an object but some non-never type, so fully overwrite TType
      TWith
    : never
  : TType extends any
  ? TWith extends any
    ? // Same as above: just overwrite TType with TWith
      TWith
    : TType
  : never;
```

In every check `TWith` stands alone on the left of `extends`. TypeScript applies such a check to each member of a union separately, and `never` is a union with no members, so the result is `never` before any branch is chosen. The `: TType` at line 29 is never reached (*read*; *run* in `m2-01`). The helper before the change had the same form (`TWith extends any ? … : never`) and gave `never` too (*run*). At line 24 the change's own code returns `never` where an object first type meets a `never` second type, and at line 29 it returns `TType`. The two branches written for `never` disagree with each other (*read*).

**Before 2 (older fault).** The result is the same at base and head (run). The sentence "unless TWith is never" is a line the pull request adds. The checks that produce `never` are lines it rewrites (11, 12, 21, 25, 26). The first two bullets of rule Before 2 cannot apply: nothing got worse or became reachable. The third bullet could apply: the mismatch is between a comment the change adds and checks the change rewrites, all in the lines it touches.

## Delivered?

The change's announced outcome is that a second type which is not an object replaces the first, while two objects are merged key by key. That arrives (GT-j1 apart, which is a separate known problem). The sentence about `never` does not hold. A developer whose middleware hands on a context typed `never` gets a `never` context, and one who joins a `z.never()` input after another gets `undefined` (run). Both results are the same as before the change. No ordinary use was found that hands the helper a `never` second type.

## Both sides

*For a minor defect.* The pull request added a sentence about an exception that its code does not implement. That is a statement that is untrue. The outcome the change announces arrives, and the `never` behaviour is what it was before the change. The helper is marked `@internal`, and no ordinary use hands it a `never` type. The commit message itself limits the promise to "a non-never TWith type".

*For a problem.* Rule Promised 5 makes a code comment's plain statement a promise. Read on its own, the sentence says that a `never` second type keeps the first type, and a developer whose middleware hands on a `never` context does not get that. The rule says the promise covers "the ordinary ways of doing that thing", though, and no ordinary way was found.

*For a suggestion.* The helper is internal (`@internal`, exported only "so users can generate their own types definitions files"), so its comment speaks to maintainers and makes no promise to users. On that reading the comment is wrong and fixing it is an improvement.
