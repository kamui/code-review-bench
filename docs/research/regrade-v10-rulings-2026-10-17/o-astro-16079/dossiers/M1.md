## Problem

A site turns on ISR (Vercel's cache for on-demand pages) and keeps a per-user page out of it with `isr: { exclude: ['/account'] }`. Visitors who ask for `/account` reach the normal function, which renders it fresh for each request. After this change anyone can also ask for the same page at `/_isr?x_astro_path=/account`. The ISR function renders it there, with whatever cookies that request carries. The ISR function's responses are cached by Vercel under the value of `x_astro_path` alone. So, if Vercel passes the visitor's cookies to the function and stores that response (neither was run), a signed-in visitor who opens such a link has their own account page stored, and the next person who opens the same link is served it.

When a request carries the header `x-vercel-isr: 1`, the function takes the page to render from the query value `x_astro_path`, with no check of where the value came from. The same file builds both the normal function `_render` and the ISR function `_isr`, and each can render every page of the site (*read*, `buildISRFolder` in `src/index.ts` builds `_isr` from the same entry; *run*, `_isr` renders `/account` below).

## What the affected person sees

- A signed-in visitor who opens `https://<site>/_isr?x_astro_path=/account` sees their own account page, status 200 (*run*, in process).
- If Vercel passes the cookie and stores the response (*not run*): whoever next opens the same address sees that visitor's account page, until the entry expires. With the default `expiration` the entry lasts for the deployment.
- If the first person to open the address is signed out, the stored response would be the redirect to `/login` (*run*: the function returns it; storing *not run*).
- Visitors who use `/account` itself are unaffected (*run*).
- Before the change every `/_isr` request returned the 404 page (*run*).
