# N1: Repeated parseBody() replaces the remembered form and drops edits

## Problem

A Hono request remembers a parsed form so later readers can use it again. After this change, a second `c.req.parseBody()` parses the original bytes again and replaces that remembered form. Edits made through `c.req.formData()` between the two calls disappear from later reads. This happens for both multipart forms and URL-encoded forms. It is a demonstrated change, not just a possible one. [run]

The sequence is `await parseBody()`, `await formData()`, edit that form, then `await parseBody()` again. With no edits, the field values remain correct. The FormData object changes at head. On Node the parsed File object changes too. On Bun, File identity already changes at the base, even between two reads from the same FormData. A universal promise of stable File identity is therefore not established. [run]

Keep N1 together. Repeated decoding, replacement of the remembered form, and lost edits are effects of one operation. No separate measured performance allegation is established here.

## What changed

The relevant lines in `src/utils/body.ts:125-132` are:

```diff
-  const formData = await (request as Request).formData()
+  const headers = request instanceof HonoRequest ? request.raw.headers : request.headers
+  const arrayBuffer = await (request as Request).arrayBuffer()
+  const formDataPromise = bufferToFormData(arrayBuffer, headers.get('Content-Type') || '')
+  if (request instanceof HonoRequest) {
+    // Cache so that a later `c.req.formData()` reuses the already-consumed body
+    request.bodyCache.formData = formDataPromise as unknown as FormData
+  }
+  const formData = await formDataPromise
```

Before the change, `request.formData()` reused the remembered FormData. After the change, the first `parseBody()` remembers both the original bytes and a parsed form. Each subsequent `parseBody()` reuses the bytes, builds a new form, and writes it over the remembered form. It never checks whether a form is already there. [read]

An edit changes the remembered FormData, not the original bytes. The next parse therefore restores the submitted values. The old FormData still holds its edits, but future request readers receive a different one. [run; read]

The full diff and relevant source excerpts are saved in [change.diff](../probes/N1/change.diff) and [source-evidence.txt](../probes/N1/source-evidence.txt). The probe used the actual Hono source at base `9728702911073aec5a63a3ba2840b7240e5d3205` and head `5226d4165d48643586152614cbd07422a0ab7a22`. Bun built an isolated bundle. Node and Bun ran it without replacement parsers or cache mocks. No dependencies were installed.

## Intended or announced

[PR #5067](https://github.com/honojs/hono/pull/5067) says `Fixes #5060`. The linked issue asks for case-insensitive matching of form and JSON media types. Neither announces repeated decoding, changed object identity, or loss of edits. There are no documentation changes among the six changed files. The saved review and inline-comment responses are empty. The conversation contains automated benchmark and coverage records. [read]

The added source comment says the cache write exists so a later `formData()` can reuse the body. That supports preserving later reads. It does not explicitly promise that mutations of a returned form become the request's authoritative values. [read]

The earlier [cache feature, PR #1333](https://github.com/honojs/hono/pull/1333), explicitly says the listed methods, including `formData()`, "will have their results cached". It predates this change. The documentation revision before the merge describes `parseBody()` for forms and files and `formData()` for a FormData result. It says nothing about object identity, repeated parsing, or modifying the form before another reader uses it. [read]

It shipped in patch release [v4.12.28](https://github.com/honojs/hono/releases/tag/v4.12.28), published July 6, 2026. Its notes describe a case-insensitive matching fix. They give no warning about this behavior. [read]

## What the affected person sees

For an application that edits the remembered form in middleware and then reads it again in its handler, edits silently disappear. The saved probe changes `foo=bar` to `foo=normalized`, deletes `removed`, adds `added=middleware`, and replaces an uploaded file. [run]

At base, the next `parseBody()` returns `foo=normalized`, preserves the added field and replacement file, and omits the deleted field. At head, it returns `foo=bar`, loses the added field, restores `removed=present`, and returns the original file. A later `formData()` also sees the restored original values. Both encodings behave this way on Node 24.21.0 and Bun 1.3.10. [run]

The application probe uses middleware to change `foo` and delete `removed`, then a handler to read the form again. It returns HTTP 200 at both commits. Before the change its JSON contains the changed field and omits the deleted field. At head its JSON contains the original field and the deleted field. There is no error text to diagnose. [run]

A developer relying on this sharing would need to pass the edited data explicitly, keep their own form reference, or change their read sequence. An unchanged form still returns the same field values. No actual application relying on edits or identity was found in the inspected callers or records. The application probe is a constructed demonstration, not a report of production use. [read; run]

The source search covered non-test callers under `src/`, the validator and method-override middleware, and the request caching tests. The validator reuses an existing cached form. Method override edits a separate reconstructed raw request. Neither establishes reliance on the N1 sequence. [read]

## What the maintainers did

On July 17, after this PR merged, [issue #5129](https://github.com/honojs/hono/issues/5129) reported the GT-p1 sequence, `formData()` first and `parseBody()` second. Its author described a real authentication middleware using that order. That report did not describe edits between repeated `parseBody()` calls. Its attribution to #5071 is the reporter's claim; the pinned #5067 diff already contains the bytes-first change. [reported; read]

Maintainer yusukebe [replied](https://github.com/honojs/hono/issues/5129#issuecomment-5008347350): "Thank you for the report! This is a bug. I'll fix it." This explicitly acknowledges GT-p1. It does not explicitly acknowledge N1's mutation or identity effects. [read]

His [PR #5131](https://github.com/honojs/hono/pull/5131) adds an early check for an existing cached form. If present, `parseBody()` converts that form directly instead of reading bytes again. It shipped in [v4.12.31](https://github.com/honojs/hono/releases/tag/v4.12.31) on July 18. [read]

The same probe fails in v4.12.28 and works in v4.12.31. That fix restores FormData identity and preserves the edits for both encodings on both runtimes. The saved source for v4.12.29 and v4.12.30 still has the unconditional path. The regression therefore shipped in v4.12.28 through v4.12.30. [run; read]

Before the merge, a maintainer had already [called a different mixed-reader failure a bug](https://github.com/honojs/hono/issues/4806#issuecomment-4078784496): "This is a bug. I'll fix it. Thanks you!" That concerned `parseBody()` followed by `text()` or `json()`. It supports mixed reads generally. It does not establish a mutation contract. [read]

The saved history of `src/utils/body.ts` and targeted searches for form mutation, parseBody identity, and repeated parsing disclosed no explicit maintainer statement about N1. The broad cache search also contains unrelated issues. Searches may miss differently worded reports. Later [PR #5366](https://github.com/honojs/hono/pull/5366) changes header handling when rebuilding other remembered body forms. It is not the fix for N1. [read]

## Relation to existing reference families and ruled claims

GT-p1 covers disregarding an already remembered FormData and overwriting it with a new parse. Its registered obligation is that a request with FormData already cached returns the same fields and files through `parseBody()`. N1 reaches that cache-bypass fault with bytes already remembered too. Instead of parsing newly serialized multipart bytes under a mismatching header, it parses the original correctly encoded bytes and loses subsequent edits. [read; run]

I propose folding N1 into GT-p1 as another manifestation of disregarding the remembered form. The changed lines are identical. The missed cache check is identical. The upstream cache-reuse fix restores both sequences. The saved probe runs GT-p1 as a control and shows both restored in v4.12.31. A shared fix alone would not establish duplication; the shared failure to honor the existing FormData is the reason. [read; run; proposed grouping]

The strongest distinction is that GT-p1's precise registered trigger starts with only FormData cached, and its immediate mechanism is a mismatch between serialized bytes and the original header. N1 has original bytes available, needs repeated reads or edits to show its consequence, and has no header mismatch. The owner may choose to keep that narrower family boundary.

N1 does not identify GT-p2 or ruled claim CL-p-concurrent-body-read. All N1 reads are awaited in order. GT-p2 fails while the first parse is still running. Ruling 3 approved that separate family, and band check 5 kept it other-material. [read, packet and saved rulings]

N1 is not CL-p-duplicate-content-type. Its headers are valid. It is not CL-p-parsebody-memory. That claim concerns extra memory on the first read and was ruled advisory in ruling 5. Its recommendation does not settle lost edits. [read, packet and saved rulings]

No first-round ruling decides N1's exact repeated-read or mutation question. No other group in this packet covers it.

## Both sides

For grouping with GT-p1: the new code ignores an existing parsed form and replaces it. N1 demonstrates the same cache ownership mistake without needing the malformed reconstruction in GT-p1. Reusing the cached form fixes both and preserves the PR's intended first-read behavior. The request cache and its purpose were visible before the merge.

Against grouping: the named family specifies re-serialized bytes parsed under the original header. N1 uses valid original bytes and loses edits instead. Different consequences and different prerequisites can justify separate families even when a common cache check fixes them.

For treating N1 separately as a material problem: an application can normalize or remove a field in middleware, then unknowingly use the original value in a handler. The constructed application returns success with that wrong value. The loss is new and was discoverable before merge. Later fixes are confirmation, not the basis for calling the change harmful.

For advice if treated separately: repeated unchanged reads still return correct values. The inspected documentation and callers do not promise or demonstrate that editing the returned FormData changes future parsed request values. Object identity alone has no demonstrated user consequence, and Bun already lacks stable File identity at base. No security bypass or durable data loss was established. The missing supported-use premise matters more than how often a hypothetical application might run this sequence.

## Recommendation

`duplicate` of `GT-p1`, confidence medium. Propose recording repeated decoding and replacement of an already remembered form as an additional manifestation of that cache-bypass fault. Do not add a third family on the strength of object identity alone. This is a recommendation for the owner's ruling, not a ruling or a change to the reference.

Strongest argument against: GT-p1 specifically describes parsing re-serialized bytes with the wrong header. N1 instead discards edits by parsing valid original bytes. If the owner retains that narrow causal boundary, N1 should receive its own threshold decision. The runs prove the changed behavior, but inspected contracts and callers do not establish reliance on mutation sharing.
