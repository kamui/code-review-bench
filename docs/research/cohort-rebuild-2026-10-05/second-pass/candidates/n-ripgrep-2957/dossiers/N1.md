# N1: Sourcing with KSH_ARRAYS prints an error but still loads completion

## Problem

The new check runs with the user's shell settings. With `KSH_ARRAYS` enabled, its two unbraced expressions parse incorrectly and print `bad output format specification`. This happens when the new source command runs from `.zshrc`. The option changes how zsh reads array expressions. [run, read]

Keep this as one problem. Both expressions belong to the same check and have the same shell-option cause. The asserted loss of completion registration is not a second established problem. In the tested setup, registration and actual Tab completion succeed despite the error. [run]

## What changed

The relevant diff in `crates/core/flags/complete/rg.zsh` is:

```diff
-_rg "$@"
+if [[ $funcstack[1] == _rg ]] || (( ! $+functions[compdef] )); then
+  _rg "$@"
+else
+  compdef _rg rg
+fi
```

At head, this check starts at source line 441. It is line 469 in the script produced by the built binary. The generator inserts a list of encodings into the template, accounting for the difference. Both saved generated scripts exactly match their pinned templates with that substitution. [read, run]

The first expression checks whether the completion system is calling `_rg`. The second checks whether the shell has the `compdef` function that registers completions. With `KSH_ARRAYS` enabled, zsh requires braces around these array expressions. The small parsing probe shows `$funcstack[1]` becoming the file name followed by literal `[1]`, and `$+functions[compdef]` becoming `1[compdef]`. The arithmetic condition prints an error and takes the `else` branch. That branch still registers `_rg` for `rg`. [read, run]

Changing only those expressions to `${funcstack[1]}` and `${+functions[compdef]}` removes the error in the sourcing control. That control is evidence for this cause, not a proposed production patch tested in every mode. [run]

Before the change, direct sourcing always called `_rg` outside an active completion. It returned status 1 and registered nothing. With `KSH_ARRAYS`, that old path also printed `bad output format specification`, from `_arguments`, followed by `can only be called from completion function`. The new check introduces its own parsing failure, but the change improves this path overall. It does not turn working sourced completion into broken completion. [run]

## Intended or announced

The [pull request](https://github.com/BurntSushi/ripgrep/pull/2957) promises that users can dynamically source the generated script. Its test plan says the source command should work and Tab should complete `--generate=complete-zs`. The added FAQ offers this line in `.zshrc`, alongside the recommended file-based method. It warns about startup time. It does not exclude `KSH_ARRAYS`, announce a shell-option restriction, or deprecate an existing method. [read]

This probe removes the independent `$ ` prompt defect from the FAQ and supplies `compinit` before sourcing. The startup probe additionally tests enabling `KSH_ARRAYS` before `compinit`. [run]

The change first shipped in the major release [15.0.0](https://github.com/BurntSushi/ripgrep/releases/tag/15.0.0), published on 2025-10-16. The merge commit is an ancestor of that tag and the same check is in that release's script. It is not in the preceding release, 14.1.1. Neither the 15.0.0 release description nor its changelog entry mentions this sourcing change or the shell-option problem. [read]

## What the affected person sees

The affected person enables `KSH_ARRAYS` and uses the advertised source method after initializing completions. Every tested shell startup prints a message such as:

```text
/proc/self/fd/13:469: bad output format specification
```

The file descriptor number varies. The message does not explain that a shell option caused it. However, the source command returns 0, `_comps[rg]` contains `_rg`, and pressing Tab changes `rg --generate=complete-zs` into `rg --generate=complete-zsh `. The shell still runs commands. The user is not stuck searching or completing arguments, although the unexplained startup message can make the setup look broken. [run; the likely confusion is an inference]

| Tested path | Before the change | At head |
| --- | --- | --- |
| Direct source, default options | Error; status 1; no registration; Tab does not finish the option | No error; status 0; completion works |
| Direct source, KSH_ARRAYS | Two errors; status 1; no registration; Tab does not finish the option | One error; status 0; completion works |
| File named `_rg` in the completion search path, default options | First Tab works without an error | First Tab works without an error |
| Same file-based method, KSH_ARRAYS | First Tab works without an error | First Tab works without an error |

These are runs with binaries built from both pinned commits. The terminal probe starts clean zsh sessions and supplies its own completion directory for the file-based cases. Two separate `.zshrc` startups at each commit confirm the repeating message and whether registration survives. [run]

There is evidence that people enable this option in interactive shells. A [public configuration from 2022](https://github.com/langel/bash-stoof/blob/e3fed47dbd92cab72b25fd0f4ecf7a5e03c56632/.zshrc#L10) enables it at top level. A [configuration saved before the merge in November 2024](https://github.com/TomJo2000/.dotfiles/blob/ad9cc9d02189f4e2295b68c89559a2c35ee05922/.zshrc#L27) enables it in its startup function and lists completion plugins. Neither establishes that its owner uses ripgrep's new source command. I did not execute either person's configuration. [read]

The zsh 5.8.1 documentation explicitly describes the option and the need for braces. Its completion system deliberately disables `KSH_ARRAYS` while completing; `compdef` also resets its local options. This explains why registration and Tab work after the top-level check prints an error. This is an established shell setting, not invalid input. Ripgrep does not expressly promise compatibility with every shell setting. [read, run]

## Relation to existing reference families and ruled claims

This is not GT-n1, the stray `$ ` prompt in the FAQ. That problem prevents the source command from running. Here it runs and registers completion. It is not GT-n2 or CL-n-fpath-order, the placement of the completion directory after `compinit`. It is not GT-n3 or CL-n-source-order, sourcing before `compinit`. This error occurs with the prerequisites satisfied. Fixing those documentation problems would not change this expression parsing. [read, run]

The first-round N1, CL-n-source-own-directory, was about `source _rg` being mistaken for a completion call. The owner ruled it advisory in `rulings/10-N1.md`. The first-round N2, CL-n-completion-file-name, was about an alternate file name making the first Tab do nothing. The owner also ruled it advisory in `rulings/11-N2.md`. They share the new check but have different triggers and mechanisms. This second-pass N1 duplicates neither. [read]

## Both sides

For eligibility, the new code has a demonstrable parsing failure in a documented sourcing path. The triggering shell setting is real and supported by zsh, and public configurations show it in use before the merge. The message repeats at startup and provides little help. The advertised improvement remains visibly imperfect. The reviewer could have found this using the pinned code and a contemporary zsh version. [read, run]

Against eligibility, the advertised completion task works at head, including with this option. The shell continues, registration survives, and actual first-Tab completion succeeds. The recommended file-based setup also keeps working. Before the change, direct sourcing in this configuration already printed errors and did not register completion. No run or fetched report establishes a lost user task caused by this residual message. The strongest basis for advice is this limited effect, not the option's rarity or the absence of reports. [read, run]

## Recommendation

`advisory`, with medium confidence. The expression parsing is wrong and correcting it would remove a repeated nuisance. The demonstrated consequence falls below the correction threshold: the new method successfully loads completion and leaves the shell usable. The alleged lost registration is refuted in the stated after-compinit setup. This is a recommendation for a human ruling, not a decision.

Strongest argument against this recommendation: a documented initialization command still emits an unexplained error at every shell start under an established valid shell setting. Even with working completion, the owner may consider that visible failure and the resulting diagnostic burden a problem that should have been corrected before release.
