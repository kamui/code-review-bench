# D4: a thread that ends without closing its connection takes a pool slot for good

Candidates covered: NC-41e17b225b4e, NC-9d5e2612f5b2. One problem, correctly grouped. NC-41e17b225b4e adds a narrow second case about the isolation level, which I could not trigger.

## Problem

Django gives each thread its own database connection. With the pool on, a thread's first query takes a connection out of the pool. The only way back in is `connection.close()`, which Django calls for you at the end of each web request.

A thread that uses the ORM outside a web request and ends without calling `close()` never returns its connection. Python then destroys the connection object and the server session ends, but the pool still counts the slot as in use. The pool does not notice and does not replace it.

After as many such threads as the pool has slots, four by default, nobody in the process can get a connection. Every query waits for the pool timeout, 30 seconds by default, and then fails. Only a restart fixes it.

## What changed

Taking a connection out:

```python
        if self.pool:
            # If nothing else has opened the pool, open it now.
            self.pool.open()
            connection = self.pool.getconn()
```

The only code that puts one back:

```python
    def _close(self):
        if self.connection is not None:
            ...
            with self.wrap_database_errors:
                if self.pool:
                    ...
                    self.connection._pool.putconn(self.connection)
                    # Connection can no longer be used.
                    self.connection = None
```

`_close()` runs only from `close()`. Nothing returns the connection when its wrapper or its thread goes away. `psycopg_pool` keeps a count of connections it has handed out and holds no reference to them, so it cannot tell that one was destroyed.

## Intended or announced

The documentation added by the change does not say that every thread must close its connection, or what happens otherwise. The release note says only that the option exists.

Existing documentation, unchanged, has this about long-running processes: "If a connection is created in a long-running process, outside of Django's request-response cycle, the connection will remain open until explicitly closed, or timeout occurs." That sentence describes an idle connection that stays open. It does not describe a process that loses database access.

A co-author later described the design on the feature ticket: "the connection is checked out at the first SQL operation in a request and returned at the end of the request. So the max size of the pool basically sets a hard limit on how many request you can handle in parallel holding a connection." https://code.djangoproject.com/ticket/33497#comment:51

The change shipped in Django 5.1.

## What the affected person sees

Who: a project that enables the pool and runs ORM code in threads it starts itself, such as a `threading.Thread`, a background job inside a management command, or a framework that calls Django's ORM from its own threads. Before the pool, such a thread lost nothing by not calling `connection.close()`, so existing code often does not.

What they see at head, from `probes/D4/result-head.txt`. The pool has a maximum of 4 and a 3 second timeout to keep the run short. Ten threads run one query each and end:

```
thread  4: query OK; server sessions now: 1; pool counts 4 connections of max 4, 0 available
thread  5: django.db.utils.OperationalError: couldn't get a connection after 3.00 sec (after 3.0s); server sessions now: 1; pool counts 4 connections of max 4, 0 available
...
thread 10: django.db.utils.OperationalError: couldn't get a connection after 3.00 sec (after 3.0s); ...
main thread, same process, afterwards:
  django.db.utils.OperationalError: couldn't get a connection after 3.00 sec (after 3.0s)
```

The server shows almost no open sessions while the pool believes all four are in use. The state never clears. With default settings each failed query takes 30 seconds, so a web worker in this state hangs every request for 30 seconds and then returns an error. The message does not say why no connection is available.

What they saw before: without the pool, at base and at head, all ten threads succeed and leave no sessions behind.

Two users reported this symptom upstream after the release. One, on this pull request: "`django.db.utils.OperationalError: couldn't get a connection after 30.00 sec`. It connects at first, and the connections are stable at 4. After a few queries, the error above starts popping up." They later traced it to their own threads never closing connections. https://github.com/django/django/pull/17914#issuecomment-2214708820

Ordinary web requests are not affected. Django returns the connection at the end of each request, and my D5 runs show reuse across request threads working.

The narrow second case does not hold up. The candidate says that if assigning the isolation level right after taking a connection raises, the connection is lost. I killed the pooled sessions on the server and ran queries with an isolation level configured. The assignment did not raise, the queries failed in the ordinary way, and the pool replaced the dead connections (`probe_isolation.py`).

## What the maintainers did

- The report quoted above drew no maintainer reply. When another user asked about it three months later, a Django team member answered "Please discuss this in a new issue, not here." https://github.com/django/django/pull/17914#issuecomment-2413374255
- On the feature ticket a user reported: "enabling connection pooling in an ASGI context causes connection leaks ... I'm seeing occasional `OperationalError: couldn't get a connection after X sec` errors." Co-author Florian Apolloner: "Whether there really is a leak or not is impossible to tell without having more information about your codebase and settings." https://code.djangoproject.com/ticket/33497#comment:43 Later: "so far noone has shown any logs or an example project to the contrary". https://code.djangoproject.com/ticket/33497#comment:51
- `_close()` is still the only return path on `main` as of 2026-10-03. The documentation there now says "Closing a Django database connection returns it to the pool for reuse." It still does not say what happens when a thread does not close.

No maintainer has acknowledged this as a defect, and none has ruled it out. They asked for evidence and received none.

## How each fact is known

- run: head with the pool fails from the fifth thread on and never recovers; head and base without the pool succeed for all ten (`probes/D4/probe.py`, result files).
- run: the isolation-level case does not lose connections (`probe_isolation.py`, end of `result-head.txt`).
- run: base rejects the pool option.
- read: the diff lines; the `psycopg_pool` 3.3.3 source, which counts connections and keeps no reference to those handed out; the documentation text; `main`.
- read: the upstream comments quoted, fetched on 2026-10-05.
- reported: the two users' production symptoms. I did not reproduce their setups (FastAPI calling the ORM, and an ASGI deployment).
- not run: Django's own ASGI handler under load. I do not know whether it can leave a connection unreturned.

## Relation to existing reference bugs and ruled claims

None. No reference bug concerns connections that are never returned.

## Both sides

For eligible:

- The same program works at base and stops working at head once the pool is on. The failure takes down database access for the whole process and stays until a restart.
- The error text gives no cause. Two upstream users hit it and one maintainer could not diagnose it from a description.
- Until this change a thread that used the ORM and ended without closing cost nothing, so existing code had no reason to close.
- The documentation written for the feature gives no warning.

Against:

- Every connection pool works by checkout and return. Code that does not return what it took exhausts any pool.
- Django's documentation already said connections made outside the request cycle stay open "until explicitly closed". The pool makes ignoring that expensive. It does not create a new duty.
- The pool is opt-in, and web requests, the main supported path, return their connections.
- The maintainers describe checkout-until-close as the design.

## Recommendation

`eligible`, with low confidence in the choice between `eligible` and `advisory`. Enabling the documented option makes a common, previously harmless pattern end in a permanent loss of database access for the process, with no warning in the documentation and no hint in the error.

Strongest argument against: this is how pools behave, and Django already told users to close connections they open outside a request. On that view the change needs a sentence in the documentation, which would make the finding `advisory`.
