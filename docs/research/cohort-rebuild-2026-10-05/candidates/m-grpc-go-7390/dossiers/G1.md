# G1: `updateAddrs` returns with the lock still held

Pull request: grpc/grpc-go #7390, "grpc: hold ac.mu while calling resetTransport to prevent concurrent connection attempts". Commit before the change: `daab5634`. Head: `76ef33f4`. One file changed, `clientconn.go`, +6 −7.

## Problem

A gRPC client keeps one "sub-connection" object per backend. Its state is guarded by a lock called `ac.mu`. When the list of backend addresses changes and the client is connected to an address that is no longer listed, the function `updateAddrs` closes the old connection and starts a goroutine (a lightweight thread) that connects to the new address.

After this change, `updateAddrs` no longer releases `ac.mu` itself. It hands the locked lock to the new goroutine, which releases it a few lines into its work. Two things follow.

1. `updateAddrs` closes the old connection on its way out (a deferred `GracefulClose`). That close needs `ac.mu`. So the caller now waits, on every such address change, until the new goroutine has started and released the lock. While it waits it holds the old connection's own lock (`t.mu`).
2. If there is no old connection to close (the client was still connecting), the caller does not wait. It returns while `ac.mu` is still locked and nothing that owns the lock is running yet.

The candidate says this stalls the caller, stalls anything that needs the old connection's lock or `ac.mu`, and leaves a comment in the code that no longer describes what happens. It also says a future edit could turn the wait into a deadlock.

I kept this as one problem. The stall, the lock left held after return, and the outdated comment all come from the same two changed lines and have the same remedy. Both candidate records (`NC-3509a2750819`, `NC-a4739bf994db`) describe the same mechanism.

Short answer from the runs: the mechanism is real and it is new. It is a wait, never a deadlock. The wait is about 8 millionths of a second in the normal case. No call failed and no call got measurably slower.

## What changed

The end of `updateAddrs`, before and after:

```diff
-	ac.mu.Unlock()
-
 	// Since we were connecting/connected, we should start a new connection
 	// attempt.
-	go ac.resetTransport()
+	go ac.resetTransportAndUnlock()
 }
```

The start of the function that the new goroutine runs:

```diff
-func (ac *addrConn) resetTransport() {
-	ac.mu.Lock()
+// resetTransportAndUnlock unconditionally connects the addrConn.
+//
+// ac.mu must be held by the caller, and this function will guarantee it is released.
+func (ac *addrConn) resetTransportAndUnlock() {
 	acCtx := ac.ctx
```

A few lines above the changed lines, untouched by the pull request, `updateAddrs` schedules the old connection to be closed when the function returns:

```go
	// We have to defer here because GracefulClose => onClose, which requires
	// locking ac.mu.
	if ac.transport != nil {
		defer ac.transport.GracefulClose()
		ac.transport = nil
	}
```

Mechanism, step by step, at the head:

1. `updateAddrs` takes `ac.mu`, decides to reconnect, and runs `go ac.resetTransportAndUnlock()`. The lock is still taken. The new goroutine exists but has not run.
2. `updateAddrs` returns. The deferred `GracefulClose` runs in the caller. It takes the old connection's lock `t.mu` and calls `onClose` (`internal/transport/http2_client.go:1046,1055`).
3. `onClose` starts with `ac.mu.Lock()` (`clientconn.go:1352`). The lock is taken, so the caller sleeps. It still holds `t.mu`.
4. The new goroutine runs. It reads a few fields, computes a deadline, sets the state to `CONNECTING`, and releases `ac.mu` (`clientconn.go:1262`).
5. The caller wakes, finishes `onClose`, releases `t.mu`, and returns.

Before the change, step 1 released `ac.mu` first. The caller then normally took the lock in step 3 at once. It waited only when the new goroutine happened to get the lock first.

Why this is not a deadlock: the new goroutine needs nothing the sleeping caller holds. Before it unlocks it only reads fields, calls the backoff calculator, logs, and queues a state notification (`serializer.Schedule`, which never blocks). It does not touch the old connection, whose `t.mu` the caller holds.

About the comment: it is not false. The close still must be deferred. If it ran before the `go` statement, the caller would wait for a lock that nobody would ever release. What the comment no longer tells a reader is that the deferred close now waits for another goroutine.

## Intended or announced

The lock hand-off is intended. The pull request description says: "This change ensures that caller of `resetTransport()` keep holding the mutex instead of releasing it and having `resetTransport()` re-acquire it." The purpose is to stop two connection attempts from starting at once, which leaked a connection (issue #7365).

The first version of the pull request did something else: it set the state to `CONNECTING` in the caller and then unlocked as before. A reviewer asked to keep the whole thing in one locked section. The author answered on 2024-07-04: "ac.updateAddrs calls `resetTransport` in a new go routine so it can't hold the lock till `resetTransport` completes. It feels a little risky to make that change. I don't know for sure, but I feel we could end up in a situation where the lock is not released correctly resulting in a deadlock. I don't want do make that change as the first option." A few days later the author made that change anyway, and a project member approved it.

The side effect on the deferred close was not discussed anywhere. Nobody mentioned the comment above the `defer`.

Release notes for v1.66.0 (2024-08-28) say: "client: fix race that could lead to orphaned connections and associated resources. (#7390)". They announce no change in locking or timing. The change shipped in v1.66.0, a normal minor release. Nothing was deprecated.

## What the affected person sees

Nothing they could notice. There is no error text, no failed call, no wrong connection state.

Who is on this path: any client using the default load-balancing policy (`pick_first`), each time the name resolver reports a new address list that does not contain the address the client is connected to. `pick_first` calls `UpdateAddresses`, which calls `updateAddrs` (`balancer/pickfirst/pickfirst.go:169`).

What I measured, by switching a connected client back and forth between two local servers. All numbers are from this machine (24 logical CPUs).

**The wait itself, connected client, nothing slowed down**

| Conditions | Before the change | After the change |
| --- | --- | --- |
| 2,000 switches, idle machine | caller waited in 0 of 2,000 (earlier runs: 1 to 6 of 2,000) | waited in 1,995 of 2,000; median 8 µs, 99th percentile about 0.1 ms, longest 0.29 ms |
| 2,000 switches, race detector on | waited in 8 of 2,000, longest 0.04 ms | waited in 1,998 of 2,000; median 25 µs, longest 0.32 ms |
| 300 switches, 4 processors, 16 goroutines burning CPU | waited once, for 40 ms | waited every time; median 15 µs, longest 0.25 ms |
| 200 switches, 2 processors, 8 goroutines burning CPU | never waited | waited every time; median 14 µs, longest 0.04 ms |
| 200 switches, 1 processor, 4 goroutines burning CPU | never waited | waited every time; median 13 µs; one wait of 19.9 ms, all others under 1 ms |

(1 µs is a millionth of a second.) So the change turns a rare wait into one that happens every time, and the usual length is around 10 µs. The long waits (20 ms after, 40 ms before) happen when the machine has more work than processors and the goroutine holding the lock loses its turn. That can happen at either commit.

For scale: in the same deferred close, at both commits, the caller already waits for the old connection's writer to shut down. That existing wait averaged 40 to 140 µs on an idle machine (the higher figure with the race detector on) and 60 to 70 ms on the overloaded ones. The new wait is added in front of it.

**Calls in flight**

Eight callers sent calls continuously during 300 switches. No call failed at either commit. Latency was the same within noise: median 0.77 ms before, 0.81 ms after; 99th percentile 2.1 ms before, 2.3 ms after. With the race detector: median 1.95 ms before, 1.98 ms after.

**Who is held up while the caller waits (window stretched on purpose)**

To see who waits, I stretched the new goroutine's locked start to 300 ms with a test-only hook. This cannot happen in a real program; it only makes the window visible.

| What was timed during the window | Before | After |
| --- | --- | --- |
| The `UpdateAddresses` call (the load balancer's goroutine) | returned at once | 300 ms |
| A call needing the old connection's lock `t.mu` | at once | 270 ms |
| One message round trip on a call already open on the old connection | at once | 270 ms |
| A call needing `ac.mu` | 270 ms | 270 ms |

So after the change, for the length of the window, the load balancer's update goroutine is stopped and calls still running on the old connection stop receiving data. Calls that need `ac.mu` wait the same at both commits, because the connecting goroutine holds `ac.mu` during that part at both commits. Before the change, one round out of 30 across three passes behaved like the "after" column: the new goroutine won the lock first. The pre-change code could produce the same stall, just rarely.

**Lock left held after return (client still connecting, no old connection to close)**

After the change `ac.mu` was still locked when `updateAddrs` returned in 499 of 500 calls. Before the change: 1 of 500. How long it stays locked depends on when the new goroutine gets a processor. A caller that deliberately never pauses could not take the lock for a median of 0.1 ms on 24 processors, and for 14 to 21 ms on a single processor (until the Go runtime forcibly interrupts the caller). A normal caller pauses almost at once, and the new goroutine is next in line on that processor. During this time the sub-connection is not connected, so no call is using it. The things that would wait are closing the client, diagnostics queries, and another connect request.

**Deadlock**

None. About 7,300 switches of a connected client at the head in the final run, under every condition above, all completed. Reading the code agrees: the new goroutine needs nothing the waiting caller holds.

Compared with before the change, then: the same person saw the same behaviour, with roughly 10 µs added to an address change that also tears down one connection and dials another.

## What the maintainers did

- Reviewed and approved the hand-off design. Member `dfawley` asked only for a doc comment: "ac.mu must be held by the caller, and this function will guarantee it is released." When another reviewer asked for a code check that the lock is held, he replied: "I think the name of the function and the comment should be sufficient for this." (https://github.com/grpc/grpc-go/pull/7390#discussion_r1671198458)
- The author voiced a general worry about holding the lock across the `go` statement before adopting it (quoted above, https://github.com/grpc/grpc-go/pull/7390#discussion_r1665560040). That is a worry about the design. It is not an acknowledgement that the merged code has a defect.
- Nobody upstream has reported this. I searched the repository's issues and pull requests for `resetTransportAndUnlock`, `updateAddrs deadlock`, `updateAddrs GracefulClose`, `GracefulClose onClose ac.mu` and `UpdateAddresses blocks ac.mu`. The hits are this pull request and unrelated stack traces and refactors. No advisory.
- Left in place. On upstream `master` at `de4775bf` (2026-10-01), more than two years later, `updateAddrs` still ends with `go ac.resetTransportAndUnlock()`, the deferred `GracefulClose` and its comment are unchanged word for word, and `GracefulClose` still calls `onClose` while holding `t.mu`. Of the 36 later commits to `clientconn.go`, none has a subject about this locking.
- Shipped in v1.66.0.

No maintainer acknowledged this as a defect, fixed it, or said it does not come from this change. They have not addressed it at all.

## Relation to existing reference bugs and ruled claims

The packet lists no reference bugs and no ruled claims for this pull request. It is a control. This problem duplicates nothing.

## Both sides

**For calling it a real bug**

- The mechanism is confirmed by running, and the change introduced it as a regular event. Before, the caller waited in under 1.5% of address changes. After, it waits in more than 99.7%.
- The path is the default one. Every `pick_first` client takes it when its connected address drops out of the resolver's list.
- While the caller waits, it holds the old connection's lock. The stretched run shows what that means: calls still open on the old connection stop receiving data and the load balancer's update goroutine stops, for as long as the new goroutine takes to start and unlock.
- Under CPU overload the wait reached 19.9 ms once in 200.
- `ac.mu` is documented in the code as a lock on the call path whose use should be kept short. It now stays locked across a goroutine start.
- The safety of the design depends on a fact that is not visible at the changed lines: nothing in the new goroutine's locked part may ever block on something the caller holds. The author named this risk during review. The comment above the `defer` does not warn about it.
- A simpler alternative existed and was the pull request's first version: set the state under the caller's lock, unlock, then start the goroutine.

**Against**

- Nothing fails. No error, no wrong state, no lost call, no deadlock, in about 7,300 switches, including runs under the race detector and under CPU overload.
- The wait is about 8 µs, on an operation that closes a connection and opens a new one, which costs milliseconds. The same close already waits 40 to 140 µs for the old connection's writer.
- Calls in flight were not measurably slower.
- The long tail is not new. Before the change the same wait happened occasionally, and its worst measured case (40 ms) was longer than the worst after (about 20 ms). Both come from CPU overload, not from the lock design.
- The 300 ms stall needs a test-only hook. No setting available to a user can stretch the locked part.
- The hand-off was the stated purpose of the change. Two maintainers reviewed it and one explicitly judged the function name and doc comment sufficient.
- The code is unchanged upstream after two years and several releases, with no report against it.
- The deadlock is a prediction about a future edit, not a property of this code.

## Recommendation

**advisory** (confidence: high).

The observation is correct. It does not meet the threshold for a bug. The threshold needs a material consequence, and the measured consequence is a wait of about 10 µs with no failing behaviour for any user. What remains is sound advice about maintainability: the lock is released by a different goroutine than the one that took it, a deferred call now depends on that, and the comment does not say so.

It is not `refuted`, because the mechanism is true. It is not `pre-existing`, because the change made the wait routine and created the "locked after return" state. It is not `eligible`, because nobody is hurt.

**Strongest argument against this recommendation:** the change made correctness depend on a hidden rule, on the default load-balancing path, and the stretched run shows the failure is one slow statement away: anything that blocks in the new goroutine's first lines would freeze calls on the old connection and the load balancer together. The author flagged that exact fear before merging. If the owner counts a newly introduced, reachable lock-ordering hazard as a defect in its own right, without waiting for it to hurt someone, this would be `eligible`. The measured evidence does not support that today: after two years upstream nothing has broken, and no supported configuration can make the window longer than a scheduler delay.
