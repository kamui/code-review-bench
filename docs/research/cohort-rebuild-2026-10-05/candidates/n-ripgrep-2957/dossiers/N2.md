# N2: installed under a file name other than `_rg`, the first Tab of each session completes nothing

Pull request: BurntSushi/ripgrep #2957. Base `79cbe89deb`, head `855bfa6cda`.

## Problem

ripgrep ships a zsh completion script. The usual way to install it is to put the file in a directory zsh searches for completion files (`fpath`). zsh then loads the file the first time the user presses Tab after `rg`.

zsh finds out which command a completion file serves from the file's first line, `#compdef rg`. It does not care what the file is called. A copy named `_ripgrep` is picked up for `rg` just like one named `_rg`.

The new code in this pull request assumes the file is called `_rg`. When it is called anything else, the first Tab after `rg` in a new shell does not complete. The script only re-registers itself and returns. The terminal bell rings and the command line stays as it was. The second Tab works, and so does every later one in that shell. The next new shell starts over.

Before the change the first Tab completed whatever the file was called.

The claim is correct. The grouping is right: this is one problem. It is a different problem from N1, although both come from the same line. N1 is the check running the completion function when the file is being sourced. N2 is the check refusing to run it when the completion system is asking for completions.

## What changed

The last executable line of `crates/core/flags/complete/rg.zsh` was replaced:

```diff
-_rg "$@"
+# Don't run the completion function when being sourced by itself.
+#
+# See https://github.com/BurntSushi/ripgrep/issues/2956
+# See https://github.com/BurntSushi/ripgrep/pull/2957
+if [[ $funcstack[1] == _rg ]] || (( ! $+functions[compdef] )); then
+  _rg "$@"
+else
+  compdef _rg rg
+fi
```

In plain words:

- The file defines a function called `_rg` that does the completing. Its last step used to be "now run `_rg`", always.
- `$funcstack[1]` is zsh's name for whatever is running right now. When zsh loads a completion file from `fpath`, that name is the file's name.
- `compdef` is the zsh command that registers a completion function for a command. `compdef _rg rg` means "use the function `_rg` for `rg` from now on". It completes nothing by itself.
- After the change, the last step runs `_rg` only if the running name is `_rg`. Otherwise it calls `compdef _rg rg`.

With the file installed as `_ripgrep`, the first Tab makes zsh load the file under the name `_ripgrep`. That is not `_rg`, so the script registers `_rg` for `rg` and returns without offering any completions. On the second Tab zsh calls the function `_rg` directly, and it works.

## Intended or announced

Not announced. The pull request describes one purpose: making `source <(rg --generate complete-zsh)` work. It says nothing about file names. The release notes do not mention the change.

The assumption was stated in review. The author wrote: "realistically you will either have `compdef` or will run the completion as `_rg`." https://github.com/BurntSushi/ripgrep/pull/2957#discussion_r1899860561 The exact check that merged was proposed by okdana, who wrote ripgrep's zsh completion. https://github.com/BurntSushi/ripgrep/pull/2957#discussion_r1899864300 Neither comment considers a file with another name.

Every place where the project names the file calls it `_rg`:

- The FAQ at head: `rg --generate complete-zsh > "$dir/_rg"`.
- The man page: "For zsh, move `_rg` to one of your `$fpath` directories."
- The release archive (`complete/_rg`) and the Debian package (`usr/share/zsh/vendor-completions/_rg`).

So installing the script under another name is not something the project's documentation tells users to do. It is also not something the documentation warns against, and zsh allows it.

The change shipped in ripgrep 15.0.0, published 2025-10-16. The same line is still on `master` (latest commit 2026-08-04, fetched 2026-10-05).

## What the affected person sees

Setup: a new interactive `zsh -f` session with an empty configuration. The generated script is the only ripgrep completion file in `fpath`. `compinit` has run. The user types `rg --generate=complete-z` and presses Tab twice.

| File name in `fpath` | Commit | After 1st Tab | After 2nd Tab |
| --- | --- | --- | --- |
| `_rg` | base | `rg --generate=complete-zsh ` | unchanged (already complete) |
| `_rg` | head | `rg --generate=complete-zsh ` | unchanged (already complete) |
| `_ripgrep` | base | `rg --generate=complete-zsh ` | unchanged (already complete) |
| `_ripgrep` | head | `rg --generate=complete-z`, bell | `rg --generate=complete-zsh ` |
| `_rg_completion` | base | `rg --generate=complete-zsh ` | unchanged (already complete) |
| `_rg_completion` | head | `rg --generate=complete-z`, bell | `rg --generate=complete-zsh ` |

There is no error message. The first Tab simply does nothing and the bell rings.

The probe also recorded which function zsh had registered for `rg`. At head with `_ripgrep`, it is `_ripgrep` before the first Tab and `_rg` after it. At base it stays `_ripgrep`.

Who is affected: anyone whose copy of the script, generated by ripgrep 15.0.0 or later, sits in `fpath` under a name other than `_rg`. That can be a user who chose another name, or a user of a plugin or package that renames the file.

When: the first completion attempt after `rg` in every new shell.

How stuck they are: not stuck. A second Tab works. But it happens again in every new shell, it is silent, and nothing points to the file name as the cause. Renaming the file to `_rg` cures it.

Is the renamed install real? Two fetched records bear on that:

- oh-my-zsh, a widely used zsh framework, shipped ripgrep's script as `plugins/ripgrep/_ripgrep` from March 2019 until it removed the plugin on 2024-07-23, five months before this pull request. Its copy ended with the old unconditional `_rg "$@"`.
- A GitHub code search for files named `_ripgrep` containing `#compdef rg` returns 181 files. The first page is mostly vendored copies of that oh-my-zsh plugin, plus a few completion collections.

Those copies were all taken from versions before this change, so they still work. They show that the renamed install is a real practice. They do not show anyone who has renamed a copy generated by 15.0.0 or later. No such report was found.

## What the maintainers did

- The check was proposed by okdana in review, adopted by the author, merged by the repository owner on 2024-12-31 and shipped in 15.0.0.
- Nobody raised the file-name case in the pull request, in issue #2956, or later. Searches of the upstream issue tracker for `funcstack`, `compdef _rg rg`, `_ripgrep`, and zsh items opened after the merge found nothing about this case.
- A later pull request by okdana, #3452 (merged 2026-07-08), reworked large parts of the same file and left this line unchanged. Its description does not mention the check, and it has no comments.
- No maintainer has acknowledged this as a defect. No fix exists. It is still in place.

## Relation to existing reference bugs and ruled claims

This is new. It is not a manifestation of any of the three reference bugs.

- GT-n1 is the stray `$ ` in the FAQ snippet.
- GT-n2 (claim CL-n-fpath-order) is the FAQ not saying that the `fpath` line must come before `compinit`.
- GT-n3 (claim CL-n-source-order) is the FAQ not saying that the `source` line must come after `compinit`.

All three are about the setup steps the documentation prints, and each fails when a user follows those steps. N2 is about the code path that loads the file from `fpath`. It happens with `compinit` run in the right order and with no `source` command at all. It needs a file name the documentation does not use. Fixing any of the three would not change N2.

## Both sides

For calling it a bug of this pull request:

- It is a regression, shown by running both commits. The same install completed on the first Tab before the change and does not after it.
- This pull request's new line is the only cause.
- zsh ties a completion file to its command by the `#compdef` line, not by the file's name. A renamed copy was a working install before.
- A major redistributor shipped the script under the name `_ripgrep` for five years.
- The failure is silent, comes back in every new shell, and gives the user nothing to go on.
- zsh has a way to tell "sourced" from "loaded by the completion system" that does not depend on names. The check did not need to assume a name.

Against:

- Every instruction and every package the project provides names the file `_rg`. A user who follows the documentation is not affected.
- The usual zsh convention is that a completion file is named after the function it defines. A file called `_ripgrep` that defines `_rg` was already off that convention.
- The consequence is small. One extra Tab per shell session, then normal behaviour. No error, no wrong completion, no lost data.
- The assumption was stated in review and accepted by the person who wrote the completion.
- The known renamed copies are old static copies that are not affected. Nobody has reported the problem since 15.0.0 shipped.

## Recommendation

`advisory`. Confidence: medium.

The observation is correct and the regression is reproduced. It falls below the bar because it needs an install the project does not document, and because the affected person is not stuck: the second Tab works and renaming the file cures it.

Strongest argument against this recommendation: this is a true before-and-after regression in the main, non-sourcing way of installing the completion, caused by a name the script had no need to assume. zsh accepts the renamed file, a well-known framework distributed it that way for years, and the failure repeats silently in every new shell. If "supported use" means what zsh supports and not only what ripgrep's FAQ prints, the claim is `eligible`.
