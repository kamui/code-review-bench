# N1: `source _rg`, typed from the directory that holds the file, still fails

Pull request: BurntSushi/ripgrep #2957. Base `79cbe89deb`, head `855bfa6cda`.

## Problem

ripgrep ships a zsh completion script. `rg --generate complete-zsh` prints it. This pull request lets a user load that script with `source`, which failed before.

The new code decides between two cases by looking at one name. If the name is exactly `_rg`, it assumes zsh's completion system is calling it and runs the completion function. Otherwise it assumes it is being sourced and registers the function for later.

When a user saves the script as `_rg`, changes into that directory and types `source _rg`, zsh reports the name as `_rg`. The check takes this for a completion call. It runs the completion function outside of completion, zsh prints an error, and nothing is registered. Typing the same file as `source ./_rg` or with a full path works.

The claim is correct. The grouping is right: this is one problem. It is a different problem from N2, although both come from the same line. N1 is the check saying "completion call" when the file is being sourced. N2 is the check saying "sourced" when the completion system is calling.

## What changed

The last executable line of `crates/core/flags/complete/rg.zsh` was replaced:

```diff
-_rg "$@"
+# Don't run the completion function when being sourced by itself.
+#
+# See https://github.com/BurntSushi/ripgrep/issues/2956
+# See https://github.com/BurntSushi/ripgrep/pull/2957
+if [[ $funcstack[1] == _rg ]] || (( ! $+functions[compdef] )); then
+  _rg "$@"
+else
+  compdef _rg rg
+fi
```

In plain words:

- `$funcstack[1]` is zsh's name for whatever is running right now. For a function it is the function name. For a sourced file it is the file name exactly as the user typed it.
- `compdef` is the zsh command that registers a completion function for a command. It exists only after the user has run `compinit`, which switches on zsh's completion system.
- Before the change the script always ran the completion function `_rg` at the end. That is correct when the completion system loads the file, and an error when a user sources it.
- After the change the script runs `_rg` only if the running name is `_rg` or `compdef` does not exist. Otherwise it calls `compdef _rg rg`, which is what a sourcing user needs.

The check cannot tell "the completion system is running the function `_rg`" from "the user sourced a file they typed as `_rg`". Both give the name `_rg`.

The probe shows the names zsh reports for the same file:

| How the file is sourced | Name zsh reports |
| --- | --- |
| `source _rg` | `_rg` |
| `source ./_rg` | `./_rg` |
| `source /full/path/_rg` | the full path |
| `source <(rg --generate complete-zsh)` | `/proc/self/fd/11` |

Only the first row equals `_rg`.

## Intended or announced

The pull request and its merge commit promise one thing: `source <(rg --generate complete-zsh)` works. That form works at head.

The FAQ at head gives two zsh methods. The recommended one saves the script to `$HOME/.zsh-complete/_rg` and adds that directory to `fpath`, the list of directories zsh searches for completion files. The second one puts `source <(rg --generate complete-zsh)` in `.zshrc`. Neither tells the user to `source` the saved file. The man page says only "move `_rg` to one of your `$fpath` directories".

So `source _rg` on a saved file is not something the project's documentation tells users to do.

Two things point the other way. The new code comment states its purpose broadly: "Don't run the completion function when being sourced by itself." The pull request description and the merge commit message both open with "Previously, you needed to save the completion script to a file and then source it." That sentence treats sourcing a saved file as a normal thing to do. It is also inaccurate about the old behaviour: at base, sourcing the saved file failed under every spelling (see below).

The review discussion does not mention this case. The release notes do not mention the change at all.

The change shipped in ripgrep 15.0.0, published 2025-10-16. The same line is still on `master` (latest commit 2026-08-04, fetched 2026-10-05).

## What the affected person sees

Setup: a new `zsh -f` session with an empty configuration, the script saved as `~/.zsh-complete/_rg`, `compinit` already run.

At head, `cd ~/.zsh-complete && source _rg` prints:

```
_arguments:comparguments:325: can only be called from completion function
```

The exit status is 1. No completion is registered for `rg`. Pressing Tab after `rg --generate=complete-z` rings the bell and completes nothing.

This is the error from issue #2956, the one the pull request set out to remove. (The issue shows line 327; zsh 5.8.1 here prints 325.)

At base the same command prints the same error with the same exit status, and completion is likewise not registered. So the person who types `source _rg` saw exactly this before the change. The change did not make it worse for them. What changed is that the other spellings now work:

| Command, after `compinit` | Base | Head |
| --- | --- | --- |
| `cd ~/.zsh-complete && source _rg` | error, status 1, not registered | error, status 1, not registered |
| `cd ~/.zsh-complete && source ./_rg` | error, status 1, not registered | no output, status 0, registered, Tab completes |
| `source ~/.zsh-complete/_rg` | error, status 1, not registered | no output, status 0, registered, Tab completes |
| `source <(rg --generate complete-zsh)` (the documented form) | error, status 1, not registered | no output, status 0, registered, Tab completes |
| `eval "$(rg --generate complete-zsh)"` | error, status 1, not registered | no output, status 0, registered |
| same file saved as `rg-completion.zsh`, `source rg-completion.zsh` | error, status 1, not registered | no output, status 0, registered |

Who is affected: someone who generated the file into the current directory, or changed into the directory that holds it, and typed `source _rg` with no path. Only the exact name `_rg` with no directory part triggers it.

How stuck they are: the error text does not say that the spelling of the path matters, so the cause is hard to guess. Both documented methods work, so a user who goes back to the FAQ gets completion.

One more case matters. If the user followed the FAQ's recommended method, so the directory was in `fpath` before `compinit`, completion for `rg` is already registered. Typing `source _rg` then prints the same error, but Tab still completes afterwards. For that user the error is noise, not a loss of completion.

## What the maintainers did

- The check was proposed in review by okdana, who wrote ripgrep's zsh completion, and the author adopted it. https://github.com/BurntSushi/ripgrep/pull/2957#discussion_r1899864300
- The repository owner merged it on 2024-12-31 and it shipped in 15.0.0.
- Nobody raised this case in the pull request, in issue #2956, or later. Searches of the upstream issue tracker for `funcstack`, `compdef _rg rg`, the error text, and zsh items opened after the merge found nothing about this case.
- A later pull request by okdana, #3452 (merged 2026-07-08), reworked large parts of the same file and left this line unchanged. Its description does not mention the check, and it has no comments.
- No maintainer has acknowledged this as a defect. No fix exists. It is still in place.

## Relation to existing reference bugs and ruled claims

This is new. It is not a manifestation of any of the three reference bugs.

- GT-n1 is the stray `$ ` in the FAQ snippet. A documentation typo. Unrelated.
- GT-n2 (claim CL-n-fpath-order) is the FAQ not saying that the `fpath` line must come before `compinit`. Unrelated to sourcing.
- GT-n3 (claim CL-n-source-order) is the closest. There the user sources the script before `compinit`, so `compdef` does not exist, and the second half of the same check runs the completion function. N1 happens after `compinit`, with `compdef` present, through the first half of the check. The trigger differs (how the path is typed, not where the line sits in `.zshrc`). The error text differs too: the probe's control run before `compinit` prints `_rg:341: command not found: _arguments`, while N1 prints `can only be called from completion function`. Fixing GT-n3 would not fix N1, and fixing N1 would not fix GT-n3.

GT-n2 and GT-n3 are about steps the FAQ tells the user to take. N1 is about a step the FAQ does not mention.

## Both sides

For calling it a bug of this pull request:

- The pull request exists to make `source` work. Its own code comment says the completion function must not run when the file is sourced. Here it runs.
- The user gets the very error the pull request set out to remove.
- The description and the merge commit message speak of saving the script to a file and sourcing it as an ordinary workflow.
- `rg --generate complete-zsh > _rg` followed by `source _rg` is a natural thing to type.
- Whether it works depends on how the path is spelled, and the error gives no hint of that.
- zsh has a way to tell the two cases apart that does not depend on names. The check could have used it.

Against:

- The behaviour for this exact command is the same at base and at head: same error, same exit status, same result. The change did not introduce it and did not make it worse. It fixed the neighbouring cases and missed this one.
- The documentation never tells a user to source the saved file. Both documented methods work.
- The trigger is narrow: the name must be exactly `_rg` with no directory part.
- A user who followed the recommended method already has completion; for them the error changes nothing.
- No user has reported it since 15.0.0 shipped, and no maintainer has treated it as a defect.

## Recommendation

`advisory`. Confidence: medium.

The observation is correct and reproduced. It points at a real gap in the new check, and closing it would be an improvement. It falls below the bar because the failing command is not a documented use, and the person who types it sees exactly what they saw before the change.

`pre-existing` is the nearest other label, since the visible behaviour is unchanged. `advisory` fits better because the cause at head is new code that this pull request wrote, and the advice is about that code.

Strongest argument against this recommendation: the fix is incomplete on its own terms. The pull request promises that sourcing the script works, the description treats sourcing a saved file as normal, and the most natural spelling of that command still produces the original error. On that reading the unmet promise is new with this change, as it was for GT-n3, and the claim is `eligible`. What separates the two is that GT-n3's trigger is a step the FAQ prints, and N1's is not.
