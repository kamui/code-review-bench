# H3: `c.req.parseBody()` now holds a second full copy of the request body in memory

Pull request: honojs/hono #5067. Commit before the change: `9728702`. Head: `5226d41`.

## Problem

`c.req.parseBody()` is Hono's documented way to receive form posts, including file uploads.

After this change, `parseBody()` reads the whole body into memory as raw bytes, then parses those bytes into a form. It keeps both the raw bytes and the parsed form (with its files) attached to the request until the request ends. Before, it kept only the parsed form.

Measured for one 100 MB file upload on Node 24.7.0, memory above the idle process:

- highest point during the request: **313 MB before, 445 MB after** (445 is the lowest of three runs; the other two were 509 MB);
- held after parsing, while the handler still runs: about 145 MB before, about 245 MB after.

On Bun 1.3.10 the highest point went from 211 MB to 310 MB, and the held amount from 110 MB to 210 MB.

So each upload costs about one extra body size of memory, and the peak rises by roughly 40 to 60 percent. The claim that the peak "roughly doubles" is too high for the peak. For memory held after parsing it is close on Bun (110 to 210 MB) and somewhat high on Node (145 to 245 MB).

Nothing returns a wrong result. The effect is higher memory use. It becomes a failure only when the process has a memory limit that the old peak fitted under and the new peak does not.

## What changed

`src/utils/body.ts`, function `parseFormData`:

```diff
-  const formData = await (request as Request).formData()
+  const headers = request instanceof HonoRequest ? request.raw.headers : request.headers
+  const arrayBuffer = await (request as Request).arrayBuffer()
+  const formDataPromise = bufferToFormData(arrayBuffer, headers.get('Content-Type') || '')
+  if (request instanceof HonoRequest) {
+    // Cache so that a later `c.req.formData()` reuses the already-consumed body
+    request.bodyCache.formData = formDataPromise as unknown as FormData
+  }
+  const formData = await formDataPromise
```

and `src/utils/buffer.ts`, `bufferToFormData` (existing helper, one line changed to lower-case the media type):

```ts
const response = new Response(arrayBuffer, { headers: { 'Content-Type': ... } })
return response.formData()
```

- Before: `parseBody()` asked the runtime to parse the incoming body as a form. The request kept one thing: the parsed form.
- After: `parseBody()` asks for all the bytes first. A Hono request remembers every form in which its body was read, so the bytes are now remembered too (`bodyCache.arrayBuffer`). The bytes are then wrapped in a new `Response` and parsed, and the parsed form is remembered as well (`bodyCache.formData`). Both stay until the request object is released.

Why the author did it this way: the goal was to accept `Content-Type` values written in mixed case, such as `Multipart/Form-Data`. Bun's own form parser rejects mixed-case values (run: `probes/H3/result-native-case.txt`), so only fixing the check at the top of `parseBody()` would not have been enough on Bun. Re-parsing the bytes under a lower-cased header makes it work on every runtime. Node's parser accepts mixed case as it is.

## Intended or announced

- The pull request description is only `Fixes #5060` and a checklist. It says nothing about memory.
- Issue #5060 asked for case-insensitive matching. It did not ask for a change in how the body is read.
- The automatic benchmark comment on the pull request reports request throughput, not memory: "Body" 35,864 before and 35,802 after, a change of -0.17%. It does not exercise large uploads.
- One test was changed because of the new path: a test that replaced `req.formData` with a fake no longer reached the code, so it was rewritten to send real form data.
- No documentation changed. The documentation page for `parseBody()` presents it for file uploads ("Single file", "Multiple files").
- Shipped in v4.12.28, a patch release, on 2026-07-06. The release note lists the pull request as a fix and does not mention memory.
- The same read-all-bytes-then-parse approach already existed in Hono before this change, in `validator('form', ...)`. At the commit before the change, an upload read through the validator used exactly the memory that `parseBody()` uses after the change (445 MB peak for 100 MB on Node; run).

## What the affected person sees

The affected person is whoever runs a Hono app that accepts large uploads through `c.req.parseBody()` on a machine or container with limited memory.

With enough memory they see nothing except higher usage per upload.

With a tight limit, an upload that used to fit no longer does. Demonstrated: a Node process limited to 420 MB by the operating system, receiving one 100 MB upload.

- Before the change: HTTP 200, three runs out of three.
- At head: the operating system kills the process (exit status 137), three runs out of three. The kernel log says "Memory cgroup out of memory: Killed process".

The 420 MB limit was chosen to sit between the two measured peaks, so this shows that such a band exists; it does not show how many deployments sit in it. For any limit, the largest upload that fits drops by about 30 percent on Node (peak about 3.1 times the upload before, 4.5 times or more after).

When it does happen, the whole server process dies, not one request, and there is no JavaScript error or stack trace to point at the cause.

How stuck they are: they can raise the memory limit, lower the allowed upload size (Hono ships a body-limit middleware), or read the upload with `c.req.formData()`, which at head still uses the old path and keeps one copy.

## What the maintainers did

- Nobody reported a memory problem upstream. Searches of the repository's issues and pull requests for `parseBody` with memory or large uploads found only older, unrelated items.
- No maintainer has commented on the memory cost of this change. Nobody acknowledged it as a defect and nobody said it was intended.
- The code is unchanged in this respect in the latest release, v4.13.13 (2026-10-04). Measured there: both entries still held, 445 MB peak for 100 MB on Node, 310 MB on Bun.
- Later work kept and built on the bytes-first path: #5131 (v4.12.31) added an early return when a parsed form is already cached and left the rest as it was; a contributor's later pull request #5384 describes the path as the right one ("`c.req.parseBody()` already gets this right: it reads the bytes first and parses them afterwards"). That is a contributor's statement, not a maintainer's, and that pull request was not merged.
- The pull request had no human review. It was opened and merged by its author within three minutes.

## Relation to existing reference bugs and ruled claims

H3 comes from the same new lines as GT-p1 (`parseBody()` reading bytes itself), but it is a different problem. GT-p1 is a wrong result when the body was already read as a form. H3 is extra memory on the ordinary first read, with correct results. Fixing GT-p1 the way upstream did (#5131) leaves H3 as it is (run on v4.13.13).

There are no ruled claims for this pull request. H3 does not overlap H1 or H2.

## Both sides

For counting it as a bug of this change:

- The cost is real and measured: about one extra body size per upload, a 40 to 60 percent higher peak, on a path the documentation offers for file uploads.
- It can turn into a hard failure. Under a memory limit between the old and new peak the server process is killed, taking every request in flight with it, with nothing in the application's logs.
- It arrived in a patch release whose notes describe a header-matching fix.
- It was not needed everywhere. On Node the runtime parser already accepts mixed-case types (run). A fix that handed the body stream to a `Response` carrying the corrected header, without first collecting all bytes, looks possible and would avoid the second copy. That alternative was not built or run here.

Against:

- No request gets a wrong answer. This is a resource cost, and how much memory is acceptable is a judgment.
- The old path also held the whole upload in memory, at about three times its size at the peak on Node. Large uploads through `parseBody()` were never cheap, and an app that needs a ceiling is expected to set a body limit.
- The project already used the same approach in `validator('form')`, with the same cost, before this change. The change made `parseBody()` match an existing pattern.
- Some buffering was needed for the fix to work on Bun.
- The kill under a limit was built by choosing a limit between the two peaks. Any increase in memory has such a band. No real deployment is known to sit in it.
- Nobody reported it in three months, and the maintainers kept the path and built on it.

## Recommendation

`advisory`, confidence medium.

The observation is correct and now measured (313 to 445 MB peak for a 100 MB upload on Node). It is a performance cost with correct results, in line with a pattern the project already used, with no upstream complaint and no maintainer treating it as a defect. That reads as sound advice below the bar for a bug.

Strongest argument against: for an operator with a memory limit, this is not a slowdown but a crash. The run under a 420 MB limit shows a 100 MB upload that worked before the change killing the whole server after it, and the person hit gets no error to diagnose. If the owner weighs that outcome by who is hurt and not by how many deployments sit near their limit, `eligible` is defensible.
