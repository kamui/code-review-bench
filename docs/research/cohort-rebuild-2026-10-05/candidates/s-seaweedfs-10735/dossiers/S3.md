# S3: a delete that runs in between the cleanup's three commands

Pull request: seaweedfs/seaweedfs #10735, "fix(redis2): remove orphaned directory index members on listing".
Candidates covered: NC-df1ff3bbbff1.

## Problem

Read S1 first for the background (value, name in the directory's list, orphan).

The cleanup is three separate Redis commands: remove the name, ask whether the value exists, add the name back if it does. Another request can run between them. S3 is about a *delete* running in that gap, after the same path was created again. Three effects are claimed:

- **(a) A stale name is added back.** The file is deleted between the question and the add-back. The add-back then puts a name in the list for a file that no longer exists. If the directory was deleted too, the add-back creates a new list for a directory that no longer exists.
- **(b) A recursive delete skips a live file.** The whole directory is deleted while the name is out of the list. The delete walks the list, does not see the file, and leaves its value in Redis. The add-back then creates a list for the deleted directory. If the directory is created again later, the file shows up in it.
- **(c) A listing that runs in the gap does not show the file.**

Grouping: I kept these as one problem. They have one cause (the gap between the removal and the add-back), come from one candidate, and get the same recommendation. Only (b) leaves anything behind that does not clean itself up.

It is not the same as S1/S2 (no failure is involved here) and not a manifestation of GT-s1 or GT-s2. See "Relation" below.

## What changed

The added helper (`weed/filer/redis2/universal_redis_store.go`, head lines 237-251):

```go
+	if err := store.Client.ZRem(ctx, dirListKey, fileName).Err(); err != nil {
+		return
+	}
+	...
+	exists, err := store.Client.Exists(ctx, store.getKey(string(path))).Result()
+	if err == nil && exists == 0 {
+		return
+	}
+
+	store.Client.ZAddNX(ctx, dirListKey, redis.Z{Score: 0, Member: fileName})
```

Between `ZRem` and `ZAddNX` the name of a possibly live file is out of the list. `DeleteFolderChildren` (unchanged, lines 145-170) deletes only the values of names it finds in the list. `ZAddNX` creates the list key if it does not exist.

Before the change the name never left the list on this branch, so there was no such gap.

## Intended or announced

- The pull request description presents the three-command form as a deliberate choice, because one atomic step is not possible on the cluster store: "a multi-key script would be `CROSSSLOT` under `redis_cluster2`. The compensating form uses only single-key commands".
- It argues that the form "converges in both interleavings" of a concurrent *insert*. It says nothing about a concurrent *delete*.
- No documentation change. First released in 4.42 (2026-08-17), together with the maintainer's follow-ups.

## What the affected person sees

Every case needs the same path to be created again inside the one-round-trip gap of a listing (as in S1), **and** a delete by a third request inside the next one or two round trips.

**(a) Stale name added back** (run, scenarios A and A2):

- After the listing and the delete, the list holds `f` and `f` has no value. That is an ordinary orphan.
- The next listing removes it (run). Nobody sees a wrong result; the cost is one extra lookup and one log line.
- If the directory was deleted too, one stray list key stays in Redis for a directory that does not exist. When the directory is created again, its first listing shows nothing and removes the stray name (run).
- Before the change: this exact case cannot occur, but orphans of any origin stayed in the list forever, with a log line on every listing.

**(b) Recursive delete skips a live file** (run, scenario B):

- The person deletes the directory recursively. The delete reports success. The directory is gone.
- The file created a moment earlier is still in Redis and can still be read by its full path (run: `FindEntry` finds it). Its data is not removed.
- If someone creates the directory again, the file appears in its listing (run).
- Nothing is lost. Something that should have been deleted survives, and nothing reports it.
- Before the change, with the same three requests in the nearest possible order, the delete sees the file and removes it (run at the base, scenario B0; the same holds at the head when the delete runs one step earlier).
- **The same end state already exists without this change and without any listing** (run at the base and at the head, scenario C): a new file is inserted while its directory is deleted recursively, with the delete landing between the insert's two commands. Result at both commits: the directory is gone, the file's value is in Redis, a list for the deleted directory holds its name, and the file appears when the directory is created again. That needs two requests, not three.

**(c) A listing in the gap misses the file** (run, scenario D): the second listing returns nothing for that file; the next one shows it. One missed listing, no lasting effect. The listing that performs the cleanup has the same one-time miss even with no third request (run, S1 scenario B).

Who is affected: users of the `redis2` store family whose directories have expiring entries, when a re-create, a listing and a delete of the same place fall within about a millisecond of each other. No report of it was found.

## What the maintainers did

- **(a) was raised on a follow-up and the maintainer accepted it as it is.** On #10744 a review bot wrote "Repair resurrects deleted index member". The maintainer chrislusf answered, verbatim: "Known and accepted: for a file member this self-heals on the directory's next listing (value gone, index empty, member dropped); the rmdir variant leaves one stray zset key until the path is recreated. Closing it for real needs the value and index keys in one atomic step, which is CROSSSLOT under redis_cluster2 — same constraint that shaped #10735." (https://github.com/seaweedfs/seaweedfs/pull/10744#discussion_r3777726360). This is a statement that the behaviour is known and will stay. It is not an acknowledgement of a defect. My runs agree with his description of both variants.
- **(b) was not discussed by anyone upstream.** No comment, issue or fix names a recursive delete skipping a file because of the cleanup's gap.
- **The wider class, an entry created while its folder is being deleted, was treated by the maintainer as an existing problem of the filer and of the Redis stores**, in #10783 (merged 2026-08-17, in 4.42): "An entry created in between ends up reachable by its own path ... but absent from `ListObjectsV2` and every other traversal, because the directory that would have carried it is gone." His remedy there keeps the entry and restores the folder. It does not name #10735.
- Left in place: scenarios A, A2, B, C and D give the same results at the follow-up #10743 commit and at release 4.42 (run at the store level; the filer-level folder restore of #10783 was not exercised).

## Relation to existing reference bugs and ruled claims

- **GT-s1** (replica reads): unrelated. No replica is involved.
- **GT-s2 / CL-s-update-membership** (an update after expiry): unrelated. No `UpdateEntry` is involved, and in S3 the name is put back.
- **S1/S2**: same helper, different trigger. S1/S2 need a failing command; S3 needs a third request and no failure.

S3 is not a manifestation of an existing reference bug or ruled claim.

## Both sides

For calling it a bug of this change:

- Route (b) is new. At the base, a file that fully exists before a recursive delete starts is always deleted. At the head it can be skipped, silently.
- What is left does not clean itself up: a file in a directory that no longer exists, which comes back if the directory is created again.
- The description argues convergence only for inserts and does not consider deletes.

Against:

- (a) and (c) repair themselves on the next listing and show nobody a wrong result. The maintainer called (a) "Known and accepted".
- (b) needs three independent requests on the same place within about a millisecond: a re-create inside one round trip of a listing, then a recursive delete whose reads fall inside the next two.
- The end state of (b) is reachable at the base by a simpler two-request race (run). The store has never been atomic against a delete of the parent. Upstream handled that class separately, as a filer-wide matter.
- In (b) nothing is lost. A delete left one file behind.
- The fix would be the atomic multi-key step that the cluster store cannot do, which is the constraint the pull request explains.

## Recommendation

**advisory**, confidence medium.

The observation is correct and reproduced. Its self-healing parts have no failing behaviour for a user, and the one lasting part needs a three-way coincidence and ends in a state the store could already reach before this change.

Strongest argument against: route (b) is attributable to this change, it makes a recursive delete silently leave a just-written file behind, and that file reappears when the directory is created again. If the owner weighs that silent survival as a failed delete for the person who asked for it, (b) alone could be **eligible**, and it would then be worth splitting from (a) and (c).
