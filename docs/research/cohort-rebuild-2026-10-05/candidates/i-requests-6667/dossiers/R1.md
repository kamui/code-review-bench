# R1: a plain `http://` request through an `https://` proxy gets the shared verified TLS context with verification switched off

Candidates: NC-ab95b1ed045c, NC-9a6319076a6f. Pull request: psf/requests #6667, base `8dd3b26b`, head `4089f3dc`.

## Problem

A program sends a plain `http://` request through a proxy whose own address is `https://`, with the default `verify=True`:

```python
requests.get("http://host/", proxies={"http": "https://proxy:443"})
```

Before the change the request completed. After the change one of two things happens, depending on the installed urllib3. requests supports both lines (`urllib3>=1.21.1,<3`).

- **urllib3 2.x:** the request raises `ValueError: Cannot set verify_mode to CERT_NONE when check_hostname is enabled.` It is not a requests exception.
- **urllib3 1.26.x:** the request completes, but it switches the one TLS context shared by the whole process to "do not verify". While that is in effect, ordinary `verify=True` requests in other threads accept certificates they must refuse.

A second route gives the same result: an adapter subclass that turns verification off inside `cert_verify` (exchangelib's `NoVerifyHTTPAdapter` does this).

Grouping: the two candidates are one problem. It is closely linked to R7a. On urllib3 2.x, R7a decides whether this request fails loudly or switches verification off silently. I recommend the owner rule R1 and R7a together.

## What changed

The change builds one TLS context when `requests` is imported and hands it to every connection pool whose request has `verify=True`. It does not look at whether the request URL is `https`:

```diff
     cert_reqs = "CERT_REQUIRED"
     if verify is False:
         cert_reqs = "CERT_NONE"
-    if isinstance(verify, str):
-        pool_kwargs["ca_certs"] = verify
+    elif verify is True:
+        pool_kwargs["ssl_context"] = _preloaded_ssl_context
```

A later, unchanged step in `cert_verify` decides that a non-`https` URL needs no verification and records that on the pool:

```python
        else:
            conn.cert_reqs = "CERT_NONE"
            conn.ca_certs = None
            conn.ca_cert_dir = None
```

For an `http://` URL sent through an `https://` proxy, the pool is a TLS connection to the proxy. So the pool now holds two things that contradict each other: the shared context, which is set up to verify, and the instruction "do not verify". When urllib3 connects, it writes the instruction into the context it was given (`context.verify_mode = CERT_NONE`).

- urllib3 2.x creates contexts with hostname checking on. Python refuses to turn verification off on such a context and raises `ValueError`. requests does not catch it.
- urllib3 1.26.x creates contexts with hostname checking off (it checks hostnames itself). The write succeeds. The context is shared, so every other thread that is in the middle of a verified handshake now runs with verification off, or skips its hostname check because it sees the mode is "none".

Before the change the pool had no context. urllib3 built a private one for that pool and nothing was shared.

## Intended or announced

Not intended and not announced.

- The pull request description speaks only of verified connections: "If a verified connection is requested, `_urllib3_request_context()` already makes it so that a connection pool using a `SSLContext` with all relevant certificates loaded is always used."
- A commenter mentioned proxies before merge and said they might not be covered: "we use `session.get(proxies={...})` which leads to even more pools and SSLContext initializations (this part might not yet be covered by this PR)". Nobody followed up.
- A CPython core developer warned in the thread that a shared context must not be reconfigured: "changing ciphers, verification settings, or mTLS certs can lead to surprising behavior. The problem is unrelated to threads and can even occur in a single-threaded program." (https://github.com/psf/requests/pull/6667#issuecomment-2094634639)
- The 2.32.0 release note lists the change as an improvement: "`verify=True` now reuses a global SSLContext which should improve request time variance between first and subsequent requests."
- It shipped in 2.32.0 (2024-05-20, a minor release) and stayed through 2.32.4. No documentation changed.

## What the affected person sees

**Who:** anyone whose plain-HTTP traffic goes through an HTTPS proxy. The proxy can come from `proxies=`, from `Session.proxies`, or from the `http_proxy` environment variable, so the person running the program may not have written any proxy code.

**urllib3 2.x, after the change:** every such request fails with

```
ValueError: Cannot set verify_mode to CERT_NONE when check_hostname is enabled.
```

The message does not mention proxies. It is a built-in `ValueError`, so `except requests.RequestException` does not catch it and retry logic does not see it. The same request worked in 2.31.0. Ways out: pass `verify=False` or `verify=<CA file>` on those requests, remove the proxy, pin `requests<2.32`, or (from August 2025) upgrade to 2.32.5.

**urllib3 1.26.x, after the change:** nobody sees an error. In a 20-second run with three threads sending proxied `http://` requests and six threads making ordinary `verify=True` requests to two servers that must be refused:

| | certificate for the wrong host name | certificate from an untrusted CA |
| --- | --- | --- |
| before the change | 0 of 500 accepted | 0 of 502 accepted |
| after the change | 743 of 3436 accepted | 251 of 3713 accepted |
| release 2.32.4 | 710 of 3193 accepted | 214 of 3468 accepted |
| release 2.32.5 | 0 of 525 accepted | 0 of 532 accepted |

A single-threaded program is not affected in this way: the next verified connection sets the mode back before it connects.

**Before the change:** the request completed. requests did not check the proxy's certificate for `http://` targets at all (the probe's proxy with an untrusted certificate was accepted at the base too). That weakness is older than this change and is not part of this problem.

## What the maintainers did

- No maintainer named this trigger or this consequence.
- Issue #6719 (2024-05-23) reports the same error text on 2.32.0 through the second route, a custom adapter used by exchangelib. A maintainer closed it within the hour as a duplicate, without analysis: "In the future, please search **closed and** open issues before creating new ones that are duplicates." (https://github.com/psf/requests/issues/6719#issuecomment-2127036358)
- The fix in 2.32.3 (#6716) skips the shared context only when an adapter supplies its own context. It does not help here: 2.32.3 and 2.32.4 still raise.
- The revert (#6767, opened 2024-07-18, merged 2025-06-13, released in 2.32.5 on 2025-08-18) removes the shared context and with it this problem. Its description: "Due to the number of edge cases and concurrency issues we've encountered with this change, we've decided the benefit doesn't currently outweigh the pain to existing infrastructure."
- The repository's security advisories do not mention the shared context.
- Outside the repository: sgl-project/sglang #7883 (2025-07) shows this traceback from `requests.get("http://127.0.0.1:30000/...")` and the reporter's fix was to unset the proxy environment variables. A user on urllib3 #3472 wrote that a "similar problem ... happens on all previous 2.32.x versions" and is fixed by 2.32.5.

## How each fact is known

- run: `ValueError` at head and success at base, for `proxies=`, `Session.proxies` and `http_proxy`; `verify=False` and `verify=<file>` still work; the error escapes `except requests.RequestException` (`probes/R1/probe.py`, `result-base.txt`, `result-head.txt`).
- run: the same on urllib3 2.8.0; no error on urllib3 1.26.18 (`result-*-urllib3-*.txt`).
- run: releases 2.31.0 (works), 2.32.0, 2.32.3, 2.32.4 (raise), 2.32.5 (works) (`result-release-*.txt`).
- run: the second route (adapter that disables verification in `cert_verify`) raises at head and in 2.32.0 to 2.32.4 (case 9 of the same probe).
- run: the concurrency counts in the table, and that the shared context reads `verify_mode=CERT_NONE` after one proxied request on urllib3 1.26.18 (`probes/R1/probe_race.py`, `result-race-*.txt`). This is real thread timing; the counts change from run to run.
- read: the diff lines, `cert_verify`, the pull request thread, release notes, #6719, #6716, #6767, the advisory list (`upstream/`).
- reported: the sglang issue and the urllib3 #3472 comment. The sglang traceback matches this path; the proxy URL itself is not shown there.

Not run: a real network attacker, and Python builds without the global interpreter lock.

## Relation to existing reference bugs and ruled claims

This is new. It is not a manifestation of GT-i1 to GT-i4.

- GT-i1 is about an adapter's own `ssl_context` being replaced. No adapter is involved in the main route here. The second route (an adapter that turns verification off) is next to GT-i1 but GT-i1's obligation does not describe it, and the fix for GT-i1 did not fix it.
- GT-i2 is about work done at import.
- GT-i3 covers the TLS leg to an HTTPS proxy for `https://` targets, where the trusted CA set silently changes. Here the target is `http://`, and the result is a crash or verification being switched off, not a different CA set.
- GT-i4 is about a client certificate staying loaded in the shared context. The concurrency half of R1 has the same root (one context, rewritten per connection) but a different thing is written and a different protection is lost. A fix that only keeps client certificates out of the shared context leaves R1 in place.

There are no ruled claims for this pull request.

## Both sides

For calling it a bug:

- It is a regression with a reproduction at both commits and across five releases.
- The trigger is ordinary, supported use: a proxy setting and a plain URL, no custom code.
- On urllib3 2.x the request cannot be made at all and the error escapes the library's own exception types.
- On urllib3 1.26.x the consequence is silent and is the protection `verify=True` exists to give.
- The fault is visible in the diff: the shared context is attached without checking the URL scheme, while `cert_verify` a few lines away sets "do not verify" for non-`https` URLs.

Against:

- Plain HTTP through an HTTPS proxy is an uncommon setup. The upstream tracker has no report with exactly this trigger.
- No maintainer acknowledged it by name. Their statements are about the feature as a whole.
- The silent half needs urllib3 1.26.x, threads, and proxied plain-HTTP traffic at the same time.
- What the request did before the change (talk to the proxy without checking its certificate) was itself questionable.

## Recommendation

`eligible`, as a new bug. Confidence: high that it is real and introduced here; medium on how the owner will want R1 and R7a grouped.

Strongest argument against: the setup is rare and no maintainer ever named it, so a reviewer could be forgiven for not thinking of proxied plain-HTTP traffic. Against that, the people it hits are fully blocked (urllib3 2.x) or silently unprotected (urllib3 1.26.x).
