# B2: clearing a required controlled field from code now shows a "required" error at once

Pull request: mui/base-ui #5460, "[field] Sync controlled value changes with field state".
Candidates covered: NC-8e9888d25c28, NC-c6255eadbbd1, NC-27b29d1abde8, NC-b927058d8472.

The grouping is right. All four describe one problem in two settings (after a submit in the default mode, and in `onChange` mode).

## Problem

Take a required text field whose text the app holds (`<Field.Control required value={value} onValueChange={setValue} />`). The app sets the value back to `''` from code. The usual cases are clearing the form after a successful submit, and a Reset button.

After this change the emptied field is immediately marked invalid and shows the browser's "required" message. Before, the same reset left the field without an error.

## What changed

The change adds a block that runs whenever the `value` prop changes, including when code changes it:

```diff
+  useValueChanged(serializedValue, () => {
+    if (serializedValue === undefined) {
+      return;
+    }
+
+    clearErrors(name);
+    setDirty(serializedValue !== (validityData.initialValue ?? ''));
+    setFilled(serializedValue !== '');
+
+    validation.change(serializedValue);
+  });
```

Three existing facts turn that into the error:

1. `validation.change('')` runs a full validation when the field validates on change. That is the case in `onChange` mode, and in the default `onSubmit` mode once a submit was attempted. The form's "submit attempted" flag is never reset.
2. The validation code hides a lone "value missing" error only for a field that was never changed. Its comment reads: "Only make `valueMissing` mark the field invalid if it's been changed to reduce error noise." The flag it checks, `markedDirtyRef`, is only ever set to true. `setDirty(false)` does not clear it.
3. So after the reset the field reports "not dirty" and "invalid, value missing" at the same time.

Before the change nothing reacted to a value set from code, so no validation ran.

## Intended or announced

Validating code-driven changes is the stated aim. The description says: "**Programmatic changes left the field stale.** Setting the value from code, such as a clear button or a form library reset, updated the input text but not filled, dirty, or validity, so a resolved error stayed visible and a pending async validator for the old value could still publish." The new test "syncs state and validates when the controlled value changes programmatically" asserts the validator runs after a code-driven change.

The description does not say that a reset to empty on a required field will raise a new error. The documentation for the default mode says it "triggers validation when the form is submitted, and re-validates on change after submission."

Shipped in v1.8.0 on 2026-09-04. The release note is "Sync controlled value changes with field state (#5460)".

## What the affected person sees

Case 1, default mode, clear on submit. `<Form onFormSubmit={() => setValue('')}>` with the required controlled field. The person types "hello" and presses Send. The submit succeeds (`{ message: 'hello' }` is delivered) and the app clears the field.

- Before the change: empty field, no error, not marked invalid. (It still carried a stale "dirty" mark.)
- After the change: empty field, `aria-invalid="true"`, and the error text. In Chromium: "Please fill out this field." In jsdom: "Constraints not satisfied".

Case 2, `onChange` mode, Reset button. The person types "x", then presses Reset.

- Before: no error.
- After: the same "required" error, on a field that reports not dirty.

The affected person is the end user of any app that clears a required controlled field from code: chat boxes, add-item rows, contact forms. They see an error on a form they just submitted successfully. They are not stuck. Typing clears the error.

Three reference points from the same probe:

- If the person deletes the text by hand, the same error appears at both commits.
- In the default mode before any submit, a reset shows no error at both commits.
- The sibling control `NumberField` shows the same error after clear-on-submit, at both commits. So this change brings `Field.Control` in line with a sibling that already behaved this way.

## What the maintainers did

- No maintainer has addressed this path. The pull request had no human review.
- The follow-up #5563 (merged 2026-08-25, same author) is the closest statement. Its description says the blur handler now re-commits the settled value "unless it settled back to the initial value (a programmatic reset stays quiet)". Its code comment says: "A rewrite back to the initial value is a programmatic reset: the field looks pristine, so committing it would only surface `valueMissing` noise." That is about the blur path only. It shows the author regards a "required" error after a code-driven reset as noise to avoid there. It is not an acknowledgement of this problem.
- Upstream master on 2026-10-05 still shows the error in both cases (run).
- No later issue or pull request reports it.

Runs used the project's own test setup. Unless a line says Chromium, they ran in jsdom, the simulated browser that setup uses.

- Cases 1 and 2, the hand-clear reference, the no-submit reference, and the `NumberField` sibling, at base and head: **run** (`probes/B2/probe.test.tsx`, `result-base.txt`, `result-head.txt`).
- Chromium wording "Please fill out this field." and the same base/head difference in a real browser: **run** (`result-base-chromium.txt`, `result-head-chromium.txt`).
- Master still shows it: **run** (`result-master.txt`).
- The diff, the `markedDirtyRef` handling, the "error noise" comment, the never-reset submit flag: **read** (`FieldControl.tsx`, `FieldRoot.tsx`, `useFieldValidation.ts`, `Form.tsx` at head).
- The description, the new test, the mode documentation: **read**.
- #5563 text and comment: **read** (`upstream/pr-5563.json`, `upstream/pr-5563-files.json`).
- Behaviour with a real form library (React Hook Form, TanStack Form) calling its own reset: not run. The handbook pattern for those libraries passes `invalid` and `dirty` from the library and does not use the native `required` attribute, so this error would not arise in that pattern (read, not run).

## Relation to existing reference bugs and ruled claims

Not GT-r1. GT-r1 is about `onBlur` mode: a value rewritten during blur loses the blur verdict. This problem needs no blur and concerns a new error appearing, not a verdict being lost. GT-r1's wording does note that "a rewrite back to the initial value may stay quiet", which is the same idea the maintainer applied in #5563.

Not GT-r2 (filled state at mount). No ruled claims exist.

## Both sides

For calling it a bug:

- Reproduced at both commits, in jsdom and Chromium. Before: no error. After: an error.
- The trigger is one of the most common form patterns, and the description names "a clear button or a form library reset" as the cases it helps.
- The library's own rule is that a "required" error should not mark an unchanged field. After the reset the field reports itself as not dirty and still shows that error.
- The same author later called this kind of error "noise" and suppressed it on the blur path.

Against:

- Validating code-driven changes is exactly what the change was written to do, and a new test asserts it.
- The field is required and is empty. The verdict is true. The person gets the same message by deleting the text by hand.
- `NumberField` behaved this way before this change and still does. The description presents matching the siblings as the goal.
- The documented default mode says the field re-validates on change after a submit.
- Nobody is blocked, and the maintainers have left it in place through a release.

## Recommendation

`eligible`, with medium confidence. It is a visible false-alarm on a successful submit, introduced by this change, on a pattern the description itself advertises, and it contradicts the library's own "no required error on an unchanged field" rule.

Strongest argument against this recommendation: this is the designed behaviour, not an accident. The change exists to make validity follow code-driven changes, the sibling control already did the same, and the error is factually correct for an empty required field. On that reading it is a design preference about when to show a true error, which is `advisory`.
