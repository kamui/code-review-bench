# B8: with `Combobox.Input` rendered as the field-aware `Input`, the label text is validated as well as the selected item

Pull request: mui/base-ui #5460, "[field] Sync controlled value changes with field state".
Candidates covered: NC-46b0f131ef8d.

The grouping is right. This is its own problem.

## Problem

A `Combobox` inside a `Field.Root` validates the selected item. Its text box can be rendered through the field-aware `Input` (`<Combobox.Input render={<Input />} />`). `Input` is `Field.Control`, so the same field now has two controls reporting to it: the combobox with the selected item, and the input with the text shown in the box.

The claim is that after this change, when the selection changes from code, the input's new sync also validates the label text (for example `"France"`), on top of the combobox validating the item (`{ label: 'France', value: 'fr' }`). A validator written for the item then gets a string and can give the wrong verdict.

## What changed

`Combobox.Input` passes the text as `value` to the element it renders. With `Input` as that element, this pull request's new block sees a controlled value change and validates it:

```diff
+  useValueChanged(serializedValue, () => {
 ...
+    clearErrors(name);
+    setDirty(serializedValue !== (validityData.initialValue ?? ''));
+    setFilled(serializedValue !== '');
+
+    validation.change(serializedValue);
+  });
```

Before, `Field.Control` only validated on its own change event, that is, when the person typed. A selection made from code changed the text without a change event, so the input did not validate.

The underlying conflict is older. Both controls register with the same field, and the one that registered last supplies the value used at submit.

## Intended or announced

Not mentioned. The description lists Combobox among the siblings that already sync through `useValueChanged`, and does not discuss `Field.Control` nested inside one.

The composition is exercised by the repository's own tests, in `ComboboxRoot.test.tsx`: "submits when input renders a field-aware input" and two neighbours use `<Combobox.Input render={<Input data-testid="input" />} />`. Those tests use plain string items and no custom validator. `Autocomplete` has the same kind of tests. No documentation page shows it.

Shipped in v1.8.0 on 2026-09-04.

## What the affected person sees

Probe: a controlled `Combobox` of country objects in a `Form`, with a validator that accepts only an object and otherwise returns "Pick a country from the list".

The app selects France from code, `onChange` mode, then the person presses Send:

- Before the change: after the selection the validator has been called once, with the object. The field is valid. On Send the validator is called with the string `"France"`, the error appears, and **the submit is blocked**.
- After the change: after the selection the validator has been called with the object and then with `"France"`. The error appears at once. On Send it is called with `"France"` again and the submit is blocked.

So the end result is the same at both commits: the form cannot be submitted. The change makes the error appear at the moment of selection instead of at Send.

The person picks France with the mouse, then presses Send:

- Before: validator gets the object. Valid. Submits.
- After: validator gets `"France"` first and then the object. Valid. Submits.

The person types "Fr": the validator gets `"Fr"` and the error shows, at both commits.

With a plain `<Combobox.Input />` none of this happens: object only, valid, submits, at both commits.

The person affected is an app developer who combines the field-aware `Input`, non-string items and a custom validator. Their end users are blocked after a code-driven selection, before the change and after it.

## Both sides

For calling it a bug of this change:

- The extra validator call with the label text on a code-driven selection is new (run: one call before, two after).
- In `onChange` mode the field now shows an error right after the app selects a valid item, where before it showed valid until Send.
- The composition is covered by the repository's tests, so it is a supported one.

Against:

- The harmful outcome, a blocked submit after a code-driven selection, is already there before the change (run). Two controls on one field disagreeing about the value is the older defect.
- On the mouse path the item is validated last and the outcome is unchanged.
- The input already validated typed text before the change.
- It needs object items plus a validator that rejects strings, which no repository test combines.

## Recommendation

`pre-existing`, with medium confidence. The observation is true, but the failing behaviour for a user (wrong verdict, blocked submit) exists before the change. The change adds one more wrongly-typed call and moves the error earlier in one path.

Strongest argument against this recommendation: "worsened" also counts. Before, the field looked valid after a code-driven selection; now it shows an error immediately. If the owner counts that earlier false error as a worsening introduced here, the label would be `advisory` or, at most, a low-impact `eligible`.
