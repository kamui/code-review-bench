# B9: when a controlled value becomes `null`, the field state stops following it

Pull request: mui/base-ui #5460, "[field] Sync controlled value changes with field state".
Candidates covered: NC-9b4d7c70af52.

The candidate holds two variants. They are kept in one dossier because they share one cause, but they have different answers:

- (a) The person empties the field and the app stores `null` for "empty". This worked before and does not after.
- (b) Code resets the value to `null`. This did not work before either, and its premise is partly false.

## Problem

Some apps and form libraries store `null` for an empty text field, for example `onValueChange={(v) => setValue(v || null)}`.

After this change, a `Field.Control` whose `value` prop is `null` has no path that updates its state. It counts as controlled, so the change handler leaves early. Its text form is "no value", so the block that follows the prop leaves early too. Dirty, filled, server errors and validity all stay as they were.

## What changed

```diff
   const isControlled = valueProp !== undefined;
   const value = isControlled ? valueUnwrapped : undefined;
+  // The DOM value is always a string, so dirty comparisons must serialize the controlled value.
+  const serializedValue = value == null ? undefined : String(value);
 ...
+  useValueChanged(serializedValue, () => {
+    if (serializedValue === undefined) {
+      return;
+    }
 ...
+          if (isControlled) {
+            return;
+          }
```

`null` is "controlled" by the first line and "undefined" by the new second line. Both new early exits apply.

Before the change, the change handler always updated field state from the text the person typed, whatever the app then stored.

## Intended or announced

Not mentioned. `null` is outside the declared type of the prop: `value` is `React.ComponentProps<'input'>['value']`, which is `string | number | readonly string[] | undefined`. The probe had to cast to pass it.

React itself rejects it. On `value={null}` it prints: "`value` prop on `input` should not be null. Consider using an empty string to clear the component or `undefined` for uncontrolled components." It then treats the input as uncontrolled and prints the controlled/uncontrolled switch warnings.

An earlier pull request, #5290 "Fix `data-dirty` tracking for null-valued controls", is about `NumberField` and `Select`, whose empty value is `null` by design. It does not make `null` a supported value for `Field.Control`.

Shipped in v1.8.0 on 2026-09-04.

## What the affected person sees

Variant (a). Required controlled field holding "abc", in a `Form` with a server error, `validationMode="onChange"`. The person deletes the text; the app stores `null`.

- Before the change: validator called with `""`. Server error cleared. The "required" error is shown. Field marked not filled.
- After the change: validator not called. "Server error" stays. Field still marked filled although empty. No "required" error.
- When the person types again, everything catches up at both commits.

With an empty string instead of `null`, the field behaves correctly at both commits.

Variant (b). Code sets the value from "abc" to `null`.

- At both commits: nothing changes. The old "Too short" error stays, dirty and filled stay.
- At both commits the input still shows "abc". React does not clear an input when its value becomes `null`. So the description "the input is cleared but the state is stale" does not hold: the input is not cleared.

The person affected in (a) is the end user of an app that stores `null`. Their emptied field keeps a stale server error and a wrong "filled" mark until they type again, and the "required" error that used to appear on emptying does not appear. They are not blocked from anything they could do before.

## What the maintainers did

- No maintainer has mentioned `null` values for `Field.Control`. No human review on the pull request.
- The follow-up #5563 changed how "filled" is computed. As a side effect, at upstream master on 2026-10-05 the field is correctly marked not filled in variant (a). The validator is still not called and the server error still stays (run).
- No later issue or pull request reports it.

## Relation to existing reference bugs and ruled claims

Not GT-r1. Related to GT-r2 but not the same: GT-r2 is the filled mark being wrong at mount for a controlled value. Here the filled mark is wrong after a change to `null`. The same upstream fix (#5563) corrects both filled symptoms. The remaining parts of this problem (no validation, server error kept, dirty not updated) are not covered by GT-r2. No ruled claims exist.

## Both sides

For calling it a bug:

- Variant (a) is a real regression, reproduced: it worked before and does not after.
- Storing `null` for an empty field is common in form libraries, and JavaScript apps get no type error.
- The component treats `null` as controlled in one line and as absent in the next. That is an inconsistency inside the change.

Against:

- `null` is not an allowed value for this prop by its type, and React warns about it and treats the input as uncontrolled.
- Variant (b) is unchanged from before, and its "input is cleared" premise is false.
- The consequence in (a) is stale state until the next keystroke. Nobody is blocked.
- The maintainers fixed the filled part in passing and left the rest.

## Recommendation

`advisory`, with medium confidence. Variant (a) is a true regression, but only for an input the prop's type forbids and React warns about. Variant (b) is not a change at all.

Strongest argument against this recommendation: the code used to tolerate `null` and now silently stops updating the field for it, in a pull request whose purpose is to remove stale field state. An app that stored `null` worked before the upgrade and shows stale errors after it.
