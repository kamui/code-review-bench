# B4: the validator gets the text of the `value` prop, not the text the input actually holds

Pull request: mui/base-ui #5460, "[field] Sync controlled value changes with field state".
Candidates covered: NC-f98f0d0ed5b4.

The grouping is right. B3 has the same root (the text form of the `value` prop becomes the field's value) but is about number-versus-text at submit. This one is about the prop text differing from what the browser keeps.

## Problem

Browsers clean up some values when they are put into an input. A text input drops line breaks. A range input clamps to its minimum and maximum. A date or number input turns an invalid value into empty text.

After this change a controlled `Field.Control` validates `String(value prop)`. If the app passes a value the browser rewrites, the validator sees the app's version while the input, and the form values passed to the same validator, hold the browser's version.

## What changed

```diff
+  const serializedValue = value == null ? undefined : String(value);
 ...
+  useValueChanged(serializedValue, () => {
 ...
+    setFilled(serializedValue !== '');
+
+    validation.change(serializedValue);
+  });
```

and, for controlled fields, the change handler no longer validates the text read from the input:

```diff
+          if (isControlled) {
+            return;
+          }
 ...
             validation.change(inputValue);
```

Before, validation on an edit used `event.currentTarget.value`, the text the input held. A value set from code was not validated at all. After, both use the prop's text.

## Intended or announced

The description announces that the field registers "the serialized value" and that `useValueChanged` owns the controlled path, like the sibling controls. It does not discuss values the browser rewrites. Nothing in the documentation says which representation the validator receives; it is typed `unknown`.

Shipped in v1.8.0 on 2026-09-04.

## What the affected person sees

All cases use a controlled field in a `Form` with `validationMode="onChange"`. Results are the same in jsdom and in real Chromium.

- Text input, code sets `"a\n"`. The input holds `"a"`. After the change the validator is called with `"a\n"` while the form value for the same field is `"a"`. Before, the validator was not called.
- Text input, code sets `"\n"`. The input is empty. After the change the validator gets `"\n"`, and the field is marked filled and dirty. Before, the validator was not called; the field was already marked filled (so that part is older).
- The person types "a" and the app rewrites it to `"a\n"`. Before: validator gets `"a"`. After: validator gets `"a\n"`. The input holds `"a"` both times.
- Range input 0 to 100, code sets `"200"`. The input holds `"100"`. After the change the validator gets `"200"` with form value `"100"`. Before, not called.

The person affected is an app developer whose stored value differs from what the input can hold. Their validator may approve or reject a value that is not the one on screen or in the form values. No end user is blocked by this alone. The app controls the value and can pass a clean one.

## What the maintainers did

- No maintainer has mentioned this. No human review on the pull request.
- Upstream master on 2026-10-05 behaves the same (run).
- No later issue or pull request reports it.

## How each fact is known

Runs used the project's own test setup. Unless a line says Chromium, they ran in jsdom, the simulated browser that setup uses.

- All four cases and a plain reference case, at base and head, in jsdom: **run** (`probes/B4/probe.test.tsx`, `result-base.txt`, `result-head.txt`).
- The same in real Chromium: **run** (`result-base-chromium.txt`, `result-head-chromium.txt`). Firefox and WebKit were not run.
- Master: **run** (`result-master.txt`).
- The diff and that form values come from the input's own value: **read** (pinned diff; `useFieldControlRegistration.ts` at head).
- That real apps pass values the browser rewrites to a `Field.Control`: not established by anyone.

## Relation to existing reference bugs and ruled claims

Not GT-r1 and not GT-r2. GT-r2 is about the filled mark at mount; the "filled although empty" detail here needs a line-break-only value and was already present before the change. No ruled claims exist. Same root as B3.

## Both sides

For calling it a bug:

- The validator and the form values handed to it in the same call disagree about the same field (run).
- For an edit the app rewrites, the validator used to see what the input held and now sees something else.

Against:

- The trigger is an app passing a value its own input type cannot hold. That is an inconsistency in the app.
- For code-driven changes there is no earlier behaviour to regress from: they were not validated before.
- The value validated is the one the app holds in state and will most likely send itself.
- No user-facing failure was shown, only a mismatch a developer could observe.

## Recommendation

`advisory`. The mismatch is real and reproduced, but it needs unusual input from the app and produces no shown failure for an end user. It is a hardening point about which representation is canonical.

Strongest argument against this recommendation: a validator can pass a value that the form then submits in a different form (for example approve `"200"` while `"100"` is submitted), and for app-rewritten edits this is a change from what the validator used to receive.
