# B6: in an uncontrolled field, `details.cancel()` stops validation but dirty and filled still update

Pull request: mui/base-ui #5460, "[field] Sync controlled value changes with field state".
Candidates covered: NC-c19fd02de9f7, NC-7b21d34c5bfe.

The grouping is right. It is the uncontrolled half of the same shortfall as B1b (see "Relation" below).

## Problem

`Field.Control` calls the app's `onValueChange(value, details)` on each edit. `details.cancel()` is documented as "Cancels Base UI from handling the event." The pull request says: "`details.cancel()` in `onValueChange` now stops the internal handling. It was ignored."

For an uncontrolled field (no `value` prop), `cancel()` now stops two of the four things the field does on an edit: clearing the server error, and validating. The other two still happen: the field is marked dirty and filled.

## What changed

```diff
-          onValueChange?.(inputValue, createChangeEventDetails(REASONS.none, event.nativeEvent));
+          const details = createChangeEventDetails(REASONS.none, event.nativeEvent);
+          onValueChange?.(inputValue, details);
 ...
           // `validation.change` reads `markedDirtyRef`, so update dirty before validating.
           setDirty(inputValue !== (validityData.initialValue ?? ''));
           setFilled(inputValue !== '');
 
           // Workaround for https://github.com/react/react/issues/9023
-          if (!event.nativeEvent.defaultPrevented) {
+          if (!event.nativeEvent.defaultPrevented && !details.isCanceled) {
             clearErrors(name);
             validation.change(inputValue);
           }
```

The new `isCanceled` check is placed below the dirty and filled updates, so it only gates the last two calls. Before the change `isCanceled` was not read at all, so all four ran.

## Intended or announced

Announced as a fix: "`details.cancel()` in `onValueChange` now stops the internal handling. It was ignored." The new test is named "does not validate when the change is canceled" and checks only that the validator is not called. So the test matches the narrower behaviour, and the description's wording is broader than the code.

Shipped in v1.8.0 on 2026-09-04. The release note does not mention `cancel()`.

## What the affected person sees

Probe: an uncontrolled field in a `Form` with a server error, `validationMode="onChange"`, and `onValueChange={(value, details) => details.cancel()}`. The person types "a".

- Before the change: the input shows "a". Validator called with `"a"`. Server error cleared. Field dirty and filled. (`cancel()` did nothing.)
- After the change: the input shows "a". Validator not called. Server error stays. Field dirty and filled.

After the change the field's marks describe the new text ("dirty", "filled") while its validity still describes the old text. With a validator that would reject the new text, no error is shown.

The app asked for this by calling `cancel()`. For a native uncontrolled input the typed text cannot be taken back, so the input really does hold "a", and "dirty" and "filled" are true statements about it. Nobody is stuck.

For comparison, in the sibling `NumberField`, `cancel()` means the value is not committed, so nothing changes at all.

## Relation to existing reference bugs and ruled claims

Not GT-r1 and not GT-r2. No ruled claims exist.

B6 and B1b are two halves of one shortfall: the new promise about `cancel()` is kept only in part. B1b is the controlled half (cancel is not consulted when the app stores the value). The same reasoning decides both.

## Both sides

For calling it a bug:

- The description says cancel "stops the internal handling". Two of four internal updates still run.
- The result is a mixed state: marks for the new text, validity for the old.
- Marking the field dirty is permanent for the "has been changed" flag used by required-field validation.

Against:

- Nothing regressed. Before, `cancel()` stopped nothing. Now it stops validation and error clearing.
- The input does hold the new text. Reporting it as dirty and filled is accurate; hiding that would make the marks wrong.
- The added test states the intended scope: validation.
- No failure for an end user was shown.

## Recommendation

`advisory`. The observation is correct: the fix is narrower than its description. It is a question of what `cancel()` should mean for an input whose text cannot be reverted, with no regression and no failing behaviour.

Strongest argument against this recommendation: a pull request that introduces a behaviour and describes it in its own words can be held to those words. "Stops the internal handling" is not what the code does, and the new test does not check dirty or filled, so the gap is unguarded.
