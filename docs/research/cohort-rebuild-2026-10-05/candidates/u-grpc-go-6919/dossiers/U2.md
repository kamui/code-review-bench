# U2: an old-generator status detail does not come back from `Details` as itself

Pull request: grpc/grpc-go #6919, "deps: move from github.com/golang/protobuf to google.golang.org/protobuf/proto".
Base `5051eeae`, head `b8374114`. Candidate covered: NC-9c446e190eb4.

## Problem

A gRPC error can carry extra messages called details. A server attaches them with `Status.WithDetails`. A caller reads them back with `Status.Details`.

Some programs still use message code produced by the old protobuf generator (before 2020). This dossier calls those old-generator messages. The packet calls them "V1-only".

The problem as raised has two parts:

1. **Outcome.** After this change, `WithDetails` still accepts an old-generator message, but the caller cannot get that message back from `Details`.
2. **Stated cause.** `Details` now returns an error in place of the message, because the new decoding call looks the type up in the new library's registry, and an old-generator message is registered only in the old one.

The run shows part 1 is true and part 2 is false.

- `Details` returns no error. The type lookup succeeds.
- What it returns is an internal wrapper object from the protobuf library (`*impl.messageIfaceWrapper`) instead of the original message type. The caller's usual code, which checks for the original type, no longer finds it.

That is exactly existing reference bug GT-u3, "Details returns a wrapper instead of the original legacy detail type". So this is not a new problem. It is GT-u3 described from the caller's side, with a wrong explanation attached.

The grouping holds one problem. It does not need splitting.

## What changed

`internal/status/status.go`, in `Details`:

```diff
 	for _, any := range s.s.Details {
-		detail := &ptypes.DynamicAny{}
-		if err := ptypes.UnmarshalAny(any, detail); err != nil {
+		detail, err := any.UnmarshalNew()
+		if err != nil {
 			details = append(details, err)
 			continue
 		}
-		details = append(details, detail.Message)
+		details = append(details, detail)
 	}
```

Both the old call and the new call find the message type in the same place: the new library's global registry.

- Old path (github.com/golang/protobuf v1.5.3, `ptypes/any.go`, `Empty`): `mt, err := protoregistry.GlobalTypes.FindMessageByName(name)` and then `return proto.MessageV1(mt.New().Interface()), nil`.
- New path (google.golang.org/protobuf v1.32.0, `anypb.UnmarshalNew`): `mt, err := r.FindMessageByURL(src.GetTypeUrl())` on `protoregistry.GlobalTypes`, and then `dst = mt.New().Interface()`.

The only difference is the last step. The old path converted the result back to the old-style form (`proto.MessageV1(...)`), which hands back the original message object. The new path returns the result as the new library sees it. For an old-generator message, that is a wrapper around the original.

The stated cause does not hold because an old-generator message is not registered "only in the old registry". The old library's registration function puts it straight into the new registry (github.com/golang/protobuf v1.5.3, `proto/registry.go`):

```go
func RegisterType(m Message, s messageName) {
	mt := protoimpl.X.LegacyMessageTypeOf(m, protoreflect.FullName(s))
	if err := protoregistry.GlobalTypes.RegisterMessage(mt); err != nil {
```

Both commits require that library version (`go.mod`: `github.com/golang/protobuf v1.5.3`).

## Intended or announced

- The pull request description says only: "Use google.golang.org/protobuf/proto instead of github.com/golang/protobuf."
- No documentation change mentions what `Details` returns.
- Before merging, a maintainer raised a neighbouring concern about the input side: `WithDetails` must keep accepting old-style messages, "This would impact anyone using proto messages generated by some other tool ... Or possibly(?) using a message generated by an old `protoc-gen-go`." The author changed the `WithDetails` signature for that. Nobody discussed what `Details` hands back.
- The v1.62.0 release notes (the release it shipped in, 2024-02-21) say nothing about `Details`.
- It was not intended. The maintainers later called it a regression (see below).

## What the affected person sees

From the probe, using the repository's own old-generator message `SearchRequestV3`.

**Before the change.** `WithDetails` succeeds. `Details` returns a `*SearchRequestV3`. A type switch on `*SearchRequestV3` matches and reads `Query="hello"`.

**After the change.** `WithDetails` succeeds. `Details` returns one item:

- It is not an error.
- Its Go type is `*impl.messageIfaceWrapper`, a type inside the protobuf library that callers cannot name.
- A type switch on `*SearchRequestV3` does not match. The detail is skipped without any message.
- A direct conversion (`d.(*SearchRequestV3)`) crashes with
  `interface conversion: interface {} is *impl.messageIfaceWrapper, not *grpc_testing_not_regenerate.SearchRequestV3`.
- It no longer has the old-style methods either, so a check for "any old-style protobuf message" also fails.

The same happens after the status is rebuilt from its wire form, which is what a client receiving the error does.

Who is affected: programs that attach or receive error details whose message code came from the old generator. How stuck: the data is not lost. A caller who knows about the wrapper can convert it back (`protoadapt.MessageV1Of`; the probe shows this returns the original `*SearchRequestV3` with `Query="hello"`), or regenerate the message code. But nothing tells the caller that. The typical symptom is error details silently disappearing from error handling, or a crash.

**The case the stated cause describes, an error from `Details`.** This does happen for an old-style message that no registry knows at all. The probe defines one by hand. `WithDetails` accepts it, and `Details` returns the error `proto: not found`. But it does so at base and at head alike. The change did not introduce or worsen it.

**Current-generator messages** round-trip correctly at both commits.

## What the maintainers did

- **First follow-up fix, #6965 (merged 2024-02-05, in v1.62.0).** A maintainer wrote: "in #6919 we broke backwards compatibility of able to handle v1 proto messages. This change fixes that." This is the statement that the change broke backwards compatibility. Its diff touches only `encoding/proto/proto.go`, the codec. It does not touch `Details`. The run at v1.62.0 confirms it: the codec accepts the old-generator message again, and `Details` still returns the wrapper. So this fix covers reference bug GT-u2, not this problem.
- **A user reported it, issue #7679 (2024-09-29),** "status/Details: unexpected code breaks after upgrading to v1.62.0 and higher". The report describes the wrapper: "The actual type of "dt" for now is "google.golang.org/protobuf/internal/impl/*messagelfaceWrapper"". It does not describe an error from `Details`. A second user later wrote "we are facing the same issue in our organization".
- **A maintainer reproduced and acknowledged it,** naming this pull request: "The change (https://github.com/grpc/grpc-go/pull/6919) seems to be backward incompatible when using old generated protobuf code." At first the team declined to act: "Since we've not gotten other reports about this issue since 1.62.0 was released 6 months ago, we don't want to make a change now."
- **Then they fixed it, #7724 (merged 2024-10-22),** "status: Fix status incompatibility introduced by #6919". The fix converts each detail back with `protoadapt.MessageV1Of` before returning it. It shipped in v1.68.0 (2024-11-07) under "Bug Fixes": "status: Fix regression caused by #6919 in status.Details() causing it to return a wrapped type when getting proto messages generated with protoc-gen-go < v1. (#7724)".
- **The fix works.** The run at v1.68.0 and at v1.84.0 returns `*SearchRequestV3` again.
- **Releases affected:** v1.62.0 up to, but not including, v1.68.0. That is about eight and a half months. Only v1.62.0 was run from that range. The v1.67.1 source was read and still lacks the conversion.

None of these upstream records mentions a decode error or a registry lookup failure. Every one of them describes the wrapper.

## Relation to existing reference bugs and ruled claims

**This is a manifestation of GT-u3, not a new bug.** GT-u3's trigger is "A registered V1-only protobuf message is attached to a non-OK status, decoded, and type-asserted by the caller". Its mechanism is "Existing type switches fail and unchecked type assertions panic after successful detail serialization". The run at head shows exactly that for this problem's trigger: lines 2, 3 and 4 of `probes/U2/result-head.txt`. The already-ruled claim CL-u-legacy-details (eligible, GT-u3) describes the same call and the same cause.

Two points the owner may need when deciding how to treat wording that describes it this way:

- The trigger named (an old-generator detail passed through `WithDetails` and read with `Details`) and the changed line named (`any.UnmarshalNew`) are the right ones.
- The symptom named (an error returned from `Details`) and the cause named (the type cannot be found in the new registry) are both wrong. The run shows no error and a successful lookup. Someone who tested for an error would find none.

It is not GT-u2. GT-u2 is the codec refusing old-generator messages in ordinary requests and replies. The run at v1.62.0 separates the two: GT-u2 is fixed there and this is not.

It is unrelated to GT-u1, GT-u4, GT-u5.

## Both sides

**For treating it as the same bug as GT-u3.**
- Same trigger, same changed line, same user-visible loss: the caller attached a message and cannot get it back as that message.
- The maintainers acknowledged that loss as a regression from this pull request and fixed it.
- The one-line outcome, "accepted by `WithDetails` but cannot be recovered through `Details`", is true for every caller who has not learned about the wrapper.

**For treating the claim as wrong.**
- The specific behaviour it predicts does not happen. `Details` returns no error.
- The specific cause it gives is false. Old-generator messages are in the new registry, and the old code path used the same registry.
- The only case where `Details` does return an error (a message no registry knows) behaves the same before and after the change.
- "Cannot recover" overstates it: the data is intact inside the wrapper and one library call returns the original.

**Is there a separate new bug hiding here?** No. Every behaviour difference the probe found between base and head on this path is the wrapper.

## Recommendation

**duplicate of GT-u3** (ruled claim CL-u-legacy-details). Confidence: high on the facts.

The problem, an old-generator detail that does not come back from `Details` in a form the caller can use, is real, introduced by this change, and already recorded as GT-u3. No new reference bug is needed.

**Strongest argument against this recommendation.** Taken as a factual claim, what was raised is refuted: it says `Details` returns an error because the type cannot be resolved, and the run shows no error and a successful resolution. It never mentions the returned type, which is the whole of GT-u3. On that reading the right label is `refuted`, with nothing matched to GT-u3. Which reading applies to a given piece of wording is a grading question this dossier does not settle; the facts above are the same either way.
