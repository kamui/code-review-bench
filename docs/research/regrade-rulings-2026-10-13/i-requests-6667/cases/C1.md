# Case C1: one comment and the known problem GT-i8

Pull request: psf/requests #6667, "Avoid reloading root certificates to improve concurrent performance". "Base" is the commit before the change, `8dd3b26b`. "Head" is the reviewed commit, `4089f3dc`. Every fact below comes from the code at those two commits, from the urllib3 source, and from runs. Each is marked *run* (executed for this case, output saved under `probes/C1/`), *read* (visible in the source or the answer key) or *reported*.

The question: does the comment below, read by its own words, say what goes wrong for the known problem GT-i8, and does it identify GT-i8's cause as a fault?

Words used here. Requests sends HTTPS through urllib3. An *adapter* (`HTTPAdapter`) owns the urllib3 *pool manager* that makes the connections. A program can subclass the adapter and override `init_poolmanager` to pass its own TLS settings to the pool manager. Two kinds of setting matter here. One is a ready-made *context* (`ssl_context`), an object that holds the whole TLS policy: allowed versions, ciphers and trusted certificate authorities. The other is a *version setting* (`ssl_version`, `ssl_minimum_version`, `ssl_maximum_version`), from which urllib3 builds a context itself. `verify=True` is the default of a request and means the server's certificate is checked. The *shared context* is the one context this change builds when requests is imported, `_preloaded_ssl_context`.

## The known problem

GT-i8, in the answer key's words: "TLS version settings an adapter passes through init_poolmanager (ssl_version, ssl_minimum_version, ssl_maximum_version) are not applied to verify=True requests".

- **What was owed** (read, answer key): "TLS version settings that an HTTPAdapter subclass passes to its pool manager through init_poolmanager must bound the versions its connections negotiate for verify=True requests, as they did at the merge-base and as they still do for verify=False and verify=<path>."
- **Trigger** (read, answer key, in part): "Subclass HTTPAdapter, pass ssl_minimum_version, ssl_maximum_version or ssl_version to the pool manager in init_poolmanager (the pattern of 'Example: Specific SSL Version' in docs/user/advanced.rst), mount it, and send a request with the default verify=True to a server that offers a version outside the adapter's range. No adapter-supplied ssl_context is involved."
- **What goes wrong** (read, answer key): "the adapter requiring TLS 1.3 is refused by the TLS-1.2-only server at the merge-base (TLSV1_ALERT_PROTOCOL_VERSION) and returns 200 over TLSv1.2 at head; the capped adapter and the documented-shape adapter negotiate TLSv1.2 at the merge-base and TLSv1.3 at head; with verify=<file> or verify=False the settings are honoured at both commits."
- **How it happens** (read, answer key): "At head _urllib3_request_context() in src/requests/adapters.py puts ssl_context=_preloaded_ssl_context into pool_kwargs whenever verify is True. urllib3 passes ssl_version, ssl_minimum_version and ssl_maximum_version to create_urllib3_context() only when it has no context and must build one; given a context it uses it unchanged, so the pool's version settings are never read."
- **The recorded cause** (read, answer key): "One fault: supplying a ready-made context makes urllib3 skip the version keywords on the pool."

The pull request has a second known problem at the same line, GT-i1: "A shared process-wide SSLContext is forced into every verified connection pool and silently discards adapter-level ssl_context customization". Its trigger is an adapter that passes its own `ssl_context`. The answer key says how GT-i8 differs from it (read): "It differs from GT-i1, where the adapter supplies its own SSLContext object and the per-request ssl_context beats it in urllib3's pool-kwargs merge: here the adapter supplies no context, its version keywords survive the merge, and they are ignored because urllib3 reads them only when it builds a context."

## The comment

The comment has text in three fields. Each is given whole.

- **File and lines:** `src/requests/adapters.py`, line 95 to line 95.
- **Kind:** finding.
- **Claim:**

  > Shared ssl_context overrides an adapter's own ssl_context for every verify=True request

- **Consequence:**

  > Callers who mount an HTTPAdapter whose init_poolmanager passes their own ssl_context (to pin minimum TLS version, restrict ciphers, trust a private CA, or enable pinning-related settings) get that context silently discarded for every default verify=True request. urllib3's _merge_pool_kwargs lets the per-request pool_kwargs override the manager's connection_pool_kw, so the module-level certifi context wins. Result: weaker protocol/cipher policy than the caller configured and a different trust anchor set, with no error. Demonstrated: with a custom context minimum_version=TLSv1_3, base uses the custom context (772), head uses the shared default (771, TLSv1_2).

- **Proposed fix:**

  > Inject the preloaded context only when the adapter has not configured its own: skip pool_kwargs['ssl_context'] when the target manager's connection_pool_kw (self.poolmanager, and the proxy manager when proxied) already carries 'ssl_context' (and keep the old ca_certs path in that case; ssl_version/ssl_minimum_version are ignored by urllib3 once any ssl_context is supplied, so cover them too). _urllib3_request_context is module-level with no adapter access, so pass the manager's connection_pool_kw or a flag into it, or do the injection in HTTPAdapter._get_connection. Add a test with an HTTPAdapter subclass that sets ssl_context in init_poolmanager and verify=True.

Where the words about version settings are. The names `ssl_version` and `ssl_minimum_version` appear once in the comment, in the proposed-fix field, inside the parenthesis of its first sentence: "ssl_version/ssl_minimum_version are ignored by urllib3 once any ssl_context is supplied, so cover them too". The claim field and the consequence field do not name a version setting. The comment does not name `ssl_maximum_version`.

## The code at the head

`src/requests/adapters.py`, function `_urllib3_request_context`, lines 91 to 95 at the head (read):

```diff
     cert_reqs = "CERT_REQUIRED"
     if verify is False:
         cert_reqs = "CERT_NONE"
-    if isinstance(verify, str):
-        pool_kwargs["ca_certs"] = verify
+    elif verify is True:
+        pool_kwargs["ssl_context"] = _preloaded_ssl_context
```

`HTTPAdapter._get_connection` passes that dictionary to the adapter's pool manager for each request, `self.poolmanager.connection_from_host(**host_params, pool_kwargs=pool_kwargs)` (read). `_urllib3_request_context` is a module-level function that receives the request, `verify` and the client certificate, and no adapter (read).

urllib3 (read, versions 2.2.1 and 2.8.0, the same lines in both):

- `PoolManager._merge_pool_kwargs` copies the manager's own settings and then writes each per-request setting over them: `base_pool_kwargs[key] = value`.
- When a connection starts TLS, urllib3 chooses the context this way:

  ```python
      if ssl_context is None:
          default_ssl_context = True
          context = create_urllib3_context(
              ssl_version=resolve_ssl_version(ssl_version),
              ssl_minimum_version=ssl_minimum_version,
              ssl_maximum_version=ssl_maximum_version,
              cert_reqs=resolve_cert_reqs(cert_reqs),
          )
      else:
          context = ssl_context
  ```

The documentation at the head, `docs/user/advanced.rst`, has an example headed "Example: Specific SSL Version" whose adapter overrides `init_poolmanager` and passes `ssl_version` to the pool manager (read). The pull request does not change the documentation (read).

## Each statement of the comment against the code

Claim field:

1. "Shared ssl_context overrides an adapter's own ssl_context for every verify=True request". True (run, part B: at the head the connection uses the shared context in all three cases; read, line 95 runs whenever `verify is True`).

Consequence field:

2. "Callers who mount an HTTPAdapter whose init_poolmanager passes their own ssl_context (to pin minimum TLS version, restrict ciphers, trust a private CA, or enable pinning-related settings) get that context silently discarded for every default verify=True request." True that the context is not used (run, part B). "Silently" holds for the version limit and the cipher limit, where the request succeeds. It does not hold for the private CA, where the request fails with an error. Pinning settings were not run.
3. "urllib3's _merge_pool_kwargs lets the per-request pool_kwargs override the manager's connection_pool_kw, so the module-level certifi context wins." True (read, `_merge_pool_kwargs`; run, part B).
4. "Result: weaker protocol/cipher policy than the caller configured and a different trust anchor set, with no error." True for the protocol and the cipher (run, part B rows 1 and 3). The trust set is different (run, row 2), and in that run the caller does get an error.
5. "Demonstrated: with a custom context minimum_version=TLSv1_3, base uses the custom context (772), head uses the shared default (771, TLSv1_2)." The comment's own run is reported. The same was run here with the same numbers (part B row 1).

Proposed-fix field:

6. "Inject the preloaded context only when the adapter has not configured its own: skip pool_kwargs['ssl_context'] when the target manager's connection_pool_kw (self.poolmanager, and the proxy manager when proxied) already carries 'ssl_context'". A request for a fix. Not run.
7. "(and keep the old ca_certs path in that case; ssl_version/ssl_minimum_version are ignored by urllib3 once any ssl_context is supplied, so cover them too)". The statement "ssl_version/ssl_minimum_version are ignored by urllib3 once any ssl_context is supplied" is true (read, the urllib3 lines above; run, part C rows 2 and 4). At the head requests supplies a context on every `verify=True` request, and an adapter's `ssl_minimum_version` or `ssl_version` then has no effect on the connection (run, part A rows 1 and 2). At the base requests supplied none and both settings took effect (run). "so cover them too" and "keep the old ca_certs path in that case" are requests about the fix.
8. "_urllib3_request_context is module-level with no adapter access, so pass the manager's connection_pool_kw or a flag into it, or do the injection in HTTPAdapter._get_connection." The first half is true (read). The rest is a request for a fix.
9. "Add a test with an HTTPAdapter subclass that sets ssl_context in init_poolmanager and verify=True." Advice on a test, for an adapter that passes its own context.

## Known only later

The answer key's text on how GT-i8 differs from GT-i1 continues: "GT-i1's obligation is met by any design that preserves the adapter's context; releases 2.32.3 and 2.32.4 do that (the shared context is skipped when the pool manager holds an ssl_context) and still ignore version keywords (run)." The statement about those releases is reported here: an earlier preparation ran them, and they are later than the reviewed commit.
