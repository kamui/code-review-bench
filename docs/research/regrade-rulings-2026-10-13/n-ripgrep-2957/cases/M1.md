The cut-off for this case is the last push to the pull request: **2024-12-31T13:09:16Z**. Everything above the last heading was knowable at that moment. The last heading lists what became known only later.

Each fact is marked *run* (executed on 2026-10-13, probe and output saved), *read* (visible in the diff, the source or a fetched record) or *reported* (someone's claim, not checked).

## What the candidate says

A person keeps a small file named `_rg` in a directory that zsh searches for completion functions. The file holds two lines:

```zsh
#compdef rg
source <(rg --generate complete-zsh)
```

With the script the pull request's head generates, the first Tab after `rg` in each new shell completes nothing, and later Tabs work. With the script from before the pull request, the same file completed on the first Tab (*reported*; run below).

## Background

- ripgrep's command is `rg`. `rg --generate complete-zsh` prints ripgrep's zsh completion script. The script defines a function `_rg` that does the completing (*read*).
- zsh's completion system is switched on by running `compinit`. It reads the first line of each file in the directories listed in `fpath`. A first line `#compdef rg` registers that file as the completion function for `rg`, under the file's own name. The file is loaded and run the first time the person presses Tab after `rg` (*read*, zsh's manual, quoted below).
- `compdef _rg rg` registers the function `_rg` for `rg` from then on. It completes nothing by itself. `compdef` exists only after `compinit` has run (*read*, *run*).
- `$funcstack[1]` is zsh's name for the innermost thing that is running: a function, a sourced file or an `eval` (*read*, *run*).
- The file in the candidate is called a *wrapper* below. It does not hold the completion script. It fetches the script from the `rg` binary each time a shell first completes for `rg`.

## What the change does

Two files change: `FAQ.md` (+20, -3) and `crates/core/flags/complete/rg.zsh` (+9, -1). The script's last statement is replaced (*read*):

```diff
-_rg "$@"
+# Don't run the completion function when being sourced by itself.
+#
+# See https://github.com/BurntSushi/ripgrep/issues/2956
+# See https://github.com/BurntSushi/ripgrep/pull/2957
+if [[ $funcstack[1] == _rg ]] || (( ! $+functions[compdef] )); then
+  _rg "$@"
+else
+  compdef _rg rg
+fi
```

These are lines 437 to 445 of the file at the head. Before the change the script always ran `_rg` at its end. After it, the script runs `_rg` only when the innermost running name is exactly `_rg` or `compdef` does not exist. Otherwise it registers `_rg` for `rg` and returns.

The generated script is this file with one placeholder, a list of encodings, filled in. The filled template and the output of the binary built at each commit have the same SHA-256 (*run*, `probes/M1/environment.txt`).

The FAQ part of the change adds two ways to set up zsh completion. They are quoted under "The project's documentation at the head".

## What bears on "Promised?"

**The operation.** The generated script, loaded by `source` or `eval` from inside a function that zsh's completion system has called for `rg`, runs the completion for that call. The script and `rg --generate complete-zsh` are ripgrep's. The wrapper is the person's own file. How a `#compdef` file is found, loaded and called is zsh's.

**zsh's documentation** (zsh 5.8.1 manual pages, read; `upstream/M1-zsh-5.8.1-docs.txt`; line breaks and spacing of the rendered pages removed).

- On a `#compdef` file, zshcompsys(1): "The file will be made autoloadable and the function defined in it will be called when completing names, each of which is either the name of a command whose arguments are to be completed or one of a number of special contexts in the form -context- described below."
- On what such a file may hold, zshmisc(1), "Autoloading functions": "If the KSH_AUTOLOAD option is set, or the file contains only a simple definition of the function, the file's contents will be executed. This will normally define the function in question, but may also perform initialization, which is executed in the context of the function execution, and may therefore define local parameters. It is an error if the function is not defined by loading the file."
- The next paragraph: "Otherwise, the function body (with no surrounding `funcname() {...}') is taken to be the complete contents of the file. This form allows the file to be used directly as an executable shell script. If processing of the file results in the function being re-defined, the function itself is not re-executed. To force the shell to perform initialization and then call the function defined, the file should contain initialization code (which will be executed then discarded) in addition to a complete function definition (which will be retained for subsequent calls to the function), and a call to the shell function, including any arguments, at the end."
- On `funcstack`, zshmodules(1): "This array contains the names of the functions, sourced files, and (if EVAL_LINENO is set) eval commands. currently being executed. The first element is the name of the function using the parameter."
- No passage of these pages mentions sourcing a generated script inside a completion function.

**zsh's own completion functions** (*read*; the 949 files zsh 5.8.1 installs under its `Completion` directory were searched for `source <(` and `eval "$(`; one file matched). zsh's function for npm, in zsh since 2011 and last changed in 2018 (`upstream/M1-zsh-5.8.1-_npm`, `M1-zsh-_npm-commits.json`):

```zsh
#compdef npm

# Node Package Manager completion, letting npm do all the completion work

if (( $+commands[npm] )); then
  eval "$(NPM_CONFIG_UPDATE_NOTIFIER=false npm completion)"
  # Monkey-patch their function to prevent update checks
  functions[_npm_completion]="
    local -x NPM_CONFIG_UPDATE_NOTIFIER=false;
    ${functions[_npm_completion]}
  "

  _npm_completion "$@"
fi
```

It evaluates a script that the tool generates, inside the completion function, and then calls the generated function itself. The rows "A wrapper that calls the function itself" in the table above are this form applied to ripgrep.
