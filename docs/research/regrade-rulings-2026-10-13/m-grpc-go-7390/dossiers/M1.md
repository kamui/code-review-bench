## Problem

Background, in plain words. A gRPC client (a "channel") keeps a *sub-connection* (`SubConn`) for each backend it may talk to. A *load-balancing policy* decides which sub-connections exist and which one carries a call. gRPC tells the policy the state of each sub-connection: IDLE (not trying), CONNECTING (trying), READY (connected) or TRANSIENT_FAILURE (an attempt failed and it is waiting before the next). The policy can call `UpdateAddresses` to give a sub-connection a new list of addresses, and `Connect()` to make an IDLE one start trying. Policies are written by the gRPC team (`pick_first` is the default) and by other people.

The claim. A policy calls `UpdateAddresses` with an empty list on a sub-connection that is READY or CONNECTING. gRPC tells the policy IDLE and, a few microseconds later, CONNECTING. Nothing is being dialled, because the list is empty. The sub-connection stays in CONNECTING. A later `Connect()` does nothing. It leaves that state only when the policy gives it addresses again or shuts it down.

Short answer from the runs: true at the head, and exactly as true at the commit before the change. In 1,600 rounds from READY and 1,600 from CONNECTING at each commit, the outcome was the same every time (*run*).

It is one thing. The candidate records name the same trigger, the same lines and the same end. Some wordings of the claim add one of two further statements. Both were checked and both are false:

- *That the sub-connection goes on to TRANSIENT_FAILURE and then to IDLE after a back-off, with a needless request to resolve names again.* It never reports TRANSIENT_FAILURE. Nothing more is reported in the next 25 seconds (*run*, `TestM1LongHold`). From READY no re-resolution is requested. From CONNECTING one is, and the same one is requested when the list is replaced by a working address, so it comes from cancelling the attempt in progress and not from the empty list (*run*, `TestM1ControlNonEmptyWhileConnecting`).
- *That the change hides IDLE from the policy, or removes a moment in which a `Connect()` could have put things right.* The policy is told IDLE and then CONNECTING at both commits, a median of 32 to 37 microseconds apart with the race detector on (*run*). At the base there is a moment with the lock free. A probe stretched it to 50 ms and used a policy that calls `Connect()` the instant it is told IDLE. `Connect()` then acts inside that moment, and the sub-connection still ends in CONNECTING for good (*run*, `results/base-widened-window.txt`).

## What changed

The pull request edits three places in `clientconn.go`. The second is the one this claim is about (*read*):

```diff
@@ -992,11 +991,9 @@ func (ac *addrConn) updateAddrs(addrs []resolver.Address) {
 		ac.updateConnectivityState(connectivity.Idle, nil)
 	}
 
-	ac.mu.Unlock()
-
 	// Since we were connecting/connected, we should start a new connection
 	// attempt.
-	go ac.resetTransport()
+	go ac.resetTransportAndUnlock()
 }
```

Before the change `updateAddrs` released its lock and then started a goroutine (a lightweight thread) that took the lock again. After it, `updateAddrs` keeps the lock and hands it to the goroutine. That closes a gap in which a second connection attempt could start. The other two edits do the same for `connect()` and rename the function, adding a comment: "resetTransportAndUnlock unconditionally connects the addrConn."

The lines around it at the head, with what each does (*read*):

```go
 990	if len(addrs) == 0 {
 991		ac.updateConnectivityState(connectivity.Idle, nil)
 992	}
 993
 994	// Since we were connecting/connected, we should start a new connection
 995	// attempt.
 996	go ac.resetTransportAndUnlock()
```

Mechanism, step by step, at the head:

1. `updateAddrs` stores the empty list. The sub-connection was READY or CONNECTING, so it cancels what was in progress and schedules the old connection to be closed (lines 954 to 988).
2. The list is empty, so it sets the state to IDLE and queues that news for the policy (lines 990 to 992). It does not return.
3. It starts a new connection attempt whatever the list holds (line 996).
4. The attempt sets the state to CONNECTING, queues that news, and releases the lock (lines 1261 and 1262).
5. It tries each address in turn (`tryAllAddrs`, lines 1309 to 1342). With no address the loop never runs, and the function returns "no error".
6. "No error" is read as "connected". The attempt resets its back-off counter and ends (lines 1300 to 1303). No connection exists. The state is still CONNECTING, and no timer or goroutine is left that would change it.
7. `Connect()` does nothing unless the state is IDLE (lines 914 to 919).

The base does the same in the same order. Its only difference is that the lock is free between step 2 and step 4.

**Which lines the change touches, and which lines cause this** (*read*):

| Lines at the head | What they do | Touched by the change? |
| --- | --- | --- |
| 990 to 992 | report IDLE for an empty list, and carry on | no; they are unchanged context in the hunk |
| 996 | start a new attempt whatever the list holds | **yes**: the statement was rewritten, and the unlock in front of it was removed |
| 1231 to 1234 | the start of the attempt function | **yes**: renamed, comment added, its own `Lock()` removed |
| 1261 and 1262 | report CONNECTING and unlock | no |
| 1264 and 1309 to 1342 | try each address; with none, return "no error" | no |
| 1300 to 1303 | treat "no error" as connected and end | no |
| 905 to 923, `connect()` | ignore `Connect()` unless IDLE, else start an attempt | lines 921 and 922 **yes** |

So the fault needs line 996, which the change rewrote, and lines 1300 to 1342, which it did not touch.

**The smallest edit at the touched place was run.** With `updateAddrs` made to return right after it reports IDLE (`patches/head-return-after-idle.patch`), the sub-connection ends in IDLE. The first `Connect()` then puts it in CONNECTING for good by the other route, through `connect()` and the same attempt function. With `pick_first`, the channel reports IDLE and a call still runs to its deadline, because `pick_first` calls `Connect()` when a call arrives (*run*, `results/head-return-after-idle.txt`; the last clause is *read*, `balancer/pickfirst/pickfirst.go` lines 243 to 246 and 280 to 283). The same happens at both commits without any patch when the empty list reaches a sub-connection that is IDLE or backing off: the next `Connect()` leaves it in CONNECTING for good (*run*, `TestM1Idle`, `TestM1TransientFailure`).

**Rule Before 2: which bullet could apply.**

- *"introduces it or makes it worse"*: cannot apply. The states reported, the final state, the ignored `Connect()`, the waiting call and the recovery are the same at both commits in every round (*run*).
- *"makes it reachable, or makes it show sooner or more clearly"*: cannot apply. The same call reaches it at the base. The policy is told the same two states in the same order, the same few microseconds apart (*run*).
- *"leaves it where a reviewer could find it, in the lines the change touches or in the thing the change says it fixes"*: the first half could apply. Line 996 is one of the statements the fault needs, the change rewrote it, and the IDLE branch sits three lines above it inside the same hunk. The second half cannot: the change says it fixes two attempts starting at once, and this is one attempt over an empty list.

The rule's words do not say whether rewriting one of several statements a fault needs puts the fault "in the lines the change touches". That is the owner's to decide.

## Promised?

**The exact operation.** Calling `UpdateAddresses` with an empty list on a sub-connection that is READY or CONNECTING.

**Who owns it.** grpc-go. `SubConn.UpdateAddresses` and `ClientConn.UpdateAddresses` are in its `balancer` package. How the owner classifies it: **deprecated**, in a package whose every interface is marked experimental. On an empty list the documentation is silent, and maintainers have said different things (below).

## What the affected person sees

The affected person is the author of a load-balancing policy that hands a sub-connection an empty list, and the people whose calls go through that policy.

- **No error text.** Nothing is logged at the default level. With verbose logging the library prints "Subchannel Connectivity change to IDLE", then "Subchannel Connectivity change to CONNECTING", then no "Subchannel picks a new address" line. A later `Connect()` prints "connect called on addrConn in non-idle state (CONNECTING); ignoring." (*run*, `result-head.txt` section 4).
- **The policy** is told IDLE, then CONNECTING, and then nothing more (*run*).
- **Calls.** With a policy that queues calls while its sub-connection is CONNECTING, as `pick_first` does, a call waits until its own deadline and fails with "DeadlineExceeded". A call with no deadline waits until addresses return. The channel reports CONNECTING (*run*). With a policy that reports failure itself when it has no addresses, as the project's test policy does, calls fail at once and nothing looks wrong (*run*).
- **How stuck.** The sub-connection recovers by itself as soon as the policy gives it a non-empty list: it reports READY, and a call that was waiting completes (*run*, every round). Shutting it down and creating a new one also works (*run*). `Connect()` does not help (*run*).
- **Compared with before the change.** The same in every respect (*run*).
