# M4: a value set from code on a disabled field removes the field's server error

Pull request: mui/base-ui #5460, "[field] Sync controlled value changes with field state".
Candidate covered: NC-bee6a2e09430.

Words used here. `Field.Control` is Base UI's text input for a form field, inside a `Field.Root`. It is "controlled" when the app passes the text in through the `value` prop. A "server error" is an error the app hands to `Form` through its `errors` prop, usually after the server has refused a submission; `Field.Error` shows it and `Field.Root` carries `data-invalid` for it. "Base" is the commit before the change, `30b8ea2`. "Head" is the reviewed commit, `14d39e5`. The cut-off is the last push, 2026-08-10T13:33:57Z.

**Already decided?** Not exactly. The known problem `GT-r8` (first-round ruling 26, changed by second-pass review S5, kept by last-push ruling 4) begins "A code-driven value change on a disabled Field.Control updates field state as if enabled". Its saved wording and its ruling name two effects: the validator's error shown on a disabled field, and the dirty mark. Neither names the clearing of a server error, and no saved probe had a `Form` with `errors`. So this is a grouping question under rule Before 4: a third effect of `GT-r8`'s fault, a problem of its own, or not a problem.

Two more saved decisions touch it and do not decide it:

- Last-push ruling 6 made the description's sentence that this pull request "does not" call `clearErrors(name)` a minor defect (claim `CL-r-description-clear-errors`), because a value set from code does clear a server error on an enabled `Input`, "which is what the documentation promises". That is about an enabled field.
- The review text behind this record also says the disabled control "runs the custom validator". That half is `GT-r8` as saved.

**The candidate record reads one source too far.** It says "FieldRoot.tsx comments that app-controlled invalidity is kept while disabled". The comment says that disabling a field does not hide an app-set invalid state. It does not say that a change of value leaves a server error in place.

**Grouping.** One thing: the server error of a disabled field is removed by a value set from code.

## Problem

A form shows a server error on a field. The field is disabled, on `Field.Root` or on the control. The app then changes the field's value from code.

After this change the server error is removed at that moment: `data-invalid` leaves `Field.Root`, and where the error text was shown it disappears. Before the change the error stayed, because nothing reacted to a value set from code.

On an enabled field the same clearing is what the documentation describes: "Once a field's value changes, any corresponding error in `errors` will be cleared from the field state."

## What changed

The new block clears the field's entry in the form's errors whenever the `value` prop changes, with no check for `disabled` (head, `FieldControl.tsx` lines 105 to 115):

```diff
+  useValueChanged(serializedValue, () => {
+    if (serializedValue === undefined) {
+      return;
+    }
+
+    clearErrors(name);                                                 // line 110
+    setDirty(serializedValue !== (validityData.initialValue ?? ''));   // line 111
+    setFilled(serializedValue !== '');
+
+    validation.change(serializedValue);                                // line 114
+  });
```

`clearErrors` removes the field's name from the errors `Form` holds (read, `Form.tsx` lines 145 to 157). Lines 111 and 114 are the ones behind `GT-r8`'s dirty mark and validator error. At the base `clearErrors` was called only from the change event, which a disabled input does not fire.

**Runs** (`probes/M4/probe.test.tsx`; a `Form` whose `errors` hold "Server error" for the field; a controlled control with the value "old"; the app sets "new" from code; the errors object is one stable object, as when an app keeps the server's errors in state; jsdom and real Chromium gave identical lines).

| Case | Base | Head |
| --- | --- | --- |
| `disabled` on the control, `onChange` mode with a validator that accepts | "Server error" stays; `data-invalid` stays; validator not called | **"Server error" gone; `data-invalid` gone**; validator called with "new"; marked dirty |
| `disabled` on the control, default mode, no validator | error stays | **error gone; `data-invalid` gone**; marked dirty |
| `disabled` on `Field.Root` (the error text is not shown for a disabled root at either commit, only the mark) | `data-invalid` stays | **`data-invalid` gone**; marked dirty; in `onChange` mode the validator is called |
| Not disabled, `onChange` mode | error stays; then Send is refused | error gone; then Send submits "new" |
| `disabled` on `Field.Root`, no value change, Send | the form submits; the mark stays | the same |
| Sibling `Switch`, disabled on the control or on `Field.Root`, flipped from code | error gone; `data-invalid` gone | the same |
| Sibling `NumberField`, disabled the same two ways, changed from 1 to 2 from code | error gone; `data-invalid` gone | the same |

Two things to note. The server error of a disabled field does not stop the form from submitting at either commit, because a disabled control is not registered with the form. And the sibling controls already cleared a server error on a code-driven change while disabled before this pull request.

A first version of the probe passed `errors={{ message: 'Server error' }}` inline, so that each render made a new object. The error then never went away at either commit, because `Form` copies a new errors object into its state again. The table is from the corrected probe.

**Which of the three ways.**

- Built and stated, for keeping it: the `FieldRoot.tsx` comment and #5116 say an app-set invalid state stays on a disabled field; #4810 stopped a locked control's change from clearing existing errors.

## What the affected person sees

- **With `disabled` on the control:** the end user sees the server's message under a field they cannot edit. When the app changes that field's value from code, the message disappears and the field is no longer styled as invalid.
- **With `disabled` on `Field.Root`:** no message was shown to begin with; the invalid styling disappears.
- Nobody is blocked at either commit: a disabled field's server error does not stop the form from submitting (run).
- Whether the message should stay is the open point. It was the server's verdict on the old value, and the value has changed.

It needs a `Form` with `errors`, a controlled `Field.Control` that is disabled while it carries one, and an app that changes that field's value from code.

## Recommendation

> **What happens:** a value set from code on a disabled controlled `Field.Control` removes the field's server error and its `data-invalid` mark; before the change the error stayed. **Promised: yes**, built and stated, as part of `GT-r8`: "App-controlled invalidity (the `invalid` prop and `<Form>` errors) keeps the field marked invalid even while disabled." (`FieldRoot.tsx` at the head) and "An app-set invalid state now stays on the field even while disabled." (#5116, 2026-06-24). **Delivered: no**, the block that `GT-r8` faults for treating a disabled control as enabled also removes its app-set error. **So: an existing family described differently, `GT-r8`**, which goes to the owner as a question of widening it. **Band, decided separately:** none; the family's saved band is other-material.

Recommendation code: `duplicate` of `GT-r8`. Confidence: low. It falls short of high on two conditions: two promises point different ways, and the rule's tests do not say whether this effect is a fault.

**Where the rules do not decide.**

- **Two promises meet.** The handbook's "Once a field's value changes, any corresponding error in `errors` will be cleared" and the code's "keeps the field marked invalid even while disabled" both apply when a disabled field's value changes. Rule Delivered 3 says the promise the application's own action calls on governs, and gives two examples, both about `cancel()` and prevented events. Here the app both disabled the field and changed its value. The rule says other kinds of conflict go to the owner.
- **Is it a symptom at all.** Rule Before 4 asks whether a comment describes another symptom of a known fault. All three tests hold. Whether removing a server error from a disabled field is something wrong, or the documented clearing doing its job, is not something the tests answer.

**Strongest argument against the recommendation.** The documentation is the only place that tells an app developer when a server error goes away, and it says: when the value changes. It makes no exception for a disabled field, the sibling controls make none, and a stale server verdict on a value that is no longer there helps nobody. The `FieldRoot.tsx` comment is about a different event, the field becoming disabled, and the maintainers' guard in #4810 is about a browser autofilling a locked control, not about the app changing its own value. On that reading the clearing is promised and delivered, and a comment on it is an observation.
