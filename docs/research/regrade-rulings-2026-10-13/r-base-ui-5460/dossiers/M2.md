# M2: a number field rendered through the field-aware `Input` has its formatted text validated after the number

Pull request: mui/base-ui #5460, "[field] Sync controlled value changes with field state".
Candidate covered: NC-367ce94c554c.

Words used here. `NumberField` is Base UI's numeric input. Its text box is `NumberField.Input`. `Input` is Base UI's plain text input, which its page says "automatically works with" a field; in the code it is `Field.Control`. Every Base UI part takes a `render` prop that says which element to draw, so `<NumberField.Input render={<Input />} />` draws the number field's text box as an `Input`. The "validator" is the app's `validate` function on `Field.Root`. "Base" is the commit before the change, `30b8ea2`. "Head" is the reviewed commit, `14d39e5`. The cut-off is the last push, 2026-08-10T13:33:57Z.

**Already decided?** Not exactly. The known problem `GT-r7` (first-round ruling 27, changed by second-pass review R6) is this fault for one composite control: "A Combobox.Input rendered through the field-aware Input validates its label as well as its selected object". Its wording, trigger and probe name the combobox only. This group is the same mechanism with `NumberField.Input`. So the question is one of grouping under rule Before 4: is this part of `GT-r7`, a problem of its own, or not a problem. The candidate record does not misread a ruling; it says the base behaviour and the promise were not checked, and both are checked below.

**Grouping.** One thing. The review text behind the record names two composites, the combobox and the number field. The combobox half is `GT-r7` itself. This group is the number-field half.

## Problem

Inside a `Field.Root`, a `NumberField` validates the number. When its text box is drawn as the field-aware `Input`, that `Input` is a second field control on the same field, and it holds the formatted text, such as `"2,000"`.

After this change the `Input` validates that text whenever it changes without the person typing: when the app sets the number from code, and when the number field reformats what the person typed as they leave the field. The validator is then called a second time with a string, and that second result replaces the first. A validator written for the number gives a different answer for the string: "Too big" is lost for 2000, and a validator that checks the type shows a false error for a valid number.

Before the change the `Input` validated only when the person typed into it.

## What changed

`NumberField.Input` passes its text as `value` to the element it draws (read, `NumberFieldInput.tsx` line 118: `value: inputValue`), and validates the number itself (read, lines 89 and 101 to 110):

```ts
  useRegisterFieldControl(inputRef, id, value, undefined, !disabled, nameProp);
  ...
  useValueChanged(value, () => {
    clearErrors(name);
    ...
    validation.change(value);
  });
```

With `Input` as that element, this pull request's new block in `Field.Control` sees a controlled value change and validates the text (head, `FieldControl.tsx` lines 105 to 115):

```diff
+  useValueChanged(serializedValue, () => {
+    if (serializedValue === undefined) {
+      return;
+    }
+
+    clearErrors(name);
+    setDirty(serializedValue !== (validityData.initialValue ?? ''));
+    setFilled(serializedValue !== '');
+
+    validation.change(serializedValue);
+  });
```

At the base `Field.Control` updated the field only from its own change event, which fires when the person types.

**An older fault sits under this one.** Both controls register with the same field, and the one that registered last supplies the value that is validated when the form is submitted (read, `useFieldControlRegistration.ts`, `register`). With the field-aware `Input` that is the text. This is the same at both commits (run, below): at Send the validator receives `"2,000"`.

**Runs** (`probes/M2/probe.test.tsx`; a controlled `NumberField` in a `Form` and a `Field.Root`; the validator is `value > 1000 ? 'Too big' : null` unless a row says otherwise; `validationMode="onChange"` unless a row says otherwise; jsdom and real Chromium gave identical lines).

With `<NumberField.Input render={<Input />} />`:

| Step | Base | Head |
| --- | --- | --- |
| The app sets 2000 from code | validator called with `2000`; "Too big" shown; field invalid | validator called with `2000`, then `"2,000"`; **no error; field marked valid** |
| Then the person presses Send | validator called with `"2,000"`; error gone; **the form submits 2000** | validator called with `"2,000"`; the form submits 2000 |
| The person types 2000 | "Too big" shown (validator called with each text and each number) | the same |
| Then leaves the field; the text becomes `2,000` | "Too big" stays | validator called with `"2,000"`; **error gone; field marked valid** |
| Then presses Send | validator called with `"2,000"`; the form submits 2000 | the form submits 2000 |
| The person presses the increment button at 1000 | validator called with `1001`; "Too big" shown | validator called with `"1,001"`, then `1001`; "Too big" shown |
| A validator that accepts only a number; the app sets 7 from code | validator called with `7`; valid | validator called with `7`, then `"7"`; **"Enter a number" shown at once** |
| Then Send | validator called with `"7"`; "Enter a number"; submit refused | the same; submit refused |
| Default mode: the app sets 2000, then Send | validator called once, with `"2,000"`; the form submits 2000 | the same |

With a plain `<NumberField.Input />` the validator only ever receives the number, "Too big" is shown and Send is refused, in every row, at both commits.

So the older fault already let a too-big number through at Send, at both commits. What the change adds: the number's verdict is replaced by the text's verdict as soon as the text changes without typing. For the person that is new in two places: after a value set from code, and after they type a value and leave the field.

## What the affected person sees

An app that draws its number field's text box as its own styled `Input`, which wraps Base UI's `Input`, inside a `Field.Root` with a validator for the number.

- **The end user types 2000 and tabs away.** At the base "Too big" stays on screen. At the head it disappears as the text becomes `2,000`, and the field shows as valid. At both commits pressing Send submits 2000.
- **The app sets a value from code** (a preset button, a loaded record). At the base a rejected number shows its error. At the head it shows none.
- **With a validator that checks the type**, the user sees "Enter a number" under a valid number as soon as the app sets it, where at the base it appeared at Send. Send is refused at both commits.

The developer can avoid it by drawing a plain `<NumberField.Input />`, or by making the validator accept the formatted text.

## Recommendation

> **What happens:** with `NumberField.Input` drawn through the field-aware `Input`, the validator is called a second time with the formatted text whenever that text changes without typing, and that verdict replaces the number's; before the change this happened only at Send. **Promised: yes**, built, as part of `GT-r7`: the project's own tests draw a composite's text box through `Input` ("submits when input renders a field-aware input", `ComboboxRoot.test.tsx:9126`); for the number field alone no test, page or statement was found. **Delivered: no**, a rejected number shows as valid, or a valid number shows a false error, as soon as the app sets it or the person leaves the field. **So: an existing family described differently, `GT-r7`**, which goes to the owner as a question of widening it from the combobox to any composite's text box. **Band, decided separately:** none; the family's saved band is other-material.

Recommendation code: `duplicate` of `GT-r7`. Confidence: low. It falls short of high on two conditions: the one-fix test does not come out cleanly, and a second rule points the other way.

**Where the rules do not decide.**

- **One fix.** Rule Before 4 joins two symptoms when one fix cures both. Here one guard line serves both, and each composite still needs its own line to mark its text box. The rule's joined examples have one changed line; its kept-separate example has two smallest fixes at different lines. This sits between them.
- **Two rules point different ways.** Rule Before 4 would make this part of `GT-r7`. Rule Promised 8 would make it not promised if the number-field composition is judged alone, because nothing the project built or wrote covers it; with programs shown doing it, that would be "relied on, not promised", which only the owner settles.

**Strongest argument against the recommendation.** `GT-r7` was ruled a problem because the project's own tests use the combobox composition. Nothing of the kind exists for the number field. No program is shown using it inside a field with a validator, and the form already let the bad value through at Send before the change. On that reading nothing was promised, and what is left is advice to the author that a second composite has the combobox's fault.
