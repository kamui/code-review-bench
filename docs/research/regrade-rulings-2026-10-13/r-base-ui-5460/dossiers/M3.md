# M3: a field enabled in the same render that sets its value is marked dirty against the value it starts from

Pull request: mui/base-ui #5460, "[field] Sync controlled value changes with field state".
Candidates covered: NC-53e60a519d27, NC-2e86f049aace, NC-0e87b8f4ad4b.

Words used here. `Field.Control` is Base UI's text input for a form field, inside a `Field.Root` that holds the field's state. It is "controlled" when the app passes the text in through the `value` prop. A field is "dirty" when its value differs from its "initial value", the starting value the field records for comparison; `Field.Root` shows that as the `data-dirty` mark. A "render" here means one update of the screen by React, in which several changes made by the app land together. "Base" is the commit before the change, `30b8ea2`. "Head" is the reviewed commit, `14d39e5`. The cut-off is the last push, 2026-08-10T13:33:57Z.

**Already decided?** No, and two saved decisions sit on either side of it.

- The known problem `GT-r8` (first-round ruling 26, changed by second-pass review S5, kept by last-push ruling 4) covers "A code-driven value change on a disabled Field.Control": the value changes while the control stays disabled. Its probe changes the value in one step and enables the control in a later one. It does not cover a control that is enabled in the same render that sets the value. The simplest cure for `GT-r8`, a check for `disabled`, does not reach this case (run, below).
- Second-pass ruling 17 (claim `CL-r-late-load-dirty`, a suggestion) covers a field that is mounted empty and enabled, whose value arrives later: it is marked dirty against the empty value recorded at mount. It does not cover a control that was disabled at mount, for which the field records nothing until the control is enabled.
- The candidate records do not misread either ruling. They ask for the runs and for the grouping decision, which follow.

**Grouping.** One thing, with two degrees. All three records describe a controlled control that is enabled and given its value in one render. Two say the field is then marked dirty. The third adds that when the field validates on change the recorded initial value is lost as well, so the mark stays wrong afterwards. Both come from the same step and the same lines, and the second happens only on top of the first. The review text also says the same happens "when the value arrives while the control is still disabled"; that route is `GT-r8`'s own and is not part of this group.

## Problem

An edit form often keeps its fields disabled while their data loads, then enables them with the loaded value. With a controlled `Field.Control` both changes land in one render.

After this change the field is marked dirty at that moment, before anyone has touched it, although the value it holds is the one the field itself records as its initial value. In the default validation mode the mark corrects itself once the person edits the field and returns to the loaded value. When the field validates on change (`validationMode="onChange"`), the recorded initial value is lost for good: the field reads dirty at the loaded value and clean when emptied.

Before the change the field came out of loading clean.

## What changed

A disabled control is not registered with its field (`useRegisterFieldControl(..., !disabled, ...)`, head line 95), so the field records no initial value while the control is disabled. The first time the control is enabled, the registration records the value it holds then (read, `useFieldControlRegistration.ts`, unchanged by this pull request):

```ts
  function captureInitialValue(registration: FieldControlRegistration) {
    if (initialValueCapturedRef.current) {
      return;
    }

    initialValueCapturedRef.current = true;
    const initialValue = getRegistrationValue(registration);

    setValidityData((prev) =>
      prev.initialValue === initialValue ? prev : { ...prev, initialValue },
    );
  }
```

The pull request adds a block that runs in the same step, right after that registration (head, `FieldControl.tsx` lines 105 to 115):

```diff
+  useValueChanged(serializedValue, () => {
+    if (serializedValue === undefined) {
+      return;
+    }
+
+    clearErrors(name);
+    setDirty(serializedValue !== (validityData.initialValue ?? ''));   // line 111
+    setFilled(serializedValue !== '');
+
+    validation.change(serializedValue);                                // line 114
+  });
```

Two things go wrong in the render that enables the control and changes its value.

- **Line 111** reads `validityData.initialValue` as it was when this render began. The registration's new value is queued and not yet visible, so the block compares against nothing, falls back to the empty text, and marks any non-empty value dirty.
- **Line 114**, when the field validates on change, runs the validator and then stores a whole new state object built from the same old reading, with `initialValue: validityData.initialValue` (read, `useFieldValidation.ts` lines 302 to 313, unchanged). That replaces the value the registration had just queued. The registration records only once, so the initial value stays empty from then on.

Before the change no code reacted to a value set from code, so nothing ran beside the registration.

**Runs** (`probes/M3/probe.test.tsx`; a controlled control that starts empty and disabled; one click sets the value to "loaded" and enables it; "recorded" is the field's initial value read through `Field.Validity`; `disabled` on `Field.Root` and on the control gave the same lines; jsdom and real Chromium gave identical lines).

| Case | Base | Head |
| --- | --- | --- |
| Default mode: enabled and given its value in one render | recorded "loaded"; not dirty | recorded "loaded"; **dirty** |
| Then the person types one more letter, then deletes it | dirty, then not dirty | dirty, then not dirty |
| `onChange` mode, validator accepts: enabled and given its value in one render | recorded "loaded"; not dirty; validator not called | **recorded nothing; dirty**; validator called with "loaded" |
| Then the person types one more letter, then deletes it | dirty, then not dirty | dirty, then **still dirty** |
| Then the person empties the field | dirty | **not dirty** |
| Default mode: the value arrives while disabled, the control is enabled in a later render (`GT-r8`'s route) | not dirty | dirty while disabled and after enabling; recorded "loaded" |
| The same in `onChange` mode, then the person types one more letter and deletes it | not dirty | dirty; validator called while disabled; after the edit and return, not dirty; recorded "loaded" |
| Default mode: the control is enabled first, the value arrives in a later render | recorded ""; not dirty | recorded ""; dirty (the ruled suggestion) |
| A field that was never disabled, value set from code | recorded ""; not dirty | recorded ""; dirty (the ruled suggestion) |
| `Field.Root` is given a new `key` when the data arrives | recorded "loaded"; not dirty | recorded "loaded"; not dirty |
| Sibling: a controlled `Checkbox` whose `Field.Root` is enabled in the render that ticks it | recorded `true`; dirty | the same |

**Whether it worked before, and whose behaviour changed.** Before the change the field came out of loading clean, with the loaded value recorded (run). Base UI's `Field.Control` changed. The sibling `Checkbox` already behaved as the head does (run).

**Which of the three ways.**

- Written: the documentation defines the mark by the field's initial value, and `Field.Validity` shows that value. At the head, in the default mode, the field shows "loaded" as its initial value, holds "loaded", and is marked dirty.
- Announced: nothing for this case. The change says code-driven changes now update the dirty state; that is the ground of second-pass ruling 17 for a field enabled at mount.
- Built: the registration records the value at the first enabling, at both commits.

The answer proposed is **yes**, written: the mark is defined against the field's own initial value. It rests on reading the value recorded at enabling as that initial value, as `GT-r8`'s ruling did for the dirty mark of a disabled control. See "Where the rules do not decide".

## Delivered?

No. The outcome the promise is for is a mark that tells whether the value differs from the field's initial value.

- In the default mode the field is marked dirty while its value equals the initial value it records (run). Rule Delivered 1 counts a status the software reports about itself. It lasts until the person's next edit.
- In `onChange` mode the recorded initial value is gone, and from then on the mark says dirty at the loaded value and clean when the field is empty (run). It stays so for the life of the `Field.Root`.

## What the affected person sees

- **The end user** opens an edit form. When the data arrives, every such field is styled as changed although they have touched nothing. If the app shows "unsaved changes" from the dirty state, it shows it at once.
- **In the default mode** the mark goes away after the person edits a field and returns to the loaded value.
- **In `onChange` mode** it never does while the loaded value is there, and a field the person empties reads as unchanged.
- **The app's developer** who reads `dirty` to decide whether to warn before leaving, or which fields to send, gets a wrong answer. No run showed an app doing that.

It needs a controlled `Field.Control` that is disabled at mount and is enabled in the render that gives it a non-empty value. A developer can avoid it by keying `Field.Root` on the loaded state (run), by passing `dirty` themselves, or by enabling the field one render after setting the value, which is `GT-r8`'s route and also marks it dirty.

## Both sides

For a problem:

- The field contradicts itself: it shows "loaded" as its initial value, holds "loaded", and says it has changed (run).
- In `onChange` mode the mark is wrong for the life of the field and reads backwards (run).
- It is new with this change, and the trigger is an ordinary one: fields disabled while data loads.
- `GT-r8` was ruled a problem on the same documented mark.

For part of `GT-r8`:

- The same block, and in the default mode only timing separates the two.
- The obligation saved for `GT-r8` already speaks of preserving "an accurate dirty baseline".

For a suggestion:

- A maintainer wrote before the cut-off that a value that arrives later "is a change → dirty", and second-pass ruling 17 made that a suggestion for a field enabled at mount. A person who reads the starting value as the one at mount sees the mark as right and only the recorded value as odd.
- The sibling `Checkbox` did the same before the change (run).
- Nobody is blocked, and no app is shown acting on the mark.

## Recommendation

> **What happens:** a controlled `Field.Control` that is enabled in the render that sets its value is marked dirty although that value is the one the field records as its initial value, and when the field validates on change the recorded value is lost, so the mark stays wrong and reads backwards. **Promised: yes**, written: "`data-dirty` | Present when the field's value has changed." and `dirty`, "Whether the field's value has been changed from its initial value." (the Field page at the head). **Delivered: no**, the field reports a change against the value it itself records as initial, and in `onChange` mode keeps doing so. **So: problem.** **Band, decided separately:** other-material: a wrong state mark that misleads styling and any "unsaved changes" logic; nobody is blocked and nothing is lost.

Recommendation code: `problem`. Band: `other-material`. Confidence: low. It falls short of high on two conditions: two readings of rule Before 4 point different ways, and no rule says which initial value a control that starts disabled has.

**Who is hurt, for the band.** The end user of an edit form, who sees untouched fields styled as changed, and the developer who reads `dirty`. Nobody is stuck. The boundary's reason for a wrong reported state that people act on would apply if an app were shown acting on this mark; none is. `GT-r8` and `GT-r2`, the two wrong state marks already on this answer key, are other-material.

**Where the rules do not decide.**

- **Grouping.** Rule Before 4 joins two symptoms only when one fix cures both, and here each smallest fix cures only its own (run), which points to a separate problem. Its sentence from decision P26 joins two places when only timing decides which fails and the result is the same, which holds here in the default mode and not in `onChange` mode. The two readings point different ways. Grouping is the owner's.
- **Which initial value.** No rule or statement says what the initial value of a control that starts disabled is. If it is the value at mount, second-pass ruling 17 makes the dirty mark announced behaviour. If it is the value recorded at enabling, as the code records it and as `GT-r8`'s ruling took it, the mark is wrong.

**Strongest argument against the recommendation.** The maintainers said before the cut-off that a value arriving after mount is a change, and the owner already ruled that exact mark a suggestion when the field is enabled at mount. Enabling the field in the same render does not change what the person sees or what the developer can do about it; the documented remedy, keying `Field.Root`, works. What is special here is an internal reading that came out stale, and outside `onChange` mode it heals at the next edit.
