# Card: a value set from code on a disabled field removes the field's server error

Pull request: mui/base-ui #5460, "[field] Sync controlled value changes with field state". Each fact is marked *run* (executed, probe and output saved under `probes/M4/`) or *read* (visible in the diff or the source). "Base" is the commit before the change and "head" the reviewed commit.

## Background

Base UI is a library of React components. `Field.Control` is its text input for a form field. It sits inside a `Field.Root`, which holds the field's state and shows it as marks such as `data-invalid` and `data-dirty`. `Field.Error` shows the field's error text.

A control is *controlled* when the app passes the text in through the `value` prop and stores each edit itself.

`Form` takes an `errors` prop: an object with field names as keys and error texts as values. An app uses it to show errors the server returned for a submission. This file calls such an error a *server error*. A field with one is marked invalid.

`disabled` can be set on `Field.Root` or on the control. A disabled control is not registered with its form (*read*, `FieldControl.tsx` head line 95).

"Base" is the commit before the change, `30b8ea2`. "Head" is the reviewed commit, `14d39e5`.

## What the change does at this place

It changes `packages/react/src/field/control/FieldControl.tsx` and its test file, and nothing else (*read*).

It adds a block that runs after each render in which the control's `value` prop has changed (*read*, head lines 105 to 115):

```diff
+  useValueChanged(serializedValue, () => {
+    if (serializedValue === undefined) {
+      return;
+    }
+
+    clearErrors(name);                                                 // line 110
+    setDirty(serializedValue !== (validityData.initialValue ?? ''));   // line 111
+    setFilled(serializedValue !== '');
+
+    validation.change(serializedValue);                                // line 114
+  });
```

`clearErrors(name)` removes the field's name from the errors that `Form` holds (*read*, `packages/react/src/form/Form.tsx` lines 145 to 157). The block has no check for `disabled`.

At the base `Field.Control` called `clearErrors(name)` only from the input's change event (*read*, base `FieldControl.tsx`: inside `onChange`, under `if (!event.nativeEvent.defaultPrevented)`). A disabled input fires no change event.

## The runs

All in the project's own test setup: a `Form` whose `errors` hold "Server error" for the field, and a controlled control with the value "old". The app then sets the value to "new" from code. The errors object is one stable object, as when an app keeps the server's errors in state. jsdom and real Chromium printed identical lines (*run*).

| Case | Base | Head |
| --- | --- | --- |
| 1. `disabled` on the control; `onChange` mode with a validator that accepts | "Server error" stays; `data-invalid` stays; validator not called; not dirty | "Server error" gone; `data-invalid` gone; validator called with "new"; dirty |
| 2. `disabled` on the control; default mode, no validator | "Server error" stays; `data-invalid` stays | "Server error" gone; `data-invalid` gone; dirty |
| 3. `disabled` on `Field.Root`; `onChange` mode with a validator that accepts | `data-invalid` stays; validator not called | `data-invalid` gone; validator called with "new"; dirty |
| 4. `disabled` on `Field.Root`; default mode, no validator | `data-invalid` stays | `data-invalid` gone; dirty |
| 5. Not disabled; `onChange` mode | "Server error" stays; then Send is refused | "Server error" gone; then Send submits "new" |
| 6. `disabled` on `Field.Root`; no value change; Send | the form submits; `data-invalid` stays | the same |
| 7. After case 1 or 3: Send | the form submits | the form submits |
| 8. Sibling control `Switch`, disabled on the control or on `Field.Root`, flipped from code | error and `data-invalid` gone | error and `data-invalid` gone |
| 9. Sibling control `NumberField`, disabled the same two ways, changed from 1 to 2 from code | error and `data-invalid` gone | error and `data-invalid` gone |

- With `disabled` on `Field.Root`, `Field.Error` shows no text at either commit, before or after the change of value; only the `data-invalid` mark is there.
- In a first version of the probe the errors were passed as a new object on every render (`errors={{ message: 'Server error' }}` inline). The error text then never went away in any case, at either commit: `Form` copies a new errors object into its state again (*run*, output not saved; *read*, `Form.tsx` lines 73 to 77).

## What the affected person sees

- With `disabled` on the control: the server's message is shown under a field the person cannot edit. When the app changes that field's value from code, the message disappears and the field is no longer marked invalid (*run*, rows 1 and 2).
- With `disabled` on `Field.Root`: no message is shown at either commit; the invalid mark disappears (*run*, rows 3 and 4).
- The form submits at both commits whether or not the mark is there (*run*, rows 6 and 7).

## Impact facts

- **Who is affected:** apps with a `Form` that shows server errors, a controlled `Field.Control` that is disabled while it carries one, and code that changes that field's value while it is disabled.
- **How:** the server error and the invalid mark of the disabled field are removed when the value changes. With `disabled` on `Field.Root` only the mark was shown, and it is removed.
- **How stuck:** nobody is blocked; a disabled field's server error does not stop the form from submitting at either commit.
- **How common:** not measured. No public program with this combination was found.
- **Neighbours:** `Switch` and `NumberField` removed a server error in the same situation before this pull request. On an enabled field a value set from code also removes the server error at the head (row 5).
