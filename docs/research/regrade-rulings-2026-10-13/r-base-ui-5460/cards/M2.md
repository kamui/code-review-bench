# Card: a number field drawn through the field-aware `Input` has its formatted text validated after the number

Pull request: mui/base-ui #5460, "[field] Sync controlled value changes with field state". Each fact is marked *run* (executed, probe and output saved under `probes/M2/`) or *read* (visible in the diff or the source). "Base" is the commit before the change and "head" the reviewed commit.

## Background

Base UI is a library of React components. A `Field.Root` holds a form field's state and runs the app's `validate` function. Controls placed inside it report their value to it.

`NumberField` is the library's numeric input. Its text box is the part `NumberField.Input`. The number field keeps a number and shows it as formatted text: the number 2000 is shown as `2,000`.

`Input` is the library's plain text input. In the code it is `Field.Control` under another name (*read*, `packages/react/src/input/Input.tsx`: `return <Field.Control ref={forwardedRef} {...props} />;`). It is called "field-aware" in the project because it reports to the surrounding `Field.Root`.

Every part takes a `render` prop that says which element to draw. `<NumberField.Input render={<Input />} />` draws the number field's text box as an `Input`. The same field then has two controls reporting to it: the number field with the number, and the `Input` with the text.

"Base" is the commit before the change, `30b8ea2`. "Head" is the reviewed commit, `14d39e5`.

## What the change does at this place

It changes `packages/react/src/field/control/FieldControl.tsx` and its test file, and nothing else. It does not touch the number field (*read*).

It adds a block to `Field.Control` that runs after each render in which the control's `value` prop has changed (*read*, head lines 105 to 115):

```diff
+  useValueChanged(serializedValue, () => {
+    if (serializedValue === undefined) {
+      return;
+    }
+
+    clearErrors(name);
+    setDirty(serializedValue !== (validityData.initialValue ?? ''));
+    setFilled(serializedValue !== '');
+
+    validation.change(serializedValue);
+  });
```

At the base `Field.Control` updated the field only from the input's change event, which fires when a person types.

`NumberField.Input` passes its formatted text as `value` to the element it draws, and validates the number itself (*read*, `packages/react/src/number-field/input/NumberFieldInput.tsx` lines 89, 101 to 110 and 118, unchanged by this pull request):

```ts
  useRegisterFieldControl(inputRef, id, value, undefined, !disabled, nameProp);
  ...
  useValueChanged(value, () => {
    clearErrors(name);

    if (blockRevalidationRef.current && !shouldValidateOnChange()) {
      blockRevalidationRef.current = false;
      return;
    }

    validation.change(value);
  });
  ...
    value: inputValue,
```

Both controls register with the same field. The control that registered last supplies the value that is validated when the form is submitted (*read*, `useFieldControlRegistration.ts`, unchanged by this pull request).

## The runs

All in the project's own test setup: a controlled `NumberField` inside a `Form` and a `Field.Root`. The validator is `value > 1000 ? 'Too big' : null` unless a row says otherwise. `validationMode="onChange"` unless a row says otherwise. jsdom and real Chromium printed identical lines (*run*).

With `<NumberField.Input render={<Input />} />`:

| Step | Base | Head |
| --- | --- | --- |
| 1. The app sets 2000 from code | validator called with `2000`; "Too big" shown; field marked invalid | validator called with `2000`, then with `"2,000"`; no error; field marked valid |
| 2. Then the person presses Send | validator called with `"2,000"`; the error goes away; the form submits 2000 | validator called with `"2,000"`; the form submits 2000 |
| 3. The person types 2000 | validator called with each text and each number; "Too big" shown | the same |
| 4. Then leaves the field; the text becomes `2,000` | "Too big" stays | validator called with `"2,000"`; the error goes away; field marked valid |
| 5. Then presses Send | validator called with `"2,000"`; the form submits 2000 | the form submits 2000 |
| 6. The person presses the increment button at 1000 | validator called with `1001`; "Too big" shown | validator called with `"1,001"`, then `1001`; "Too big" shown |
| 7. A validator that accepts only a number or an empty field, and returns "Enter a number" for anything else; the app sets 7 from code | validator called with `7`; valid | validator called with `7`, then `"7"`; "Enter a number" shown |
| 8. Then Send | validator called with `"7"`; "Enter a number" shown; submit refused | "Enter a number" shown; submit refused |
| 9. Default mode: the app sets 2000, then Send | validator called once, with `"2,000"`; the form submits 2000 | the same |

With a plain `<NumberField.Input />`, the same steps at both commits: the validator receives only the number, "Too big" is shown in rows 1 to 6 and Send is refused; in row 7 the field is valid and Send submits 7.

## What the affected person sees

An app that draws its number field's text box as an `Input` built on Base UI's `Input`, inside a `Field.Root` with a validator written for the number.

- The person types 2000 and tabs away. At the base "Too big" stays under the field. At the head it disappears as the text becomes `2,000`, and the field is marked valid. Pressing Send submits 2000 at both commits (*run*, rows 3 to 5).
- The app sets a value from code. At the base a rejected number shows "Too big". At the head it shows no error (*run*, row 1).
- With a validator that checks the type, "Enter a number" appears under a valid number as soon as the app sets it. At the base it appears at Send. Send is refused at both (*run*, rows 7 and 8).

## Impact facts

- **Who is affected:** apps that draw `NumberField.Input` through `Input` (or through their own input component built on it) inside a `Field.Root` whose validator is written for the number.
- **How:** after a value set from code, or after the person types a value and leaves the field, the result shown is the one for the formatted text. A rejected number can show as valid, and with a validator that checks the type a valid number shows an error.
- **How stuck:** with the "Too big" validator nobody is blocked; the form submits the number at both commits. With the type-checking validator Send is refused at both commits. Drawing a plain `<NumberField.Input />` avoids it (*run*).
- **How common:** not measured. Two public programs drew a number field's text box through a wrapped Base UI `Input` before the cut-off; neither is shown with a validator.
- **Neighbours:** at the base the form already validated the text at Send and submitted 2000. A `Combobox.Input` drawn through `Input` is validated with its item and then with its label text at the head.
