# Card: a controlled field renders twice for each keystroke when it validates on change

Pull request: mui/base-ui #5460, "[field] Sync controlled value changes with field state". Each fact is marked *run* (executed, probe and output saved under `probes/M1/`) or *read* (visible in the diff or the source). "Base" is the commit before the change and "head" the reviewed commit.

## Background

Base UI is a library of React components. `Field.Control` is its text input for a form field. It sits inside a `Field.Root`, which holds the field's state: whether it is valid, dirty (changed), filled, and so on. Other parts of the field (label, error message) read that state.

A control is *controlled* when the app passes the text in through the `value` prop and stores each edit itself in `onValueChange`. It is *uncontrolled* when the input keeps its own text.

`validationMode` on `Field.Root` says when the app's `validate` function runs: `onSubmit` (the default), `onBlur` or `onChange`.

A *render* is one run of a component's code by React. When several state updates happen inside one event, React renders once for all of them. A state update made in a *layout effect*, which runs right after a render, causes another render at once, before the browser paints.

"Base" is the commit before the change, `30b8ea2`. "Head" is the reviewed commit, `14d39e5`. The "earlier revision" is `6a40cf1`, the first commit pushed to the pull request at 13:12:08Z, which the last push replaced.

`useValueChanged` calls its function from a layout effect when the value differs from the previous render's (*read*, `packages/react/src/internals/useValueChanged.ts`). When validation runs, it ends by storing a new result object in the field's state (*read*, `useFieldValidation.ts` line 313). At the base the handler did all of this inside the change event, the same event in which the app stores the new text.

The change also adds this test (*read*, `FieldControl.test.tsx` lines 47 to 80):

```tsx
  it('renders once per keystroke for controlled input changes', async () => {
    const renderCountRef = { current: 0 };

    function App() {
      const [value, setValue] = React.useState('');
      return (
        <Field.Root>
          <Field.Control
            data-testid="control"
            value={value}
            onValueChange={setValue}
            render={(props) => {
              renderCountRef.current += 1;
              return <input {...props} />;
            }}
          />
        </Field.Root>
      );
    }

    renderNonStrict(<App />);

    const control = screen.getByTestId('control');

    // The first keystroke also flips dirty and filled, so measure the steady state after it.
    fireEvent.change(control, { target: { value: 'a' } });
    const settledRenderCount = renderCountRef.current;

    fireEvent.change(control, { target: { value: 'ab' } });
    fireEvent.change(control, { target: { value: 'abc' } });

    // The controlled echo must not schedule a second render per keystroke.
    expect(renderCountRef.current).toBe(settledRenderCount + 2);
  });
```

The test has no `validationMode` and no `validate`, so it runs in the default mode before any submit. This test is not in the earlier revision; it came with the last push (*read*, the diff between the two commits).

## What the affected person sees

A person typing sees no difference: the same text, the same validation result, the same screen (*run*: the same validator calls per keystroke at both commits; *read*: the second render lands before paint).

An app developer who profiles renders sees the control and every part of the field that reads its state render twice per keystroke.

## Impact facts

- **Who is affected:** apps with a controlled `Field.Control` (or `Input`) in a field that validates on change: `validationMode="onChange"`, the default mode once a submit has been attempted, or a field the app marks invalid.
- **How:** the field's render work per keystroke roughly doubles. Measured, that is about 0.03 ms more per keystroke for an ordinary field and about 0.2 ms more for a field with fifty extra parts, in development mode.
- **How stuck:** nobody is blocked and nothing is shown wrong. An uncontrolled control renders once per keystroke.
- **How common:** controlled controls with validation on change are an ordinary setup; two public programs with it were found before the cut-off. No report of slowness was found.
- **Neighbours:** the two sibling controls that were run, `NumberField` and `Checkbox`, already rendered twice per change before this pull request, `NumberField` on every typed digit.
