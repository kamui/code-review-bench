# Card: validating many selections of one field that carry arguments takes longer

Pull request: graphql/graphql-js #3457, "OverlappingFieldsCanBeMergedRule: simplify argument comparison". graphql-js is the reference JavaScript implementation of GraphQL. A server validates each query a client sends with `validate(schema, document)` before executing it. Validation is synchronous: while it runs, the Node.js process does nothing else. "Base" is the commit before the change and "head" the reviewed commit.

A query may select the same field more than once under one response name, directly or through fragments. One validation rule compares every pair of such selections, so N selections make N × (N − 1) / 2 comparisons. The change rewrites how one comparison checks the two fields' arguments. At the base it matched the arguments by name and printed each pair of values. At the head it builds a wrapper object over each field's whole argument list, sorts it and prints it, for every pair, and stores nothing between pairs.

## The runs

Clones of the repository at both commits, Node v24.21.0, on a machine shared with other work. Timings ran one process at a time, base and head alternated in three rounds, and the figures are medians. Probes: `probes/M1/`. Results: `probes/M1/results/`. All *run*.

The probe validates `{ <selection> <selection> ... }`, the selection written N times. Every run returns no errors at both commits.

The query text is 10 kB for 1000 selections of `one(a: 1)` and 20 kB for 2000.

- **Growth.** At both commits time grows with the square of N. The change raises the time for each pair by 3 to 7 microseconds and does not change how the time grows.
- **All default validation rules**, 1000 selections: one scalar argument 1,744 ms and 4,114 ms; two scalars 3,334 and 5,423; nested 13,405 and 16,397.
- **`NODE_ENV=production`**, which the project's README tells production servers to set, 1000 selections: one scalar argument 1,802 ms and 4,217 ms; two scalars 3,628 and 5,450; nested 13,969 and 16,874.
- **Small queries**, microseconds for one validation with all default rules: 2 selections of `one(a: 1)`, 57 and 57; 5 selections, 94 and 144; 10 selections, 235 and 423; 20 selections, 769 and 1,648.
- **Fragments.** A query that spreads N fragments on one object, each selecting `avatar(size: 64) friends(first: 10) { avatar(size: 64) }`, all default rules: 5 fragments, 0.27 ms and 0.49 ms; 20 fragments, 2.7 ms and 5.2 ms; 50 fragments (a 4.4 kB query), 15.6 ms and 34.8 ms.
- **The project's own benchmarks** at the head do not repeat a field (*read*) and show no difference: 0.228 ms and 0.234 ms; 0.660 ms and 0.616 ms.
- **The project's tests.** All 521 validation tests pass at both commits.
- **The added work can be left out.** With the printed text stored per field (eleven added lines on the head), 1000 selections take 68 ms with one scalar argument, 67 ms with two and 73 ms with the nested object, and all 521 tests pass. With the base's comparison put back, the times are the base's.

## What the affected person sees

No error and no changed answer. A validation takes longer, and the process is blocked for that time.

- A document that selects a field with arguments a few times: tens to hundreds of microseconds more.
- A document that reaches one field with arguments through 50 fragments: 15.6 ms before, 34.8 ms after.
- A document that repeats `one(a: 1)` 1000 times (10 kB): 1.85 s before, 4.5 s after. 2000 times (20 kB): 7.0 s before, 18.9 s after.

## Impact facts

- **Who is affected:** the operator of a server that validates documents written by clients, and through it the server's other users while a validation runs.
- **How:** the Node.js process is blocked for longer. Nothing fails and no answer is wrong.
- **How stuck:** graphql-js at the head has no setting that changes this cost and no limit on document size (*read*). An operator can limit request size or query complexity outside the library, or cache validated documents, as before the change. One server package of the time capped a request body at 100 kB, which holds about 10,000 selections of `one(a: 1)` (*read*).
- **How common:** servers pass every new client document to `validate` (*read*, two server packages as they stood before the change). How often documents select one field with arguments many times was not measured.
- **Before the change:** the same documents already took time that grows with the square of the number of selections: 1.85 s for 1000 selections of `one(a: 1)` and 14.5 s for 1000 selections of the nested object.
- **What the project had said:** the comment above `validate` reads "Attackers can send pathologically invalid queries to induce a DoS attack, so by default `maxErrors` set to 100 errors." Three weeks before the change a project member wrote of this rule that its cost "is quadratic in both number of fields in the selection sets, and in the levels of nested fragments. This might be exploited for denial of service attacks" (*read*).
- **Neighbours:** the same selections without arguments. There the base did almost nothing for a pair, and 1000 selections of `hello` go from 61 ms to 2,373 ms.
