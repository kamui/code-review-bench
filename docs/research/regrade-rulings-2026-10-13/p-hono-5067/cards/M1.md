# Card: a form read a second time on one request is parsed again

Pull request: honojs/hono #5067. Hono is a web framework for Node, Bun, Deno and Cloudflare Workers. `c.req.parseBody()` is its documented way to read a form or a file upload. `validator('form', ...)` is its validation middleware. A Hono request remembers a body it has read, so that a second reader does not read it again. "Base" is the commit before the change and "head" the reviewed commit.

## The runs

Hono's own source at both commits, on Node 24.7.0 and Bun 1.3.10. Probes: `probes/M1/`. Results: `probes/M1/results/`. All *run*.

How often the platform's form parser is entered for one request:

| What the application does | Base | Head |
| --- | --- | --- |
| `c.req.parseBody()` once | 1 | 1 |
| `c.req.parseBody()` twice | 1 | 2 |
| `c.req.parseBody()` five times | 1 | 5 |
| `validator('form')`, then `c.req.parseBody()` in the handler | 1 | 2 |
| `validator('form')`, then `c.req.valid('form')` in the handler | 1 | 1 |

The values returned are the same at both commits, with HTTP 200.

Time spent in each further `parseBody()` call, in milliseconds:

| Body | Node, base | Node, head | Bun, base | Bun, head |
| --- | --- | --- | --- | --- |
| urlencoded form, 25 bytes | under 0.001 to 0.001 | 0.006 to 0.010 | 0.001 | 0.003 to 0.004 |
| multipart, 1 MB file | 0.004 to 0.005 | 0.9 | 0.003 to 0.005 | 0.14 to 0.15 |
| multipart, 8 MB file | 0.008 to 0.014 | 4.6 to 6.3 | 0.02 | 5.8 to 6.2 |
| multipart, 100 MB file | 0.03 to 0.04 | 190 to 192 | 0.02 to 0.03 | 102 to 116 |

Whole request on Node, 100 MB upload, in milliseconds: one call 249 at the base and 396 at the head; two calls 208 and 606; five calls 227 and 1,169; validator then `parseBody()` 338 to 369 and 531 to 734. Whole-request times moved with the machine's other load.

Peak memory on Node, 100 MB upload, MiB above the process's baseline, three fresh processes:

| What the application does | Base | Head |
| --- | --- | --- |
| `parseBody()` once | 313 | 445 |
| `parseBody()` twice | 313 | 646 to 713 |
| `parseBody()` five times | 313 to 314 | 1,045 to 1,109 |
| validator, then `parseBody()` | 445 | 545 to 646 |

For an 8 MB upload on Node the peak for two calls is 34 to 35 at the base and 74 to 75 at the head. On Bun further calls add no measurable memory at 8 MB and 100 MB.

One patch of three lines, which returns the remembered form, brings every figure above back to the base's for the further calls, keeps mixed-case media types working on Node and Bun, and passes the project's tests for these files. The rise for a single call, from 313 at the base to 445 at the head, stays under that patch.

No run put the process under a memory limit.

## What the affected person sees

Nothing in the response. The fields and files are right. An operator sees a longer request on the routes that read a form twice and, on Node, more memory per request. Nothing in the output points to the second parse.

## Impact facts

- **Who is affected:** an application that reads a form twice on one request. Five public programs written before the pull request have a route with `validator('form')` or `zValidator('form')` whose handler then calls `c.req.parseBody()`. Three of those routes take a file upload. The project's own tests run that order.
- **How:** each further read costs one more full parse of the body. For a form of a few fields that is 2 to 16 microseconds. For an upload on Node it is about 0.6 to 1.9 milliseconds per megabyte, and the second read of a 100 MB upload adds about two upload sizes to the peak memory.
- **How stuck:** the application can read the form once and pass the result on, or use `c.req.valid('form')` after the validator.
- **How common:** not measured.
- **Neighbours:** on the same request, when the form is edited between the two reads, the second read returns the original values. With one call only, the first read already needs more memory at the head than at the base.
