# Card: an input that is a union of objects gains members no variant has when a middleware follows it

Pull request: trpc/trpc #5017. tRPC is a TypeScript library for typed APIs. Faults here are in types: a developer sees them as a build error or as a wrong type, and nothing wrong runs. "Base" is the commit before the change and "head" the reviewed commit.

A procedure is built in steps: `.input(...)` declares a validator, `.use(...)` adds a middleware, `.query(...)` adds the resolver. The library works out the caller's type (what a call must pass) and the resolver's type (what the resolver receives). The schema in the runs:

```ts
const schema = z.discriminatedUnion('type', [
  z.object({ type: z.literal('a'), x: z.string() }),
  z.object({ type: z.literal('b'), y: z.number() }),
]);
```

## The runs

Small programs were compiled against the library's source at both commits with the project's own TypeScript, 5.1.3, and Zod 3.20.2. Probes: `probes/M1/`. Results: `probes/M1/results/`. All *run*. TypeScript 5.2.2 gives the same results.

The procedure is `t.procedure.input(schema).use((opts) => opts.next())`. "Control" is the same without `.use()`.

At release 10.43.0, published before the reviewed commit, the caller's type is the declared union and the mixed call is refused; the resolver's type already has the four members.

### Where it goes wrong

The pull request rewrites the two checks of one type helper, `Overwrite`, from "any type" to "an object type" and leaves the part that copies the fields of two object types as it was. Both the old and the new checks are applied to each member of a union separately, so with the same union on both sides every variant is merged with every other. Lines of the library the pull request does not touch hand the helper the same input type twice after every `.use()`.

Each variant is the head with one patch (`probes/M1/patches/`). All *run*.

- **`fix-union-pairs`.** Inside the helper, a member of the first type that fits a member of the second is merged only with the members it fits. All rows above that fail at the head compile or are refused as they should be.
- **`fix-same-input`.** Outside the helper: when the procedure's input type already fits the type the middleware reports, it is kept. The same result.
- **Both checks written as non-distributive.** The helper then gives `{ type: "a" | "b"; }` for the union with itself and 19 of the 22 probes report errors.

## What the affected person sees

A server developer who tells the variants apart by field gets a build error in the resolver (`result-head.txt`):

```text
TS2345: Argument of type '{ type: "a"; x: string; } | { type: "b"; x: string; y: number; } | { type: "a"; x: string; y: number; }' is not assignable to parameter of type 'A'.
  Type '{ type: "b"; x: string; y: number; }' is not assignable to type 'A'.
    Types of property 'type' are incompatible.
      Type '"b"' is not assignable to type '"a"'.
```

A server developer with several middlewares after the input gets "TS2589: Type instantiation is excessively deep and possibly infinite." on the procedure. The message names no cause.

A front-end developer sees four members where the schema has two, and a payload that mixes two variants is not flagged at compile time.

## Impact facts

- **Who is affected:** a developer whose procedure takes a union of object types as its whole input, with variants that differ in their field names, and has at least one middleware after `.input()`.
- **How:** a mixed-up payload is not caught at compile time; a resolver that narrows by field does not compile; with enough variants and middlewares the procedure does not compile. Nothing changes at run time.
- **How stuck:** three rewrites compile (*run*): narrow on the tag, or annotate the input with its declared type; move the middlewares before the input; hold the union in a field of an object input. The TS2589 message points to none of them.
- **How common:** not measured. The project's documentation shows a middleware after an object input and shows no union input. No public program with a middleware after a union input was found, and four found with a union input put the middleware first; that search is of code as it stands on 2026-10-13, later than the cut-off, and could not be dated.
- **Compared with before the change:** the same types and the same failures, except that two variants with four middlewares compiled before and do not after.
- **Neighbours:** with a middleware after the input, an array or tuple input, an object input with an optional key, and a branded string input each have a wrong type of their own, the same before and after the change.
