# Card: a listing page filled by names whose records are gone comes back empty or short

Pull request: seaweedfs/seaweedfs #10735. SeaweedFS is a distributed file store; its *filer* keeps file metadata in a pluggable store, here Redis (`redis2`). The store keeps a *record* for each file and the file's *name* in its directory's list. A name whose record is gone, for example after a time-to-live ran out, is a *dead name*. The pull request makes a listing remove dead names from the list. "Base" is the commit before the change and "head" the reviewed commit.

A listing asks Redis for at most `limit` names, once. It skips each dead name and asks for no name in its place. Those lines are older than the pull request and unchanged by it; the pull request adds one line directly above the skip.

## The runs

The real store and filer code of each commit against a real Redis 8.2.1. Nothing raced, nothing injected. Dead names are files stored with a time-to-live that Redis expired; they sort before the live ones. Probes and outputs: `probes/M1/`. All *run*.

Called directly:

| Call | Directory | Base | Head |
| --- | --- | --- | --- |
| store listing, limit 100, repeated from the start | 100 dead, 50 live | 0 entries on every call; the dead names stay | 0 entries on the first call, 50 on the next |
| the same | 250 dead, 5 live | 0 on every call | 0, 0, then 5 |
| filer listing, limit 100 | 101 dead, 50 live | 0 entries, "no more", on every call | 0 and "no more" once, then 50 |
| filer listing, limit 100 | 1 dead, 300 live | 100 entries, "no more", on every call | "no more" once, then "more" |
| the count the S3 empty-folder cleaner uses, limit 1000 | 1001 dead, 5 live | 0 on every call | 0 once, then 5 |
| "is this directory empty?" (a listing with limit 1) | 1 dead, 1 live | yes, on every call | yes once, then no |
| delete of the directory without the recursive flag | 1025 dead, 3 live | succeeds; the 3 live files' records are deleted | the same |

The documented way, end to end: the server on the Redis store, files stored over HTTP with `?ttl=1m` and others without, a wait past the minute, then a listing.

| What is done | Directory | Base | Head |
| --- | --- | --- | --- |
| one gRPC `ListEntries` request, repeated | 1024 expired, 10 live | 0 entries every time | 0 once, then 10 |
| `weed shell` `fs.ls`, repeated | the same | nothing every time | nothing once, then 10 names |
| S3 `ListObjectsV2`, repeated | 1002 expired, 10 live objects | `KeyCount` 0, `IsTruncated` false, every time | that once, then 10 keys |
| HTTP listing with `limit=100`, repeated | 1 expired, 150 live | 100 entries, `ShouldDisplayLoadMore` false, every time | false once, then true |
| HTTP `DELETE` of the directory, no `recursive=true` | 1025 expired, 3 live | 204; a live file answers 200 before and 404 after | the same |

One patch to the store's listing, so that it asks Redis again until it has `limit` entries or the list ends, gives the right answer on the first call in every row of the first table (*run*). The end-to-end steps were not run with the patch.

A helper that deletes a directory it finds empty (`DeleteEmptyParentDirectories`) deletes a directory with live children when called on one whose first name is dead (*run*, both commits). A listing reached that helper only through a file carrying the S3 expiry flag and a modification time earlier than its creation time; through an ordinary expired file it did not (*run*).

## What the affected person sees

At the head, right after a batch of files in one directory has expired, where their names sort before the live ones:

- an S3 listing says the folder holds no objects and that the answer is complete, while 10 live objects are there; the same request made again lists them;
- the shell and a gRPC `ListEntries` request see an empty directory once;
- the HTTP listing returns a full page and says there is no more, while more files exist;
- no error is returned;
- a directory removed without the recursive flag, while 1025 or more dead names sort first, is removed with success, and its live files' records are deleted with it.

At the base the first four happened on every request and never stopped, and the fifth the same way.

## Impact facts

- **Who is affected:** a person or program that lists, or deletes without the recursive flag, a directory of a filer on the Redis store in which files lost their records while their names stayed, and the dead names fill the page the caller asks for.
- **How:** a listing answers "empty" or "that is all" with no error while live files follow. At the head this lasts for one listing per page of dead names; at the base it lasted for good.
- **How stuck:** asking again works at the head. A listing loses nothing. The delete without the recursive flag deletes live files' records, at both commits.
- **How common:** not measured. It takes as many consecutive dead names, in sort order, as the caller's page: 1 for the emptiness check, 1002 for a default S3 listing, 1024 for gRPC, 1025 for the delete; one dead name is enough for the HTTP listing to say "no more" wrongly. No report of it was found before the cut-off. Three public repositories turn this store on; one of them sets a time-to-live on bucket folders.
- **Neighbours:** the documentation says of the listing that the filer will "retrieve the next x files", documents storing files with a time-to-live, and lists this store as supporting it. The fault is the same at the commit before the change, where it never healed. The pull request's stated purpose is to stop dead names piling up, and its description does not speak of what a listing returns.
- **Limits of the evidence:** one standalone Redis; the cluster and sentinel variants, a mount and the S3 empty-folder cleaner end to end were not run.
