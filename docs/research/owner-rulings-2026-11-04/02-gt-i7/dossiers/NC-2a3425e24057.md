# NC-2a3425e24057: an adapter whose `cert_verify` sets `conn.ca_certs` widens every session's trust

requests pull request 6667, base `8dd3b26`, head `4089f3d`, cut-off 2024-05-15T20:07:26Z (the merge). Each fact is marked **run**, **read** or **reported**. Facts after the cut-off are marked *later* and only confirm. `NC-e9470b7251c2` describes the same route; its dossier points here.

## Problem

**run** An `HTTPAdapter` subclass overrides `cert_verify()`: it calls the parent, then sets `conn.ca_certs` to a private CA file when `verify is True`. After one `verify=True` request through it, a plain `Session` and `requests.get()` accept a server whose certificate chains only to that private CA. The shared context's CA count goes from 121 to 122. At the base the adapter still reaches its server, and plain sessions still reject it (round 2 probe, `docs/research/audit-v2-r2-reconciliation-2026-11-04/probes/requests-6667-subclass-conn-ca-certs/output.txt`; urllib3 2.8.0, OpenSSL 3.5.7).

## What changed

**read** At the head, `_urllib3_request_context()` puts the module-level context into the pool's settings for every `verify=True` request (`src/requests/adapters.py` lines 94 to 95):

```python
    elif verify is True:
        pool_kwargs["ssl_context"] = _preloaded_ssl_context
```

At the base no context was passed, so urllib3 built one per pool. urllib3's `ssl_wrap_socket()` calls `context.load_verify_locations(ca_certs, ca_cert_dir, ca_cert_data)` on the context it is given whenever the connection carries CA material. A CA file the subclass sets on the pool is therefore loaded into the one context every `verify=True` pool shares. A context cannot drop a certificate once loaded.

## Promised?

**Promised: yes, written.** The requests guide says: "Requests verifies SSL certificates for HTTPS requests, just like a web browser. By default, SSL verification is enabled, and Requests will throw a SSLError if it's unable to verify the certificate", and "Requests uses certificates from the package `certifi`." `cert_verify()`'s docstring says it "is only exposed for use when subclassing the :class:`HTTPAdapter`". The guide's Transport Adapters section says "you might look at subclassing the HTTPAdapter". At the base, the subclass's CA stayed on its own pools (run), and how a promised use behaved before is part of its promise (rule promised-7a). Searches: `summary.json`, `upstream/`.

## Delivered?

**Delivered: no.** A plain `Session` and `requests.get()` with `verify=True` should reject a server that chains only to a CA they were never given. After the adapter is used once, they accept it (run).

## Intended or announced

**read** The change's purpose is speed: "Avoid reloading root certificates to improve concurrent performance". Its author wrote: "I'm not sure that setting `conn.ca_certs` ... in `cert_verify()` is even still needed". Nothing says CA material set by a subclass may now reach other sessions. *Later* (**read**): requests 2.32.5 (2025-08-18) reverted the shared context; GT-i7's entry records that 2.31.0 and 2.32.5 behave as the base.

## What the affected person sees

Nothing fails. After one request through such an adapter, every `verify=True` request in the process, from any `Session` or from `requests.get()`, trusts the adapter's private CA until the process exits (run). A server holding a certificate from that CA is accepted where it was rejected before.

## What the maintainers did

**read** Before the cut-off, the author's review comment gives the goal "to avoid setting `ca_certs` or `ca_cert_dir` in the most common use case as it triggers another ... call to `load_verify_locations()` by urllib3". No maintainer statement about subclasses that set CA material was found (`upstream/maintainers-search.txt`). *Later*, issues 6726 and 7040 discuss `cert_verify` and `ca_certs` on custom adapters, and none addresses this leak. The 2.32.5 revert removed it.

## Relation to existing reference families and ruled claims

GT-i7: "CA material an adapter sets on its own pools through init_poolmanager is loaded into the process-wide SSLContext and trusted by every later verified connection". Ruled a known problem in first-round ruling 32 of 2026-10-05 (`CL-i-adapter-ca-shared`). Ground rule 4's three tests, against GT-i7 (see `grouping-tests.md` for the full reasoning):

1. **The same lines cause both: yes, with a caveat.** Both leak because lines 94 to 95 hand the shared context to the pool. GT-i7's route also needs a second changed line, `cert_verify()` no longer overwriting `ca_certs` with the default bundle; this route does not.
2. **One fix cures both: yes (run).** One context per `verify=True` pool stops both. A fix aimed at GT-i7's own trigger leaves this route leaking, which is not the test.
3. **One cause sentence is true of both: yes.** "CA material an adapter attaches to its own pools is loaded into the context every verify=True pool shares."

It is apart from GT-i4 (a client certificate, `load_cert_chain`), GT-i3 (connections that never get the shared context) and GT-i1 (the adapter's own setting lost), for the reasons GT-i7's entry gives.

## Both sides

- **For joining it to GT-i7.** The three tests hold. The leak, the call and the result are GT-i7's. The `cert_verify` hook is documented for subclassing, so this is another documented route to the same fault.
- **Against.** GT-i7's wording names `init_poolmanager` only. At the base GT-i7's route did nothing, since `cert_verify()` overwrote it, while this route worked privately; so the two break different things a developer did. Ground rule 4's kept-separate example (tRPC) kept two inputs to one block apart. There, though, each smallest fix cured only its own case; here the smallest fix for this route, one context per pool, cures both. On 2026-11-04 the owner chose to widen GT-i7 (round 2 reconciliation, audit call 5 and question 31).

## Recommendation

> **What happens:** an adapter whose `cert_verify` sets `conn.ca_certs` for `verify=True` makes every other session trust its private CA. **Promised: yes**, the requests guide's default `verify=True` trust in certifi's bundle and `cert_verify`'s documented use when subclassing. **Delivered: no**, plain sessions accept the private-CA server after one adapter request. **So: duplicate of GT-i7**, by ground rule 4's three tests; GT-i7's wording widens to name the `cert_verify` route. **Band, decided separately:** none; GT-i7 keeps its label.
