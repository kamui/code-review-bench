# Local sandbox alternatives

Research date: 2026-10-05. This is a documentation and source review, not a sandbox execution test or benchmark. Read `AGENTS.md` and `docs/clean-context.md` before research. No provider calls or software installation occurred.

## Recommendation

Keep rootless Podman as the first implementation for issue #35. Its explicit filesystem, process and network namespaces fit private clones and fresh homes, and it provides the same Linux userspace on Linux and macOS through Podman Machine. Treat Podman as the confinement mechanism, not a credential broker. The required broker and its caller restrictions remain separate implementation work. A shared macOS VM gives a host-to-VM boundary, not a separate VM boundary between concurrent attempts. [Podman run](https://docs.podman.io/en/latest/markdown/podman-run.1.html), [Podman Machine](https://docs.podman.io/en/latest/markdown/podman-machine.1.html).

The strongest lighter alternative to investigate is Anthropic sandbox-runtime with an explicit policy and a separate broker admission design. Current source already masks credentials and substitutes them in a host TLS proxy, but shell descendants can use that proxy too. Vetto's shipped agent profiles pass real provider keys into the sandbox and expose client state. Docker Sandboxes has a useful microVM and credential-proxy design, but is proprietary. Consider gVisor as optional stronger isolation after compatibility checks. These are design judgments, not measured rankings.

Honor an explicit `none` mode. A missing sandbox prerequisite should fail the requested sandbox mode, with `none` available only when the user selects it. Record that choice in evidence. Apply confinement before executing repository setup commands, dependency scripts or the native client; wrapping only the review process leaves earlier repository execution outside the boundary.

## What the source establishes

Vetto v0.6.0 resolves to `be19bad1e273863b4312364573c6839fa2c266b3`, dated October 4. Also inspected current main `a2838176a6d227f2752ace86d1b6270fcb6371ed`, dated October 5; the Claude and Codex profile files are unchanged. The default Linux profile permits selected toolchains, caches, `.local/share`, `.gitconfig` and runtime paths, not the entire home. Selecting an agent adds its state roots and passes `ANTHROPIC_API_KEY` or `OPENAI_API_KEY`. The loader deliberately skips a deny exactly matching that agent's root. That exposes auth material placed there to ordinary descendants. The prior home-exposure criticism needs this Linux/macOS distinction. [Default profile](https://github.com/shleder/vetto/blob/be19bad1e273863b4312364573c6839fa2c266b3/profiles/default.toml), [loader](https://github.com/shleder/vetto/blob/be19bad1e273863b4312364573c6839fa2c266b3/src/policy/loader/resolve.rs#L149), [current Claude profile](https://github.com/shleder/vetto/blob/a2838176a6d227f2752ace86d1b6270fcb6371ed/profiles/agents/claude.toml).

Inspected sandbox-runtime main `232db177034e986bc771b5551c05acc4641e70a9`, dated October 5. Credentials are affected only when declared in configuration. Masking requires TLS termination unless plaintext injection is explicitly enabled. Set each credential's `injectHosts` narrowly; omission defaults to all allowed domains. The sentinel registry stores real values in host process memory. Linux gives sandbox processes proxy URLs containing a session auth token. This protects raw key values but gives descendants the proxy capability. An allowed provider request from `curl` can still consume credentials and budget. Client-only admission needs an independently enforced process boundary, and a broker should also bound request methods, paths, concurrency and budget. API-key masking does not prove OAuth refresh or subscription compatibility. [Schema](https://github.com/anthropics/sandbox-runtime/blob/232db177034e986bc771b5551c05acc4641e70a9/src/sandbox/sandbox-config.ts#L447), [registry and proxy setup](https://github.com/anthropics/sandbox-runtime/blob/232db177034e986bc771b5551c05acc4641e70a9/src/sandbox/sandbox-manager.ts#L204), [Linux proxy token](https://github.com/anthropics/sandbox-runtime/blob/232db177034e986bc771b5551c05acc4641e70a9/src/sandbox/linux-sandbox-utils.ts#L54).

## Performance and admission limits

No comparable local-agent performance evidence was found. Vetto's README compares container creation with its own interval between `fork` and `execve`, and compares against a rootful Docker privilege model. That does not describe rootless Podman. Its separate full-session benchmark executes `vetto --tui=none -- /bin/true`; the committed v0.6.0 baseline reports only an `fs-only` median of 184.267 ms and p95 of 185 ms. That number has no comparable Podman sample or recorded machine context in the JSON and is not a new measurement here. [README comparison](https://github.com/shleder/vetto/blob/v0.6.0/README.md#comparison-with-docker), [benchmark code](https://github.com/shleder/vetto/blob/v0.6.0/benches/e2e_spawn.rs), [baseline](https://github.com/shleder/vetto/blob/v0.6.0/benches/baseline/perf-baseline.json).

gVisor's performance guide explains syscall/filesystem overhead, but much of its published data uses old Debian 9 machines and the slower ptrace platform. Firecracker boot specifications measure VM behavior, not a ready native-agent session. A fair comparison needs identical admitted isolation policy, credentials, private home/clone, toolchain, warmed caches, concurrency and workload; report initial installation/image setup, cold host/VM start, warm attempt startup, complete review time, peak memory and cleanup separately. [gVisor methodology](https://gvisor.dev/docs/architecture_guide/performance/), [Firecracker specifications](https://github.com/firecracker-microvm/firecracker/blob/main/SPECIFICATION.md).

Before admitting any backend, test provisioning and review descendants against sibling clones, orchestration records, host homes, raw credential files/environment/process memory, broker endpoints, direct IP/DNS/IPv6 egress, local sockets and cancellation cleanup. Test successful native authentication as well. This source review establishes mechanisms and conflicting defaults; it does not prove an integrated backend meets #35.
