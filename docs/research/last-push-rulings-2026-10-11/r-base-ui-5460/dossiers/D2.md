# D2: the description at the last push says the change does not clear a server error on a value set from code, and the head does

Pull request: mui/base-ui #5460, "[field] Sync controlled value changes with field state".
Candidates covered: none from the first rounds. This group was added in this round; see `D1.md`, "Grouping", for why D is split in three and for the case that the three are one fault.

Every fact is marked as knowable at the last push or later.

Words used here. `Field.Control` is Base UI's text input for a form field. It is "controlled" when the app passes the text in through the `value` prop. A "server error" is an error the app hands the `Form` through its `errors` prop. "A value set from code" is a change of the `value` prop that no keystroke caused, such as a reset. "Base" is the commit before the change. "Head" is the reviewed commit, `14d39e5`. The "earlier revision" is `6a40cf1`, the first commit pushed to the pull request, which the last push replaced. "The description at the last push" is the pull request body as written at 2026-08-10T13:16:20Z.

## Problem

The description at the last push ends with:

> ## Open question
>
> The sibling controls also call `clearErrors(name)` when their value changes. This PR does not, so a programmatic change clears a server error on a Switch but not on an Input. I can align it either way.

The head does call `clearErrors(name)` when the value changes. At the head a value set from code clears a server error on an Input, as on a Switch. The question the description asks a reviewer is already answered by the code, the other way from what the description says.

## What changed

The head's new block (`FieldControl.tsx`, lines 105 to 115) starts with the call the description says is absent:

```diff
+  useValueChanged(serializedValue, () => {
+    if (serializedValue === undefined) {
+      return;
+    }
+
+    clearErrors(name);
+    setDirty(serializedValue !== (validityData.initialValue ?? ''));
+    setFilled(serializedValue !== '');
+
+    validation.change(serializedValue);
+  });
```

The earlier revision's block, which the description was written for, did not have it (read, `upstream/FieldControl-6a40cf1.tsx`, lines 112 to 123):

```ts
  useValueChanged(serializedValue, () => {
    const processedValue = processedValueRef.current;
    processedValueRef.current = undefined;
    if (serializedValue === undefined || serializedValue === processedValue) {
      return;
    }

    setDirty(serializedValue !== (validityData.initialValue ?? ''));
    if (!disabled) {
      validation.change(serializedValue);
    }
  });
```

**Runs** (`probes/D2/probe.test.tsx`; a controlled `Field.Control` and a `Switch` in a `Form`, each showing "Server error"; default mode and `validationMode="onChange"` gave the same results; jsdom and real Chromium agree at every commit).

| What the app's code does | Base | Earlier revision | Head |
| --- | --- | --- | --- |
| Sets the input to the value it already has | error stays | error stays | error stays |
| Sets the input to a new value | error stays | error stays | **error clears** |
| Sets the switch | error clears | error clears | error clears |
| Stores a server error and a new value in the same update | error shows on both | error shows on both | error shows on both |

So the sentence is true of the base and of the earlier revision, and untrue of the head.

## Promised?

**The exact operation.** A server error on a controlled `Field.Control` being cleared when the app changes the value from code. The `Form`, its `errors` prop and the clearing are all Base UI's.

**How the owners classify it.** The `errors` prop is public and documented, and when an error clears is stated.

**The six places searched.** Every one is knowable at the last push unless marked.

1. **Project documentation at the head** (`upstream/d2-project-docs-search.txt`; two searches, 24 hits, all read). The forms handbook: "Once a field's value changes, any corresponding error in `errors` will be cleared from the field state." It does not separate a value typed from a value set from code.
2. **The owning dependency's documentation.** Not applicable. No dependency owns the clearing of a Base UI form error.
3. **The change itself** (`upstream/pr-5460-usercontentedits.json`, `upstream/pr-5460.diff`).
   - The description at the last push has the passage quoted under "Problem".
   - In the same description, of the bug the change fixes: "Setting the value from code, such as a clear button or a form library reset, updated the input text but not filled, dirty, or validity, so a resolved error stayed visible".
   - The diff adds `clearErrors(name)` in the new block. No code comment explains it, and no added test involves a server error.
4. **Maintainers up to the last push** (`upstream/n3-maintainers-read.json` and `.txt`, the searches run for N3 in this round on the same subject; seven searches limited to `created:<2026-08-10T13:33:57Z`; 29 distinct hits, 26 read, the 3 unread are dependency updates opened by a bot).
   - Issue #2758 (2025-11-07): "external `errors` are always cleared on change as they cannot be revalidated internally by `<Form>`".
   - #3136 (2025-11-05): "it's a better UX to optimistically clear external (server) errors on change", after React Aria's rule that errors are "cleared after the user modifies each field's value".
   - #5446, merged 2026-08-10T06:59:12Z, seven hours before the push: its automated review counted "all 13 `clearErrors` call sites (all in event handlers or `useValueChanged`", which agrees with the description's "The sibling controls also call `clearErrors(name)` when their value changes."

5. **Public code** (`upstream/n3-public-code.json`, the searches run for N3: 193 files over two rounds; this round read 28 of them, and the other 165 were screened by the earlier round's script). Three programs pass `errors` to a `Form` and control a text field. None is shown setting the field's value from code while a server error shows, so none is shown depending on the error staying or on it clearing.
6. **The documented way to do the same thing, run at the head** (`probes/D2/result-head.txt`). The documentation's way to clear a server error is to change the field's value. At the head that works for a value set from code as well as for a typed one. At the base it worked for a typed value only.

**What the code and the project's tests deliberately support.** `Form.test.tsx` has "removes errors upon change" and "removes errors for every field that changes within a single commit"; both change values by a person's action. No test at either commit sets a `Field.Control` value from code under a server error (read).

**Whether it worked before, and whose behaviour changed.** Before the change a value set from code left the error (run). Base UI's behaviour changed, towards what the documentation says.

**Which of the three ways.**

- Written: the documentation promises that the error clears once the field's value changes.
- Announced: the description at the last push says the opposite for a value set from code, as a statement of what the change does not do, and leaves the choice open.
- Built: the sibling controls clear on a value set from code (run, the switch row).

So two statements a reviewer could read at the cut-off disagree. The documentation says the error clears. The description says this change does not make it clear. The head does what the documentation says. I propose **yes**, written, and note that rule Promised 5 says a conflict between what a change says and what the documentation says is the owner's.

## Delivered?

Yes, for the documentation's promise: at the head a server error clears once the field's value changes, from a keystroke or from code (run).

What is wrong is the sentence. A reader of the description is told the change does not do this and is asked to choose. The code has already chosen.

## Recommendation

> **What happens:** the description a reviewer could read at the last push says "This PR does not" call `clearErrors(name)` when the value changes, "so a programmatic change clears a server error on a Switch but not on an Input", and the head calls it, so a value set from code does clear the error on an Input. **Promised: yes**, written: "Once a field's value changes, any corresponding error in `errors` will be cleared from the field state" (forms handbook at the head). **Delivered: yes**, at the head the error clears on a value set from code as on a typed one (run); what is wrong is that the description says the opposite and asks a question the code has already answered. **So: minor defect.** **Band, decided separately:** none.

Recommendation code: `minor-defect`. Confidence: low.

**Where the rules do not decide.**

- **A stale description.** As in D1: the rules do not say what a description written for a replaced revision announces at the cut-off.
- **A statement of what a change does not do.** Rule Promised 5 covers "this now does X" and "this no longer does Y". It does not cover "this does not do Z, and I can go either way". If it is read as the change saying the old behaviour stays, it conflicts with the documentation, and the rule says that conflict is the owner's.
- **Whether an untrue sentence in a pull request description is "something in fact wrong".** The minor defects so far are an error line, a stale name and two untrue wordings of a promise in the code or its documentation. None is a sentence in a description.
- **Grouping.** With D1 and D3 this passes the three tests of Before 4 as one fault. As part of one known problem it would be a symptom, not a separate entry.

**Strongest argument against the recommendation.** It could be more or less than a minor defect. More: the passage denies a behaviour change, server errors clearing on any value the app sets from code, in the only statement of intent a reviewer had, so a reviewer could not review that change from the description. Less: nothing a person using the software sees is wrong, the description named this outcome as acceptable, and a sentence that stayed for 24 seconds after the push, in a text nobody ships, is an observation.
