# B4: the validator gets the app's stored value, not the text the input holds

Pull request: mui/base-ui #5460, "[field] Sync controlled value changes with field state".
Candidate covered: NC-f98f0d0ed5b4.

This dossier prepares the saved ruling on B4 again with the cut-off at the last push. It is a full dossier. Every fact is marked as knowable at the last push or later.

Words used here. `Field.Control` is Base UI's text input for a form field. It is "controlled" when the app passes the text in through the `value` prop and stores each edit itself. The "validator" is the app's `validate` function on `Field.Root`. "Base" is the commit before the change. "Head" is the reviewed commit, `14d39e5`. The "earlier revision" is `6a40cf1`, the first commit pushed to the pull request, which the last push replaced.

**Grouping.** One thing, and the grouping is right. It shares a root with GT-r4, the text form of the `value` prop becoming the field's value, but GT-r4 is about a number or an array turned into text at submit. This is about the app's text differing from what the browser keeps.

**The times that matter** (read, `upstream/pr-5460-usercontentedits.json`, `upstream/pr-5460-timeline.json`): the first description is of 2026-08-10T13:16:20Z; the last push, the cut-off, is 2026-08-10T13:33:57Z; the author rewrote the description at 13:34:21Z, 24 seconds later; the pull request was marked ready and merged on 2026-08-13.

## Problem

Browsers tidy some values when they are put into an input. A text input drops line breaks. A range input keeps its value between its minimum and maximum.

After this change a controlled `Field.Control` validates the text form of the `value` prop. If the app stores a value the browser tidies, the validator receives the app's version, while the input, and the form values handed to the same validator call, hold the browser's version.

## What changed

```diff
+  // The DOM value is always a string, so dirty comparisons must serialize the controlled value.
+  const serializedValue = value == null ? undefined : String(value);
 ...
+  useValueChanged(serializedValue, () => {
 ...
+    setFilled(serializedValue !== '');
+
+    validation.change(serializedValue);
+  });
```

and, for controlled fields, the change handler no longer validates the text read from the input (head, `FieldControl.tsx` lines 142 to 146 and 155):

```diff
+          // Controlled values sync from the `value` prop instead, so that a value the consumer
+          // rejects or rewrites never reaches the field state.
+          if (isControlled) {
+            return;
+          }
 ...
             validation.change(inputValue);
```

In plain words: before, an edit was validated with `event.currentTarget.value`, the text the input held, and a value set from code was not validated at all. After, both are validated with the text of the `value` prop.

**Runs** (`probes/B4/probe.test.tsx`; a controlled field in a `Form` with `validationMode="onChange"`). jsdom and real Chromium gave identical lines at every commit. The base and head lines are identical to the ones the first preparation saved.

| Case | Base | Earlier revision | Head |
| --- | --- | --- | --- |
| Text input, code sets `"a\n"`; the input holds `"a"` | validator not called | called with `"a\n"`, form value `"a"` | called with `"a\n"`, form value `"a"` |
| Text input, code sets `"\n"`; the input is empty | not called; the field is already marked filled | called with `"\n"`, form value `""` | called with `"\n"`, form value `""`; marked filled and dirty |
| The person types "a" and the app rewrites it to `"a\n"`; the input holds `"a"` | called with `"a"` | called twice: `"a"`, then `"a\n"` | **called once with `"a\n"`** |
| Range input 0 to 100, code sets `"200"`; the input holds `"100"` | not called | called with `"200"`, form value `"100"` | called with `"200"`, form value `"100"` |
| Text input, code sets `"abc"` (nothing to tidy) | not called | called with `"abc"`, form value `"abc"` | called with `"abc"`, form value `"abc"` |

No run produced a wrong verdict, a blocked submit or a lost value. The runs establish the differing argument only.

## Promised?

**The exact operation.** The text a custom `validate` function receives for a controlled `Field.Control` when the app's stored value differs from what the input can hold. The `validate` argument belongs to Base UI. The tidying belongs to the browser.

**How the owners classify it.** `validate` is public. Which text it receives in this situation is unstated: the documented type is `(value: unknown, formValues: Form.Values)`.

**What the code and the project's tests deliberately support.** The added test checks that a value set from code is validated with the prop's text. No test at either commit passes a value the browser rewrites (read).

**Whether it worked before, and whose behaviour changed.** For values set from code there is no earlier behaviour: they were not validated (run). For an edit the app rewrites, the validator received the input's text before and receives the app's text after (run). Base UI's behaviour changed.

**Which of the three ways.** None was found for the validator receiving the input's text.

- Written: nothing names which text the validator receives.
- Announced: the change says the opposite for a rewritten value, in a code comment, and says it registers "the serialized value".
- Built: no test covers a rewritten value; the added test expects the prop's text.

For the one row with an earlier behaviour, the typed edit the app rewrites, rule Promised 7a could keep the earlier behaviour alive as part of a supported use. The code comment names that case: a value the app rewrites "never reaches the field state". Rule Promised 2a says a change that says so ends the old behaviour, and 2c lists code comments among the places it can say so. So the answer proposed is **no**.

## What the affected person sees

The person affected is an app's developer whose stored value differs from what the input can hold. Their validator may approve or reject text that is not the text on screen or in the form values. For example it can approve `"200"` while the form holds `"100"`. No end user is blocked by this alone, and no run showed a wrong verdict. The app controls the value and can store one the input can hold.

What is new with the change: values set from code are validated at all, and an edit the app rewrites is validated with the app's text and not the input's. What is older: a line-break-only value already marked the field filled at the base.

## Both sides

For a problem or a minor defect:

- The validator and the form values handed to it in the same call disagree about the same field (run).
- For an edit the app rewrites, the validator used to receive what the input held and now receives something else, and the description a reviewer could read at the last push describes a design in which it still would.
- A validator can approve a value the form then submits in another form.

For a suggestion:

- No contract names which text the validator receives.
- The change says, in a code comment and a test, that a controlled field follows the `value` prop, and says in its description that it registers the serialized value.
- The trigger is an app storing a value its own input type cannot hold.
- For values set from code there is no earlier behaviour to lose.
- No wrong verdict, blocked submit or lost value was produced in any run, and nobody is shown depending on it.

## Recommendation

> **What happens:** a controlled `Field.Control` now hands the validator the app's stored text even when the browser shows a tidied one, so the validator's argument and the form value can differ; before, an edit was validated with the input's text and a value set from code was not validated. **Promised: no**, no documentation names which text the validator receives, the change says in a code comment that a value the app rejects or rewrites "never reaches the field state" and in its description that the control "now registers the serialized value", its added test expects the prop's text, and the maintainers before the push and public code are silent. **Delivered: not asked**, and storing a value the input can hold gives one text everywhere at the head. **So: suggestion or observation (improvement).** **Band, decided separately:** none.

Recommendation code: `suggestion`. Confidence: medium. This is the saved outcome; the recommendation does not change it.

**Where the rules do not decide.**

- The description at the last push does not match the head on which path validates a typed keystroke. It describes the change handler still doing it, which is the base's behaviour for the typed-edit row. The rules do not say what a description that no longer matches the code announces or promises, or which of a description and a code comment governs when they differ.
- The saved line, and the first example under rule Promised 2a, rest on this ruling. The example says "the Base UI change says a controlled field now validates the value the app stores". At the last push the change says so in a code comment and a test, not in its description.

**Strongest argument against the recommendation.** For an edit the app rewrites, the validator's argument did change, and at the last push the only prose a reviewer had about typed keystrokes said the change handler still handled them. Read that way the old behaviour belongs to a supported use (Promised 7a), a code comment about "field state" does not plainly name the validator's argument (Promised 2b), and the validator now disagrees with the form values it is handed, which is something in fact wrong.
