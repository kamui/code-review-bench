## Problem

The cleanup's first command removes a name from the directory's list. If that command reports an error, the cleanup returns at once. It does not ask whether the value exists and does not add the name back. That is safe only when an error means nothing was removed. It is not safe when Redis ran the command and only the reply was lost. If the file had just been created again, it is left with a value and no name in the list, as in S1.

Grouping, checked again:

- **S2 is the same fault as S1**, at the first line of the helper instead of the last. The three tests of rule Before 4 are applied in `S1.md`: the same 15-line helper, one fix, and one sentence about the cause that is true of both. All three candidates under S2 describe both lines. Grouping is the owner's to decide.
- **What S2 adds by itself is narrow.** The runs show how narrow. See "What the affected person sees".
- **It is not a milder effect of GT-s1, GT-s2, GT-s4 or GT-s5.** See "Relation" below.

## What changed

The added helper (`weed/filer/redis2/universal_redis_store.go`, head lines 237 to 240). This is the diff, so it is knowable at the last push.

```go
+func (store *UniversalRedis2Store) removeOrphanedDirectoryListMember(ctx context.Context, dirListKey string, path util.FullPath, fileName string) {
+	if err := store.Client.ZRem(ctx, dirListKey, fileName).Err(); err != nil {
+		return
+	}
```

Mechanism:

1. A listing finds name `f` in the list, and Redis says `f` has no value.
2. Another request creates `f` again. Its "add the name if absent" does nothing, because the old name is still there.
3. The listing sends the removal (`ZRem`). Redis runs it. The reply does not reach the client, so the client reports an error.
4. The helper returns. It does not ask whether the value exists and does not add the name back.

Before the change there was no removal on this branch (run at the base, every scenario).

### The platform and its settings

The trigger that is a setting here is `max_retries = -1`.

- **How the platform treats it.** With retries off, go-redis hands the caller the error of a single lost reply (`EOF`) although Redis ran the command (run, scenario B2). With the default three retries it sends the removal again on a new connection, gets "0 removed" without an error, and the helper goes on and puts the name back (run, scenario B).
- **A comparable.** The same store before the change, and the sibling `redis` and `redis3` stores at the head, issue no removal on this branch (read). The base keeps the name with retries off (run, scenario B2 at the base).
- **How common.** Not known. No public configuration that sets it was found (two code searches, 0 hits). It is documented, and it is not the default.

The other real trigger, Redis going silent, is not a setting.

## What the affected person sees

The same as S1: the file exists, is missing from every later listing, is not brought back by an overwrite, is skipped by a recursive delete, and comes back only after a delete and re-create by exact path. No error and no log line (run, scenario A, "aftermath" lines). Knowable at the last push, and run again in this round.

When it can happen. The runs separate these cases, all with the re-create in the gap:

| Case | Result at the head | How produced |
| --- | --- | --- |
| A. The client is handed an error after Redis ran the removal | name lost | error injected inside the client |
| B. The reply is really lost once: the connection is cut after Redis ran the removal; Redis stays reachable; default client settings | **name kept**. The client retries the removal on a new connection, gets "0 removed" without an error, goes on, and puts the name back | real: a TCP relay drops one reply |
| B2. The same single lost reply with retries switched off (`max_retries = -1`, a documented store setting) | name lost. The removal reports `EOF` | real |
| C. Redis keeps running commands and stops answering from the removal on | name lost. The removal reports "i/o timeout" | real: the relay withholds replies; read timeout 150 ms |
| D. The listing's deadline passes while the removal's reply is on its way (store called directly) | The removal does **not** report an error: the client ignores the deadline for a command already in flight. The two following commands are then refused, and the name is lost by the S1 route | real: the relay delays the reply past the deadline |

What this means:

- With default settings, one lost reply is repaired by the client's own retry (B). This line matters by itself only when retries are switched off (B2), or when Redis stops answering for long enough that the removal gives up (C).
- In case C Redis was not answering at all, so the two later commands would have met the same silence had the helper gone on. That is reasoned from the run, not run. So for a lasting outage S2 and S1 are the same event: fixing only one of the two lines would not save the name.
- A cancelled or expired context cannot produce "ran on Redis and reported as failed" with the client's default options (D). Through the filer the context is detached anyway (`S1.md`, scenarios F and F2).

At the base the name is kept in every case (run).

Not known: how long Redis must stay silent for case C with the default 3 second read timeout. The run used 150 ms, and the removal gave up after about 0.3 s. How often any of this coincides with a re-create in the gap was not measured.

## Recommendation

> **What happens:** on a `redis2` filer, when Redis runs the cleanup's removal and the client reports an error for it, the cleanup returns without putting back the name of a file created again a moment earlier, and the file is left out of every later listing with no error and no log. **Promised: yes**, written and built, by the same sources as S1: the wiki's "The Filer Store persists all file metadata and directory information", the documented `max_retries` setting, the name kept in the same sequence before the change (run), and the change's own test that a re-created entry "still lists"; all knowable at the last push. **Delivered: no**, the create and the listing report success and the file is missing from its directory. **So: problem**, as the second site of S1's fault and not as a separate problem. **Band, decided separately:** serious with S1, S2 and S4 of the boundary; taken alone the reach is smaller, which limits the label and is not a reason to lower it.

It is the same outcome as the saved ruling. **The saved ruling stands at the last push** for this line as part of the S1 problem. Confidence: medium for "the same problem as S1". If S1 were ruled a suggestion, this should follow it.

**Strongest argument against.** Taken alone, this line matters only with a non-default setting that nobody is shown using, or during an outage long enough that the rest of the helper fails anyway. The one sentence that said in words what the line assumes was written after the push. On that reading it is a suggestion to harden the cleanup.
