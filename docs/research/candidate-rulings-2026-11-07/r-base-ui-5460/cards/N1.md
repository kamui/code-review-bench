# Card: a controlled Base UI field renders once more on the first keystroke into an empty field

Pull request: mui/base-ui #5460. Base UI is a React component library. `Field.Control` is its text input inside `Field.Root`, which holds the field's state. A "controlled" control gets its text from the app's `value` prop, and the app stores each edit itself. The field marks itself dirty when its value differs from the starting value, and filled when it is not empty. A "render" is one run of a component's code by React. "Base" is the commit before the change and "head" the reviewed commit.

## The runs

Renders of the control per keystroke, counted with a `render` prop on the control. The project's source was rendered with React 19.2.5 in development mode in jsdom. The app stores each edit at once with `useState`, and the field starts empty. Probes: `probes/N1/`. All *run*.

| Case | First keystroke, base | First keystroke, head | Next two keystrokes, base | Next two keystrokes, head |
| --- | --- | --- | --- | --- |
| Default validation mode, no validator | 1 | 2 | 1, 1 | 1, 1 |
| Default mode with a validator, before any submit | 1 | 2 | 1, 1 | 1, 1 |
| `onBlur` mode, before any blur | 1 | 2 | 1, 1 | 1, 1 |
| `onChange` mode, validator accepts | 1 | 2 | 1, 1 | 2, 2 |
| `onChange` mode, validator rejects | 2 | 3 | 1, 1 | 2, 2 |
| Field marked invalid by the app | 1 | 2 | 1, 1 | 2, 2 |
| Default mode after a submit attempt | 1 | 2 | 1, 1 | 2, 2 |
| Uncontrolled control, default mode | 1 | 1 | 0, 0 | 0, 0 |

- The dirty, filled and invalid marks and the validator's calls are the same at both commits.
- An earlier run in the project's own test setup, in jsdom and in Chromium, gave the same counts. It also showed one more render at the head on clearing the field and on typing away from or back to the starting text.
- Why (*read*): the change moved the controlled field's dirty and filled updates from the change handler into a block that runs in a layout effect after the app's render. React processes state updates from a layout effect before the browser paints, with one more render.
- A patch that sets dirty and filled in the change handler for a controlled keystroke removes the extra first-keystroke render in the modes that do not validate on change. In the modes that validate on change, the first keystroke's extra render goes only when validation also moves to the handler. With the dirty-and-filled patch alone, a keystroke the app refuses turns dirty and filled on while the input stays empty. That is how the base behaved.

Not measured: the time of the extra render; a production build of React; other browsers.

## What the affected person sees

- A person typing sees nothing different: the same text, marks and validation. The second render happens before the screen updates.
- An app developer who counts renders sees the field render twice on the first keystroke into an empty field, where it rendered once.

## Impact facts

- **Who is affected:** apps that use a controlled `Field.Control`, a documented use, in any validation mode.
- **How:** one more render of the field on the first keystroke into an empty field, and on the few other keystrokes that turn dirty or filled on or off. No value, mark, message or validation result differs.
- **How stuck:** not stuck. Nothing needs working around.
- **How common:** every controlled `Field.Control` that starts empty, once per editing session for the first keystroke. Most keystrokes are not affected in the modes that do not validate on change.
- **Neighbours:** a known problem of the same pull request has the same field render twice on every keystroke while it validates on change. Both come from the same block run after the render.
