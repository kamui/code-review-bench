## Problem

**run** With `OPTIONS["pool"] = True` and the default `CONN_HEALTH_CHECKS = False`, a request after a server restart or a dropped connection gets a pooled session that the server has already ended. Its first query fails with `OperationalError`. With the default pool of four sessions, the next four requests fail one after another, and then the pool has replaced all four sessions and requests succeed. Without the pool and with the default `CONN_MAX_AGE = 0`, no request fails, because each request opens a new session.

## What changed

**Background (read).** Django opens a database connection at the first query of a request. At the start and end of each request it calls `close_if_unusable_or_obsolete()` on every connection (`django/db/backends/base/base.py` head lines 591 to 616). With `CONN_MAX_AGE = 0`, the default, the connection is closed at the end of each request, so the next request opens a new one. With `CONN_MAX_AGE` above 0 ("persistent connections"), the connection is kept across requests. `CONN_HEALTH_CHECKS = True` makes Django test a kept connection once per request before using it (`close_if_health_check_failed()`, head lines 578 to 589).

**The change (read).** It adds `OPTIONS["pool"]`. The pool requires `CONN_MAX_AGE = 0` (head lines 208 to 211 raise otherwise). Closing the connection then hands the session back to the pool with `putconn()` instead of ending it (head lines 385 to 399), and the next request takes a session from the pool with `getconn()` (head lines 345 to 348). So sessions live across requests, as with persistent connections. The pool is built here (`django/db/backends/postgresql/base.py` head lines 228 to 234):

```python
            enable_checks = self.settings_dict["CONN_HEALTH_CHECKS"]
            pool = ConnectionPool(
                kwargs=connect_kwargs,
                open=False,  # Do not open the pool during startup.
                configure=self._configure_connection,
                check=ConnectionPool.check_connection if enable_checks else None,
                **pool_options,
            )
```

Line 232 gives the pool a check only when `CONN_HEALTH_CHECKS` is on. The change also makes Django's own per-request check do nothing for pools (head lines 501 to 505, discussed in N1b).

**Whose code decides (read, psycopg-pool 3.2.1 source, `upstream/owner-psycopg-pool-3.2.1-pool.py`).** `getconn()` takes the next idle session and calls `_check_connection()`, which returns at once when no `check` was given (lines 286 to 293). Nothing else tests the session on checkout. The pool notices a broken session only when it is handed back: `_return_connection()` discards a session whose transaction status is `UNKNOWN` and asks a worker for a new one, logging "discarding closed connection" (lines 676 to 696). `max_lifetime` (default one hour) is applied on return and in `check()`, not on checkout (lines 514 and 697). `max_idle` (default ten minutes) only closes sessions above `min_size` (lines 778 to 800). `min_size` defaults to 4.

**Step by step, at the head with health checks off (run).** A request takes session A, queries, and hands it back. The server ends every session. The next request calls `getconn()`; the pool hands it session A with no test; Django runs `SELECT 1`; libpq reads the server's goodbye or end of file; Django raises `OperationalError`. At the end of the request Django hands A back; the pool sees it is broken, discards it and opens a new session in the background. The next request gets idle session B, which is also dead, and so on until all four are replaced.

**With health checks on (run).** `getconn()` calls `ConnectionPool.check_connection`, which runs `SELECT 1` on the session. On failure the pool discards it and tries the next, opening a new one when needed. Every request succeeds.

**Is the comment's second cause real? (run)** The head with lines 501 to 505 removed behaves exactly as the head, with checks off and with checks on (`probes/N1/grouping/results-no-override.txt`). With `CONN_MAX_AGE = 0`, `connect()` marks every new connection as already checked (head line 253), so Django's own per-request check never runs for a connection the request just obtained. The failure comes from line 232 and the pool's unchecked checkout alone.

## Promised?

The exact operation is handing a pooled session to a request without testing it, when `CONN_HEALTH_CHECKS` is off. psycopg-pool owns the checkout; Django owns the choice of `check=None` (line 232). Both are public interfaces: the pool option is documented, and `check` is a documented constructor parameter of `ConnectionPool`.

The six places (searches saved under `upstream/`, listed in `upstream/SOURCES.md`):

## What the affected person sees

A site with the pool on and the default settings. After the database server restarts, fails over, or a proxy or load balancer drops idle connections, the next requests fail with `django.db.utils.OperationalError: consuming input failed: terminating connection due to administrator command` or `... server closed the connection unexpectedly`, usually a 500 page (run, stub). How many: one per idle session in the pool, four with `"pool": True`, more if the pool grew to a larger `max_size`. Then the pool has replaced them and requests succeed with no action (run). The person is not stuck: `CONN_HEALTH_CHECKS = True` prevents it (run), but the pool section does not say so. Before the change, the pool did not exist; the same site without the pool and `CONN_MAX_AGE = 0` saw no failed request (run). A site with persistent connections and health checks off saw the same failures before and after the change, one per worker thread (run, documented).

## Both sides

- **For a problem.** The pool section is the only documentation of the new feature. It omits what the persistent-connections section says about connections the server ends, and the remedy, `CONN_HEALTH_CHECKS`, is documented only for persistent connections. The dependency's documented remedy fails through Django's dictionary (GT-v7). So a user had no documented way that works. In rulings 40 and 41 the owner ruled the same kind of omission in the same section a problem: "because it's not documented, this is a real bug as users will probably use it incorrectly". Users moving from `CONN_MAX_AGE = 0` lose a resilience they had. Maintainers later documented exactly this relationship (ticket 37283).
- **For a suggestion.** The behaviour is what the documentation promises: "the ``ConnectionPool`` defaults", whose owner states "By default no check is made on the connection" and that "the application might be served a connection in broken state". The change builds and tests that default, and wires the existing health-check setting to the pool on purpose. Django's documentation already accepts that reused connections without health checks fail once after a server restart. Nothing changes for anyone who does not turn the pool on. Rulings 40 and 41 were made under an earlier reading of the rules, and the current rule text has no rule that a missing caveat is a broken promise, except a missing minimum version (Delivery rule 1).

## Recommendation

> **What happens:** with the pool on and `CONN_HEALTH_CHECKS` off, the pool hands requests sessions the server has ended, so up to one request per idle session fails with `OperationalError` after a restart or a drop, and then the pool recovers. **Promised: no**; the pool section promises "the ``ConnectionPool`` defaults", whose owner documents "By default no check is made on the connection"; the change's test asserts that default; the six places were searched and none promises tested sessions or per-request fresh sessions with the pool. **Delivered: not asked.** **So: suggestion or observation (improvement):** turn checks on by default, or document `CONN_HEALTH_CHECKS` for the pool. **Band, decided separately:** none.
