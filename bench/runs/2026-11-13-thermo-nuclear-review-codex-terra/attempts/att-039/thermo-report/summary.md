[P1] Authenticate the ISR path override before trusting it — `packages/integrations/vercel/src/serverless/entrypoint.ts:24-25`

The same entrypoint is built into `_render` as well as `_isr`, and the new branch accepts `x-vercel-isr: 1` without authenticating its source. If that header reaches `_render` from a client, a request to `/api/public?x_astro_path=/api/private` is matched and rendered as `/api/private`, even though Vercel routed and applied any path-based protections to `/api/public`. I reproduced this with the built security-test fixture: the request returns `{"id":"public"}` without the header and `{"id":"private"}` with it. This reintroduces the path-override bypass that the existing untrusted-query test guards against and can bypass path-based access controls or ISR exclusions. The Vercel platform was unavailable, so whether it strips this particular incoming header could not be verified.

[P2] Preserve streamed request bodies when rewriting ISR requests — `packages/integrations/vercel/src/serverless/entrypoint.ts:24-25`

An ISR request with a body now enters the existing request reconstruction at lines 27–33, where `request.body` is a stream but the new `Request` has no `duplex` option. In Node this throws `TypeError: RequestInit: duplex option is required when sending a body` before route matching or rendering. Calling the built `_isr` handler with a POST body, `x-vercel-isr: 1`, and `x_astro_path=/one` reproduces the exception. Consequently, body-bearing requests that Vercel forwards to an ISR function fail instead of reaching the Astro route; the platform itself was unavailable to verify which methods it forwards.
