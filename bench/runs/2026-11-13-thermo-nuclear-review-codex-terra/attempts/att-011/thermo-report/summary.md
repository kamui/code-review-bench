**P1 — Preserve membership when an update races cleanup** ([weed/filer/redis2/universal_redis_store.go:245](../../clone/weed/filer/redis2/universal_redis_store.go#L245), lines 245–247)

An update can recreate the value after this existence check has returned zero, leaving it permanently absent from directory listings. For example, `Filer.CreateEntry` can read the existing TTL entry and select `UpdateEntry`; the Redis value then expires, a listing observes it missing, removes its index member and sees `EXISTS == 0`, and finally the pending `UpdateEntry` writes the value. `UpdateEntry` only calls `doInsertEntry` and does not add the directory member, so the successful update is invisible to future listings until a later insert adds the name. The recheck needs to account for in-flight updates as well as inserts.

**P1 — Do not silently lose the member when repair fails** ([weed/filer/redis2/universal_redis_store.go:238](../../clone/weed/filer/redis2/universal_redis_store.go#L238), lines 238–250)

The removal and restoration are separate Redis commands, but errors leave no durable repair path. If a concurrent `InsertEntry` writes the value and completes its `ZAddNX` before this `ZRem`, the cleanup removes the live member; a timeout or other error on the subsequent `ZAddNX` is discarded and the listing returns success. A `ZRem` timeout can also mean Redis applied the removal even though the client saw an error, and the early return skips the existence check entirely. In either case the value remains accessible by name but disappears from all future directory listings, which cannot retry cleanup because the member is already gone. The pre-change listing did not remove this live member.
