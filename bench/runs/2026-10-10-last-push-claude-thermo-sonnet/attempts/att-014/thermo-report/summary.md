# Thermo-nuclear code quality review: bokeh/bokeh#9232 (DatePicker UTC+ display fix)

Range reviewed: `ccb4bcb4c2b841d89b0e88303a97bf4604a5795f..36549bca3a63d581f7b68d08054a7813c1e6a499` (2 files, +104/−2). Detail files: `01_date_picker_widget.md`, `02_integration_tests.md`. Single reviewer, no delegation, no cross-model review. Execution was limited to scratch Node scripts run under several `TZ` values; the build, browser and Selenium suite were unavailable, so nothing in the integration test file was executed.

## Verdict

Do not approve as is. The change is two lines of logic, but it does not fix the underlying design problem, which is that `_unlocal_date` is handed two different kinds of input and treats them as one. It repairs one kind (local-midnight strings produced by the widget itself) in UTC+ zones and, by the same edit, breaks the other kind (UTC-midnight values produced by Python) in UTC− zones. The added integration test does not pin a timezone and does not assert on the path that regressed, so it cannot catch this. The simplification the author could have made is to delete the offset arithmetic and the ISO-string round trip altogether.

## Findings

**1. The offset shift in `_unlocal_date` fixes UTC+ by regressing UTC− for Python-supplied values (structural / correctness regression).** In `bokehjs/src/lib/models/widgets/date_picker.ts:78-88`, the new `getTimezoneOffset()` shift is only correct when the incoming `Date` is local midnight, which is what `new Date("Mon Sep 16 2019")` yields after the widget's own `_on_select` writes `toDateString()` back into `model.value`. The initial `value`, `min_date` and `max_date` coming from Python are different: a `datetime.date` or `datetime` is serialized as a UTC-midnight timestamp (or an ISO date string, which JavaScript also parses as UTC). For those inputs the original code, which read the UTC calendar date directly, was already correct everywhere except where it was applied to local-midnight strings. I ran the old and new function in Node with `TZ` set and `new Date(Date.UTC(2019, 8, 20))` as input: in `America/Los_Angeles` the old code returned Fri Sep 20 and the new code returns Thu Sep 19, while `Europe/Paris` and `Pacific/Auckland` return Sep 20 for both. The ISO string `"2019-09-20"` behaves the same way. So a user in the US who loads a page with `DatePicker(value=date(2019, 9, 20))` now sees the 19th, and `min_date`/`max_date` bounds shift by a day as well. The PR thread records a successful manual check in PST, but that exercised the post-selection path (local-midnight string), not the initial render from Python. The remedy is to stop guessing: normalize at one boundary. Either make the model always carry a single representation, or have the view branch once on the input type, rather than applying a blanket shift that is only right for one of them. Detail and a worked proposal are in `01_date_picker_widget.md`.

**2. Missed code-judo move: the whole "shift, format as ISO, split, rebuild" pipeline can be deleted (missed simplification).** `_unlocal_date` still builds a string with `toISOString().substr(0, 10)`, splits it on `-`, and reconstructs a `Date` from `Number()` conversions. With the new offset shift in front of it, the function now performs three conversions (timestamp shift, ISO string, tuple) to answer a single question: "what is the calendar day of this value?". If the value is a local-midnight `Date` (the case the PR targets), `new Date(date.getFullYear(), date.getMonth(), date.getDate())` is already the answer and needs no offset arithmetic; if it is a UTC-midnight timestamp, `new Date(date.getUTCFullYear(), date.getUTCMonth(), date.getUTCDate())` is the answer and needs no string round trip. Both are three-argument constructor calls on integer fields, with no `substr`, `split` or `Number`. Splitting by input kind also makes finding 1 disappear instead of moving it around. See `01_date_picker_widget.md` for the proposed shape.

**3. `_unlocal_date` mutates its argument and the comment block restates the arithmetic instead of the invariant (boundary / legibility).** `date.setTime(...)` at `date_picker.ts:83` modifies the `Date` the caller passed in. The three current callers (`date_picker.ts:68,70,71`) all pass a fresh `new Date(...)`, so nothing breaks today, but the method is public-looking (`_unlocal_date` is not `private`), and a pure function from `Date` to `Date` costs nothing. The replacement comment at lines 79-81 describes the mechanics ("get the UTC offset … then multiply to get the offset in ms") and contains the incorrect claim that the result is "agnostic to their local system's timezone", which is exactly what finding 1 shows to be untrue for UTC− zones. The original comment explained why the function exists; the new one explains what the next two lines do and gets the guarantee wrong. The new code also drops the repository's comment spacing convention (`//Get` without a space) and introduces `timeOffsetInMS` as the only camel/upper mix in the file.

**4. The integration test file does not pin a timezone and does not assert the initial-render path, so it cannot guard this fix (test coverage of the stated bug).** `tests/integration/widgets/test_datepicker.py` is the file Bryan suggested in the PR thread. It is a reasonable copy of the radio-button-group pattern, but none of the three tests sets `TZ` (or passes a browser timezone option), so on CI (UTC) they pass with or without the `date_picker.ts` change. `test_js_on_change_executes` asserts that clicking day 16 yields `'Mon Sep 16 2019'` in both the callback and the input element, which is the local-midnight path that was never broken in the form tested; no test asserts what the input shows for the Python-supplied `value=datetime(2019, 9, 20)` right after load, which is the path that finding 1 shows regresses in UTC−. The issue (#9129) is a timezone bug, and the PR body leaves "tests added / passed" unchecked. Remedy: add a test that reads `.bk-input` immediately after load and asserts `Fri Sep 20 2019`, and run it under at least one UTC+ and one UTC− browser timezone (Chrome `--lang`/`TZ` env on the driver, or `Emulation.setTimezoneOverride` through devtools). See `02_integration_tests.md`.

**5. The test file repeats an identical `DatePicker(...)` construction three times and carries a dated `max_date=datetime.utcnow()` (duplication / determinism).** All three tests build `DatePicker(title='Select date', value=datetime(2019, 9, 20), min_date=datetime(2019, 9, 1), max_date=datetime.utcnow(), css_classes=["foo"])` inline (`test_datepicker.py:42,50,76` of the new file). The only thing that differs between them is what is done after construction. A small module-level factory or a pytest fixture would remove two copies and give the one place a timezone-parametrized variant would need. The `utcnow()` upper bound also makes the widget's selectable range depend on the wall clock; since the tests click day 16 of September 2019, a fixed `max_date` such as `datetime(2019, 9, 30)` is both deterministic and closer to what the test is about.

## Proposed remediation sequence

First decide, and document in `date_picker.ts`, which representations `model.value`, `min_date` and `max_date` can hold when they reach the view (UTC-midnight timestamp or ISO string from Python, `toDateString()` string from `_on_select`). Second, replace `_unlocal_date` with one pure helper per representation (or a single helper that branches once on the representation) that uses the integer calendar-field constructors and no offset arithmetic, deleting the ISO round trip. Third, add the two timezone-pinned integration assertions from finding 4 so the fix is guarded in both a UTC+ and a UTC− zone. Fourth, hoist the repeated `DatePicker(...)` construction and fix `max_date` in the test file. Finally, check the `tests/` suite and bokehjs unit tests for existing coverage of `_unlocal_date` (none was found by grep in `bokehjs/test`), and complete the PR checklist item for tests.
