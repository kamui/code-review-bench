# Detail: clientconn.go (addrConn connect / updateAddrs / resetTransportAndUnlock)

Range reviewed: `git diff main...review-head` (1 file, +6/−7). Verification: read the full diff and the surrounding code at head; `go vet .` in the root package is clean (offline, allowed env). No tests were run; the PR's own claim (Test/AuthorityRevive, 100000 runs) was not reproduced. File size: clientconn.go is 1839 lines at base and 1838 at head, so the 1k-line rule is not newly triggered (it was already over).

## Finding A — Lock ownership is handed across a function boundary and a goroutine boundary

Evidence: `connect()` (clientconn.go ~L905-924) now returns from its locked section by calling `ac.resetTransportAndUnlock()`. `updateAddrs()` (~L996) runs `go ac.resetTransportAndUnlock()` while holding `ac.mu`, so the mutex is locked by one goroutine and unlocked by another. `resetTransportAndUnlock` (~L1231-1300) then performs a short locked prologue (ctx check, read addrs, compute backoff and dial deadline, move to CONNECTING) and a long unlocked body (tryAllAddrs, backoff wait, repeated Lock/Unlock pairs).

Problem: the fix is correct in intent — the check-then-act window between `connect()`'s idle check and the CONNECTING transition has to be closed. But the way it is closed is a "caller locks, callee unlocks" contract. The function has an early `Unlock` return, a mid-function `Unlock` and about five further Lock/Unlock pairs, so a reader has to track which path owns the lock at every line. The contract is enforced only by a doc comment. A reviewer pointed out that nothing checks it. The author's answer was that unlocking an unlocked mutex panics and tests run under the race detector, which does not cover a caller that forgets to lock before a path that never unlocks. The codebase's convention elsewhere is `...Locked` for "caller holds the lock and it stays held"; this introduces a second, inverted convention (`...AndUnlock`) in the same type. The `go f()` in `updateAddrs` that starts with the lock held is the most surprising form of it.

Code-judo proposal: split the function at the natural seam instead of passing the lock through it. Add a small locked helper, for example `func (ac *addrConn) prepareConnectLocked() (attempt connectAttempt, ok bool)`. It checks `ac.ctx.Err()`, snapshots `ac.ctx`, `ac.addrs` and the connect deadline, and calls `updateConnectivityState(Connecting)`. The rest becomes `func (ac *addrConn) runConnectAttempt(a connectAttempt)`, which takes no lock on entry. `connect()` would do `a, ok := ac.prepareConnectLocked(); ac.mu.Unlock(); if ok { ac.runConnectAttempt(a) }`. `updateAddrs()` would do the same and run the second half with `go`, with no lock crossing the `go` statement. Each function then has a single obvious lock discipline, the `...Locked` naming convention is reused, and the state transition still happens in the same critical section as the idle check, which is what fixes the race. The net diff is similar in size, but the contract is structural instead of documented.

## Finding B — The `defer GracefulClose` rationale in updateAddrs no longer matches the code

Evidence: `updateAddrs` (~L983-986) says "We have to defer here because GracefulClose => onClose, which requires locking ac.mu", and defers `ac.transport.GracefulClose()`. Before the PR, `ac.mu.Unlock()` ran before the function's deferred calls, so GracefulClose ran unlocked and never contended with a connect attempt. At head, `go ac.resetTransportAndUnlock()` is the last statement while the mutex is still held, and the spawned goroutine only releases it after `updateConnectivityState(Connecting)` returns, which calls `acbw.updateState`. The deferred `GracefulClose()` -> `onClose()` (internal/transport/http2_client.go ~L1055) now runs on the caller's goroutine and blocks on `ac.mu` until the new goroutine finishes its prologue.

I found no deadlock: the spawned goroutine never waits on the caller, and `onClose` bails out on `ctx.Err()` because the old ctx was cancelled. So this is a maintainability and latency-coupling issue, not a proven bug. But the comment is now incomplete, the ordering between teardown of the old transport and start of the new attempt is implicit, and any future change making `acbw.updateState` or the prologue wait on the caller would turn it into a deadlock. Remedy: with the Finding A split, `updateAddrs` can unlock before its defers run, as it did before, which restores the original GracefulClose-outside-the-lock invariant. Otherwise the comment needs to say that the lock is held by the spawned goroutine at that point and that GracefulClose may block briefly.

## Finding C — No deterministic regression test for the race; commit message does not match the diff

Evidence: the diff touches only clientconn.go. Verification is "Test/AuthorityRevive no longer flakes for 100000 attempts", which is a stress run on an xDS test with a 0.4% failure rate, not a test of the contract. The invariant "two concurrent `connect()` calls produce exactly one `tryAllAddrs`" can be tested directly in package grpc (for example by calling `ac.connect()` from N goroutines against a dialer that counts attempts). The second commit is titled "Make callers of resetBackoff() lock the mutex", but the diff has no `resetBackoff` caller change; it is about `resetTransport`. A squash will probably hide this, but the history is misleading.

Remedy: add an internal test that fires concurrent `connect()` calls (and a `connect()` racing `updateAddrs`) and asserts a single dial. Fix the commit message if history is kept.
