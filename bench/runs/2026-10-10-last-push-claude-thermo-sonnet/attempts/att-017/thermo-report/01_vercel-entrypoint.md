## Finding 1 — Trust boundary re-opened with a client-controllable header (structural/boundary regression)

The path override is again reachable by an unauthenticated caller. The previous change made the override depend on a shared secret precisely because the query param and `x-astro-path` header are attacker-controlled. The new `else if` makes the query param authoritative whenever the request carries `x-vercel-isr: 1`. That header is a plain request header; nothing in the entrypoint (or the build) proves that Vercel, rather than the client, set it, and the same handler serves non-ISR functions. The scratch run shows a request to `/api/public` with that header being served the `/api/private` route. That is the exact scenario the sibling security test guards, and the fix passes that test only because the test omits the header. The PR text says the ISR path "needs" rewriting but does not argue why the header is a trustworthy signal.

Code-judo remedy: do not infer "I am the ISR function" from a request header. The ISR function is generated by `buildISRFolder`, which already knows it is the ISR function. Give that folder its own trust signal at build time (for example bake a flag into its config / a distinct tiny entrypoint wrapper that calls the shared `fetch` with the query param already resolved, or reuse the existing `middlewareSecret` plumbing, or use Vercel's documented bypass mechanism) so the shared `fetch` no longer needs any request-derived mode switch. The `else if` branch then disappears from the shared path.

## Finding 2 — Special-case branch bolted onto a security-sensitive shared path (spaghetti growth)

`realPath` went from a single expression with one source to a mutable `let` that is assigned in two branches, with a literal `'x-vercel-isr'` magic string (not a named constant beside `ASTRO_PATH_HEADER`/`ASTRO_PATH_PARAM` in `src/index.ts`, where the ISR rewrite contract lives). The `else if` also runs when the middleware secret is present but wrong, so a bad secret plus the ISR header silently falls through to a different trust path. The `hasValidMiddlewareSecret` boolean is now consulted in three places with different meanings (path source, locals gating, secret scrubbing).

Remedy: extract a small pure helper, e.g. `resolveRealPath(request, url, hasValidMiddlewareSecret): string | null`, with the header name exported as a constant from `index.ts`, so the three-way decision is named, typed and unit-testable, and the `fetch` body keeps one line `const realPath = resolveRealPath(...)`.

## Finding 3 — No regression test for the new behaviour, and the security test is blind to it

The PR states "No additional test cases added" and relies on manual deployment. `test/isr.test.js` exists but only checks build output, and `test/path-override-security.test.js` has no case for `x-vercel-isr`. The in-process handler harness already used in the security test makes both a positive test (ISR request with the param resolves the real route) and a negative test (header spoofed on a non-ISR function must not rewrite) cheap. Without them the 404 regression this PR fixes could recur silently, and the spoofing path in Finding 1 is unguarded.

## Finding 4 — Type and style looseness in the edited lines (minor)

`let realPath = undefined;` yields an evolving-`any`-style declaration instead of `string | null`; the following `typeof realPath === 'string'` guard then papers over the unclear invariant. The block also uses `if(` without a space and a missing semicolon, inconsistent with the surrounding tab/prettier style. The changeset text ("Fix vercel ISR path rewrite") is terse but acceptable.

Remedy: declare `let realPath: string | null = null;` or, better, use the helper from Finding 2 which returns that type directly.

## Worked code-judo proposal

1. In `src/index.ts`, export `ASTRO_ISR_HEADER = 'x-vercel-isr'` only if the header is kept; preferred is not to key on it.
2. Have `buildISRFolder` emit the ISR function with a build-time constant (virtual module field next to `middlewareSecret`) saying "this function receives the rewritten path in the query string".
3. In the entrypoint, compute `realPath` via one helper that reads the header only with a valid secret, and the query param only when the build-time constant is set — never from a request header.
4. Add the two tests from Finding 3.

Result: one explicit source of trust per function, no request-derived mode switch, and the previously fixed spoofing hole stays closed.
