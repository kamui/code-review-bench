# 01 — The APIv1 message boundary (codec, binary logging, status details, pretty)

Scope: `encoding/proto/proto.go`, `internal/binarylog/method_logger.go`,
`internal/status/status.go`, `internal/pretty/pretty.go`, and the status tests.

Review range: `5051eeae..b8374114` (`git diff main...review-head`).

## The shared root cause

`github.com/golang/protobuf/proto.Message` and `google.golang.org/protobuf/proto.Message`
have the same spelling at every call site (`proto.Message`) but are different interfaces:

- the old one is `protoiface.MessageV1` — `Reset()`, `String()`, `ProtoMessage()`;
- the new one is `protoreflect.ProtoMessage` — `ProtoReflect()`.

Messages generated by current `protoc-gen-go` implement both, so a pure import swap
compiles and every in-repo test passes. Messages that implement only APIv1 (code
generated by `protoc-gen-go` before v1.4, gogo/protobuf output, hand-written legacy
messages) satisfy the old interface and not the new one. The old package also did the
adaptation internally: `golang/protobuf/proto.Marshal(m)` calls `protoimpl.X.ProtoMessageV2Of(m)`
before delegating to APIv2. The new package does not.

So anywhere the PR swapped the import under a `v.(proto.Message)` type assertion on a
caller-supplied `any`, the assertion silently narrowed. The PR treated the migration as
an import rename; it is actually a boundary change, and the boundary needed to be made
explicit exactly once. Instead it is handled four different ways:

| Site | How V1-only messages are handled at head |
| --- | --- |
| `encoding/proto/proto.go:41,49` | not handled — rejected with an error |
| `internal/binarylog/method_logger.go:242,282` | not handled — payload silently dropped |
| `internal/status/status.go:141` (`WithDetails`) | `protoadapt.MessageV2Of` on the way in |
| `internal/status/status.go:158-163` (`Details`) | not unwrapped on the way out |
| `internal/pretty/pretty.go:39-41` | `protov1.MessageV2` from the *old* module |
| `channelz/service/service.go:193` (pre-existing) | `protoadapt.MessageV2Of` |

## Finding 1 — default codec rejects APIv1-only messages

`encoding/proto/proto.go:40-54` at head:

```go
func (codec) Marshal(v any) ([]byte, error) {
	vv, ok := v.(proto.Message)          // now google.golang.org/protobuf/proto.Message
	if !ok {
		return nil, fmt.Errorf("failed to marshal, message is %T, want proto.Message", v)
	}
	return proto.Marshal(vv)
}
```

The function body is byte-for-byte identical to base; only the import on line 27 changed.

### Verification (confirmed by execution)

A scratch test was injected with `go test -overlay` (nothing written to the clone). The
test defines a struct with only `Reset/String/ProtoMessage` plus a `protobuf:"bytes,1,..."`
field tag, registers it with `golang/protobuf/proto.RegisterType`, and calls
`codec{}.Marshal` / `codec{}.Unmarshal`. It was run once against head and once with
`encoding/proto/proto.go` overlaid by `git show main:encoding/proto/proto.go`.

```
GOFLAGS=-mod=readonly GOPROXY=off GOSUMDB=off GOTOOLCHAIN=local \
  go test -v -overlay <work>/scratch/overlay_codec_head.json \
  -run TestScratchLegacyCodec -count=1 ./encoding/proto/
```

Head:

```
SCRATCH marshal: bytes=[] err=failed to marshal, message is *proto.legacyMsg, want proto.Message
SCRATCH unmarshal: out="" err=failed to unmarshal, message is *proto.legacyMsg, want proto.Message
```

Base `proto.go`:

```
SCRATCH marshal: bytes=[10 1 110] err=<nil>
SCRATCH unmarshal: out="n" err=<nil>
```

This is the codec registered under the name `proto`, i.e. the default for every RPC.
A service whose stubs were generated by an old generator would start failing every call
with an `Internal` status after upgrading grpc-go. No test in the PR exercises a
V1-only message through the codec (`git grep protoadapt` finds no use in `encoding/`).

### Worked proposal

```go
// messageV2Of returns v as an APIv2 message, adapting APIv1-only messages.
// It returns nil if v is not a protobuf message.
func messageV2Of(v any) proto.Message {
	switch v := v.(type) {
	case proto.Message: // fast path: everything generated by protoc-gen-go >= 1.4
		return v
	case protoadapt.MessageV1:
		return protoadapt.MessageV2Of(v)
	}
	return nil
}

func (codec) Marshal(v any) ([]byte, error) {
	vv := messageV2Of(v)
	if vv == nil {
		return nil, fmt.Errorf("failed to marshal, message is %T, want proto.Message", v)
	}
	return proto.Marshal(vv)
}
```

`Unmarshal` takes the same shape. The legacy wrapper returned by `MessageV2Of` holds the
caller's pointer, so `proto.Unmarshal` into it populates the caller's struct, which is
what the base behaviour was. Add a table test with one V1-only message type.

## Finding 2 — binary logging silently drops APIv1-only payloads

`internal/binarylog/method_logger.go:242-251` (`ClientMessage.toProto`) and `:282-291`
(`ServerMessage.toProto`) contain the same block:

```go
if m, ok := c.Message.(proto.Message); ok {
	data, err = proto.Marshal(m)
	...
} else if b, ok := c.Message.([]byte); ok {
	data = b
} else {
	grpclogLogger.Infof("binarylogging: message to log is neither proto.message nor []byte")
}
```

Same import swap, same narrowing. The failure mode is worse than finding 1 because it
is silent: the entry is still emitted, with `Length: 0` and empty `Data`.

### Verification (confirmed by execution)

Same overlay technique, package `./internal/binarylog/`, calling
`(&ClientMessage{Message: &legacyMsg{Name: "n"}}).toProto()` and the `ServerMessage`
equivalent.

Head: `SCRATCH client len=0 data=[]; server len=0 data=[]`

Base `method_logger.go`: `SCRATCH client len=3 data=[10 1 110]; server len=3 data=[10 1 110]`

### Worked proposal

The two blocks were already copy-pasted before this PR; the PR had to touch both and
left both. Collapse them and reuse the helper from finding 1:

```go
// marshalPayload returns the bytes to record for an RPC message.
func marshalPayload(msg any) []byte {
	if b, ok := msg.([]byte); ok {
		return b
	}
	m := messageV2Of(msg) // shared helper, see below
	if m == nil {
		grpclogLogger.Infof("binarylogging: message to log is neither proto.message nor []byte")
		return nil
	}
	data, err := proto.Marshal(m)
	if err != nil {
		grpclogLogger.Infof("binarylogging: failed to marshal proto message: %v", err)
	}
	return data
}
```

`ClientMessage.toProto` and `ServerMessage.toProto` then differ only in the event type,
which is the only thing that actually differs between them.

Minor leftover in the same file, `method_logger.go:92-93`: the mechanical rewrite kept a
temporary that only existed to discard the old error return —
`timestamp := timestamppb.Now(); m.Timestamp = timestamp` should be
`m.Timestamp = timestamppb.Now()`.

## Finding 3 — `Status.Details()` no longer round-trips what `WithDetails()` accepts

`internal/status/status.go:134` deliberately types the input as `...protoadapt.MessageV1`
(identical to the old `golang/protobuf/proto.Message`, so source-compatible) and adapts
with `protoadapt.MessageV2Of` on line 141. That is the right call for the input side.

The output side, lines 152-166, is not symmetric:

```go
detail, err := any.UnmarshalNew()   // returns google.golang.org/protobuf/proto.Message
...
details = append(details, detail)
```

Base used `ptypes.UnmarshalAny(any, &ptypes.DynamicAny{})` and appended `detail.Message`,
which goes through `proto.MessageV1(mt.New().Interface())` and therefore unwraps legacy
messages back to their concrete Go type.

### Verification (confirmed by execution)

Overlay test in `./status/` attaching a V1-only `*legacyDetail` via `WithDetails` and
inspecting `Details()[0]`; run against head and against base `internal/status/status.go`.

Head: `SCRATCH detail type=*impl.messageIfaceWrapper concrete=false implementsV1=false`

Base: `SCRATCH detail type=*status.legacyDetail concrete=true implementsV1=true`

User code of the form

```go
for _, d := range st.Details() {
	switch d := d.(type) {
	case *mypb.LegacyDetail: ...
	}
}
```

silently stops matching, and the value it now receives is a type from
`google.golang.org/protobuf/internal/impl` that the user cannot name. The returned value
does not even satisfy the interface `WithDetails` accepts, so `st2.WithDetails(st.Details()[0].(protoadapt.MessageV1))`
panics for these messages.

The commit list contains "add compatibility test for status" (54e1afbe) but no such test
survives in the final tree; `status/status_test.go` only exercises `errdetails` messages
that implement both APIs.

### Worked proposal

```go
// Details returns ... Each decoded detail is returned as the same Go type
// that was (or would be) passed to WithDetails.
detail, err := any.UnmarshalNew()
if err != nil {
	details = append(details, err)
	continue
}
// MessageV1Of unwraps a legacy wrapper back to the user's concrete type and
// returns messages that already implement APIv1 unchanged.
details = append(details, protoadapt.MessageV1Of(detail))
```

`UnmarshalNew` resolves through `protoregistry.GlobalTypes`, so every value it returns
is either generated code (implements both APIs, returned as-is) or a registered legacy
message (unwrapped). Add a V1-only detail to `TestStatus_ErrorDetails`.

Test fallout of the asymmetric contract, `status/status_test.go:359`:

```go
if !proto.Equal(details[i].(protoreflect.ProtoMessage), tc.details[i].(protoreflect.ProtoMessage)) {
```

Two casts plus a new `protoreflect` import whose only use is spelling `proto.Message`
(already imported in the file) a second way. With the fix above this becomes
`cmp.Diff(got, want, protocmp.Transform())` over the whole slice, or at minimum
`proto.Equal(protoadapt.MessageV2Of(got), protoadapt.MessageV2Of(want))`.

## Finding 6 — `pretty.ToJSON` kept two branches that are now the same branch

`internal/pretty/pretty.go:39-61` at head:

```go
case protov1.Message:
	mm := protojson.MarshalOptions{Indent: jsonIndent}
	ret, err := mm.Marshal(protov1.MessageV2(ee))
	if err != nil { return fmt.Sprintf("%+v", ee) }
	return string(ret)
case protov2.Message:
	mm := protojson.MarshalOptions{Multiline: true, Indent: jsonIndent}
	ret, err := mm.Marshal(ee)
	if err != nil { return fmt.Sprintf("%+v", ee) }
	return string(ret)
```

Before the PR the first branch used `jsonpb.Marshaler`, so two branches were justified.
After it, they differ only in (a) the adapter call and (b) `Multiline: true`, and (b) is
a no-op: the `protojson` v1.32.0 doc on `MarshalOptions.Indent` says "If non-empty, then
Multiline is treated as true" (`encoding/protojson/encode.go:50-54` in the module cache).
The file also still imports `github.com/golang/protobuf/proto` (line 27) solely for
`protov1.Message` / `protov1.MessageV2`, while every other file the PR touched uses
`protoadapt` for the same thing.

### Worked proposal

```go
func ToJSON(e any) string {
	if m := messageV2Of(e); m != nil {
		ret, err := protojson.MarshalOptions{Indent: jsonIndent}.Marshal(m)
		if err != nil {
			// (existing comment about unresolvable Anys)
			return fmt.Sprintf("%+v", e)
		}
		return string(ret)
	}
	ret, err := json.MarshalIndent(e, "", jsonIndent)
	...
}
```

One proto branch, no `golang/protobuf` import, no aliasing of two `proto` packages.

## The code-judo move across findings 1, 2 and 6

All three want the same ten-line function: "give me this `any` as an APIv2 message, or
nil". Define it once in a leaf internal package (it imports only
`google.golang.org/protobuf/proto` and `protoadapt`, so `encoding/proto`,
`internal/binarylog` and `internal/pretty` can all depend on it without cycles) and
delete the three hand-rolled type switches. After that, "what counts as a protobuf
message in grpc-go" has one answer in one place, and the remaining `protoadapt` calls in
`internal/status` and `channelz/service` are the only places that need to know V1 exists.
