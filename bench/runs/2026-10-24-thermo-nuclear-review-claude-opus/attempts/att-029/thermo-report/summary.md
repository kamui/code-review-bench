# Thermo Nuclear Review — grpc/grpc-go#6919 (`main...review-head`, 5051eeae..b8374114)

Scope: this PR moves protobuf imports and call sites from `github.com/golang/protobuf` to `google.golang.org/protobuf` across 68 files. I read the whole non-test diff and the test diffs that change behavior (status tests). I compared each replaced `ptypes`/v1 `proto` call against its replacement in the module cache (`github.com/golang/protobuf@v1.5.3`, `google.golang.org/protobuf@v1.32.0`). I compiled the tests of every changed package and ran the focused tests for `status`, `encoding/proto`, `internal/binarylog`, `xds/internal/httpfilter/...` and `xds/internal/xdsclient/xdsresource`. All of them pass. I also ran two throwaway tests through `-overlay` files kept in the work directory, without changing the clone, to confirm the behavior described below.

## Findings

### 1. [High] The default gRPC codec now rejects every message that only implements the v1 (legacy) protobuf API, so RPCs using older generated code fail with `codes.Internal`

File: `encoding/proto/proto.go`, lines 41-53 (`codec.Marshal` / `codec.Unmarshal`).

Evidence: the only change in this file is the import, from `github.com/golang/protobuf/proto` to `google.golang.org/protobuf/proto`. The function bodies stayed the same, but what `v.(proto.Message)` checks for is different now:
- Before, `proto.Message` was `protoiface.MessageV1`, meaning `Reset`/`String`/`ProtoMessage`. The v1 `proto.Marshal`/`proto.Unmarshal` wrap legacy messages internally (`protoimpl.X.ProtoMessageV2Of`), so they work.
- After, `proto.Message` is `protoreflect.ProtoMessage`, which requires a `ProtoReflect()` method. Code generated by protoc-gen-go older than 1.4 (the `plugins=grpc` era) and gogo-generated messages don't have that method. They now fail the type assertion.

This is the default codec, registered in `init()` and used for every RPC that doesn't override the codec. Every unary or streaming send/receive of such a message now fails. The client gets `rpc error: code = Internal desc = grpc: error while marshaling: failed to marshal, message is *X, want proto.Message`. A server receiving such a message fails while unmarshaling the request.

Reproduced:
- **Codec level:** a legacy message registered with `protov1.RegisterType`. v1 `proto.Marshal(m)` returns `err=<nil>`, but `encoding.GetCodec("proto").Marshal(m)` and `.Unmarshal` both return `failed to (un)marshal, message is *proto_test.legacyMsg, want proto.Message`.
- **End to end:** the repository's own legacy generated package `reflection/grpc_testing_not_regenerate`, whose `testv3.go` has no `ProtoReflect`. I registered `pbv3.RegisterSearchServiceV3Server` (the same server `reflection/serverreflection_test.go` registers) and called `pbv3.NewSearchServiceV3Client(cc).Search(...)`. The call fails with `rpc error: code = Internal desc = grpc: error while marshaling: failed to marshal, message is *grpc_testing_not_regenerate.SearchRequestV3, want proto.Message`. Before this PR it succeeded.

Impact: this is a silent runtime break for downstream users whose services still use older generated stubs or gogo messages with the default codec. It compiles, and then every RPC fails. Nothing in the PR's intent ("migrate imports and call sites") says dropping support for v1-only messages is wanted, and no test exercises it. The existing tests pass only because every message they send over the wire is APIv2-generated. To keep the old behavior, the codec should accept both kinds of message: convert `protoadapt.MessageV1` values with `protoadapt.MessageV2Of` before calling `proto.Marshal`/`proto.Unmarshal`.

### 2. [Medium] `Status.Details()` now returns an internal wrapper type instead of the user's concrete type for legacy detail messages, breaking type assertions

File: `internal/status/status.go`, lines 152-163 (`Details`), together with `WithDetails` at lines 134-149.

Evidence: before, `Details()` called `ptypes.UnmarshalAny(any, &ptypes.DynamicAny{})`. That path calls `ptypes.Empty`, which returns `proto.MessageV1(mt.New().Interface())` and unwraps legacy messages back to their original Go type. Now it returns `any.UnmarshalNew()` directly. For a legacy-registered type, `mt.New().Interface()` is a `*impl.messageIfaceWrapper`, not the user's struct.

`WithDetails` still accepts legacy messages, because `protoadapt.MessageV2Of` wraps them. So a legacy message survives the round trip through `WithDetails`, but what comes back out of `Details()` is a different type.

Reproduced with the overlay test: `status.New(codes.Internal, "x").WithDetails(legacyMsg)` succeeds, then `s.Details()` gives `*impl.messageIfaceWrapper` and `d.(*legacyMsg)` is `false`. Generated APIv2 types such as `*errdetails.BadRequest` still come back as their concrete type, which is why the existing tests pass.

Impact: client code that reads error details sent with older generated detail messages, using the standard pattern `for _, d := range st.Details() { if x, ok := d.(*mypb.MyErr); ok {...} }`, stops matching without any error. Callers lose access to error metadata such as retry or quota info, and error-handling branches stop running. This affects `status.FromError(err).Details()`, the public API of the `status` package. The `Details()` error values also change, for example from `message type url "" is invalid` to `invalid empty type URL`, as the updated `status/status_test.go` expectations show. That is a smaller change but also user-visible. To keep the old behavior, unwrap results with `protoadapt.MessageV1Of` before returning them.

### 3. [Low] The LRS invalid-interval error message now prints a stale `nil` error instead of the validation error

File: `xds/internal/xdsclient/transport/loadreport.go`, lines 173-177.

Evidence: the replacement code is `if rInterval.CheckValid() != nil { return nil, 0, fmt.Errorf("invalid load_reporting_interval: %v", err) }`. It throws away the `CheckValid()` result and formats `err`, which is still the variable from the earlier `resp, err := stream.Recv()` and is known to be `nil` at this point. Before, `err` was the result of `ptypes.Duration(...)`.

When an LRS server sends a missing or out-of-range `load_reporting_interval`, the warning `Reading from LRS stream failed: invalid load_reporting_interval: <nil>` no longer says why the interval was rejected. The stream is still rejected and retried with backoff as before. I checked that `(*durationpb.Duration)(nil).CheckValid()` returns `invalid nil Duration`, so a missing interval cannot reach `time.NewTicker(0)`. Only the diagnostics get worse. The fix is to capture the error, e.g. `if err := rInterval.CheckValid(); err != nil`.

### 4. [Low] The merge-conflict resolution downgrades `golang.org/x/tools` in the tools module from v0.17.0 to v0.14.0

File: `test/tools/go.mod`, line 7, and `test/tools/go.sum`.

Evidence: the base commit 5051eeae ("grpc: Update go mod (#6939)") had just bumped `golang.org/x/tools` to v0.17.0. The PR's go.mod sets it back to `golang.org/x/tools v0.14.0`, adds `golang.org/x/sys v0.13.0 // indirect`, and replaces the v0.17.0 and `x/sync v0.6.0` sums with v0.14.0 and `x/sync v0.4.0` ones. The PR's intent only calls for replacing `github.com/golang/protobuf/protoc-gen-go` with `google.golang.org/protobuf/cmd/protoc-gen-go` in `tools.go`, so the downgrade looks like a leftover from the "resolve conflicts" commit (b8374114).

`vet.sh -install` runs `go install golang.org/x/tools/cmd/goimports` from `./test/tools`, so developers and CI would quietly pin an older `goimports` and undo the base's dependency update. Nothing fails today, but it is an unintended dependency regression worth reverting to v0.17.0.

## Checked and not reported

- `balancer/rls/config.go` `convertDuration`: `d.AsDuration(), d.CheckValid()` saturates durations that overflow `time.Duration` where `ptypes.Duration` returned an error. `maxAge` is clamped to 5m, and a saturated lookup timeout of about 292 years behaves the same in practice. Not harmful.
- `internal/pretty.ToJSON`: switching from `jsonpb.Marshaler{Indent}` to `protojson.MarshalOptions{Indent}` keeps lowerCamelCase names and leaves unpopulated fields out. It is only used for logging.
- `WithDetails` now takes `protoadapt.MessageV1`, which is the same type alias (`protoiface.MessageV1`) as the old `github.com/golang/protobuf/proto.Message`, so there is no API break. Marshaling a proto2 message with a missing required field returned an error with both the old and the new code, so that is not a regression.
- The `ptypes.UnmarshalAny`/`ptypes.Is` → `Any.UnmarshalTo`/`Any.MessageIs` swaps in the xDS filters and resources, the `ptypes.DurationProto`/`TimestampProto` → `durationpb.New`/`timestamppb.Now` swaps, and the `wrapperspb`/`structpb`/`durationpb`/`timestamppb` import swaps are equivalent (the types are aliases). No feature gates or env-var handling are touched.
