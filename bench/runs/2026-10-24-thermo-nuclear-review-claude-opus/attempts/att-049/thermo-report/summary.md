# Thermo Nuclear Review — django/django#16631

Range: `9b224579875e30203d079cc2fee83b116d98eb78..2396933ca99c6bfb53bda9e53968760316646e01` ("Fixed #34384 -- Fixed session validation when rotation secret keys.")

The change makes `django.contrib.auth.get_user()` accept a session whose stored `_auth_user_hash` matches an HMAC computed with one of `SECRET_KEY_FALLBACKS`, then cycles the session key and stores the current-key hash. It adds `AbstractBaseUser.get_session_auth_fallback_hash()` and a private `_get_session_auth_hash(secret=None)`. I traced every caller of `get_user` (`AuthenticationMiddleware` lazy `request.user`, `auser()` via `sync_to_async`, the test client), `login()`, `update_session_auth_hash()`, `SessionBase.cycle_key()` and `SessionMiddleware`. I also ran `auth_tests.test_basic`, `auth_tests.test_views` and `auth_tests.test_middleware`: 130 tests, OK. Password-change invalidation still works, because the fallback HMACs cover the current password. I found no authentication bypass. The findings follow.

## Finding 1 — [Medium] `get_user()` raises AttributeError for user objects that implement `get_session_auth_hash` but not the new `get_session_auth_fallback_hash`

**File/lines:** `django/contrib/auth/__init__.py` lines 200–221, specifically 214–216 (`for fallback_auth_hash in user.get_session_auth_fallback_hash()`).

**Evidence:** Session verification is still gated only on `hasattr(user, "get_session_auth_hash")` (line 200), which is a duck-typing contract: any user object returned by a backend's `get_user()` that has that method takes part in session verification. The new mismatch branch then calls `user.get_session_auth_fallback_hash()` without any `hasattr`/`getattr` guard. Only `AbstractBaseUser` defines that method. It is called whenever a stored hash exists but doesn't match. That includes the common, non-rotation case of a password changed in another session, and it happens even when `SECRET_KEY_FALLBACKS` is empty, because the attribute lookup happens before the generator is iterated. I confirmed this with a scratch script (outside the clone): a backend returns a plain object with `pk`, `is_authenticated` and `get_session_auth_hash()`, and the stored hash mismatches. `auth.get_user(request)` raises `AttributeError: 'DuckUser' object has no attribute 'get_session_auth_fallback_hash'`. Before this change the same request ran `request.session.flush()` and returned `AnonymousUser`.

**Failure:** For projects whose user objects don't inherit from `AbstractBaseUser` (third-party/non-ORM user models, wrapper or proxy user objects, custom backends) but follow the `get_session_auth_hash` contract, every request that touches `request.user` with a stale session returns HTTP 500 instead of logging the user out. The session is never flushed, so the 500 repeats on every request until the cookie is cleared. That is a denial of service for those users. It also breaks the "sessions are invalidated on password change" feature for them. This ships in a patch release (4.1.8 backport), where such a regression is especially unexpected. The call should be guarded (for example `getattr(user, "get_session_auth_fallback_hash", None)`), so that it falls back to the old flush behaviour.

## Finding 2 — [Medium] `cycle_key()` on fallback verification logs users out on concurrent (and 5xx) requests during key rotation, re-creating the bug being fixed

**File/lines:** `django/contrib/auth/__init__.py` lines 213–218 (`request.session.cycle_key()` followed by `request.session[HASH_SESSION_KEY] = session_auth_hash`); interacts with `django/contrib/sessions/backends/base.py` lines 298–307 and `django/contrib/sessions/middleware.py` lines 56–59.

**Evidence:** `SessionBase.cycle_key()` creates and persists a new session key, then immediately runs `self.delete(old_key)` for server-side backends (db, cache, cached_db, file). The client gets the new cookie only when this response comes back. So any other request already in flight, or sent before the browser processes `Set-Cookie`, still carries the old key, and that key no longer exists. The typical case is parallel XHR/fetch calls from an SPA, or several tabs, on the first page load after deploying the rotated key. Those requests load an empty session and get `AnonymousUser`. I reproduced this with the db backend in a scratch script: request 1 with the old cookie returns the user and cycles the key; request 2 with the same old cookie then returns `AnonymousUser`. Also, `SessionMiddleware` skips `save()` and the cookie update for responses with status ≥ 500, but `cycle_key()` has already deleted the old session row. So if the first post-rotation request for a user happens to error, that user is logged out too. Re-storing `HASH_SESSION_KEY` alone is enough to migrate the session to the new key (the session ID is not derived from `SECRET_KEY`), so the cycle adds no security value that's needed here.

**Failure:** Ticket #34384 is about users being logged out when `SECRET_KEY` is rotated. With this change, any user whose first post-rotation page fires several authenticated requests at once (or hits a 5xx) is still logged out. Instead of a smooth rotation, some sessions are randomly lost. The tests only exercise one sequential request, so they don't catch this.

## Finding 3 — [Low] Fallback verification ignores overridden `get_session_auth_hash()`, so the fix silently doesn't apply to customised user models

**File/lines:** `django/contrib/auth/base_user.py` lines 135–153 (`get_session_auth_hash` delegating to `_get_session_auth_hash`, and `get_session_auth_fallback_hash` calling `_get_session_auth_hash(secret=fallback_secret)` directly).

**Evidence:** `get_session_auth_fallback_hash()` doesn't call the public `get_session_auth_hash()` with a different key. It calls the private base implementation (fixed salt, `self.password` only). A subclass of `AbstractBaseUser` that overrides `get_session_auth_hash()` is a documented customisation point, for example to mix in a per-user "log out everywhere" token or another salt. Its fallback hashes are computed with a different formula from the stored hash, so they never match. The public method also has no way to take a `secret`.

**Failure:** For such projects, rotating `SECRET_KEY` with `SECRET_KEY_FALLBACKS` still logs out every user. The release note and docs say that's fixed, and nothing tells those projects they must also override `get_session_auth_fallback_hash()`. This is not a security issue (the mismatch fails closed), but it is an incomplete fix that is undocumented for custom user models.
