**[P1] Invalidate the cached pool before switching to the test database.** File: `django/db/backends/postgresql/base.py`, lines 239-241. The pool is cached only by alias and retains the connection parameters captured at construction. When access to the `postgres` database is denied, the existing `_nodb_cursor()` fallback creates a wrapper with the original alias and opens a pool against the configured application database to create the test database. `BaseDatabaseCreation.create_test_db()` then closes the wrapper and changes `settings_dict["NAME"]` to the test database before running migrations. Closing now returns the connection to that cached pool, so subsequent connections still use the application database. The new pool cleanup in cloning and destruction does not cover this transition. An offline reproduction exercised the actual fallback and `create_test_db()` with simulated raw connections: at the intercepted `migrate` call, the configured name was `test_production`, while the connection's database remained `production`. Consequently, migrations and tests can modify or flush the application database instead of the test database. Close and invalidate the pool before test setup changes the database name, and ensure maintenance fallback connections cannot leave a pool cached for the application alias.

**[P1] Compose the role statement using the connection supplied to the pool callback.** File: `django/db/backends/postgresql/base.py`, lines 99-103. The new `ensure_role()` receives the raw connection being configured but calls `ops.compose_sql()`. `DatabaseOperations.compose_sql()` delegates to `psycopg_any.mogrify()`, which opens a cursor through the owning Django wrapper. With pooling enabled, this runs in a pool worker before the first configured connection has been delivered to the wrapper. That wrapper still has `connection=None`, so its cursor call re-enters `connect()` and waits for another connection from the same pool. Every new connection needs the same callback, so initialization cannot complete and database access times out. An offline reproduction using the real `ConnectionPool` and wrapper, with successful raw connection creation simulated, connected successfully without `assume_role` but raised Django `OperationalError` caused by `PoolTimeout` when `assume_role` was enabled; the recorded composition call ran in the pool worker. Thus the existing `assume_role` option is unusable with the new pooling feature. Format the statement through the supplied raw connection without opening a wrapper cursor.

**[P2] Treat an empty pool options dictionary as an enabled pool.** File: `django/db/backends/postgresql/base.py`, lines 204-206. The documented configuration accepts a dictionary of `ConnectionPool` options, but the `not pool_options` check treats `OPTIONS={"pool": {}}` as disabled. An empty dictionary is a valid way to request the pool's defaults, yet `wrapper.pool` returns `None`, `get_connection_params()` removes the option, and connections silently use the direct connection path. The offline check confirmed this result. Users supplying an initially empty options dictionary therefore receive no connection reuse or pool connection limit, despite opting into pooling. Distinguish an empty dictionary from an absent or explicitly disabled pool option.
