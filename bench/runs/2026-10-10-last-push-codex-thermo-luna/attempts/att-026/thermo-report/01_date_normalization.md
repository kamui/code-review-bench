# Date normalization subsystem

## Finding: the offset adjustment shifts UTC-midnight dates backward in UTC− timezones

The changed production lines are `bokehjs/src/lib/models/widgets/date_picker.ts:82-83`. The helper now reads `date.getTimezoneOffset()`, multiplies it by 60,000, and mutates its argument with `date.setTime(date.getTime() - timeOffsetInMS)`, after which it extracts the UTC ISO date and reconstructs a local `Date`.

That calculation is only appropriate for an input whose instant came from local midnight. `DatePicker`'s Python `Date` property is serialized as milliseconds since the UTC epoch: `bokeh/util/serialization.py:152-176` converts Python `datetime.date` values through a midnight `datetime` minus `DT_EPOCH`. Thus, an initial value such as `datetime(2019, 9, 20)` arrives as UTC midnight. In Los Angeles on that date, `getTimezoneOffset()` is `420`, so subtracting seven hours changes the ISO date from September 20 to September 19. The same mistake applies to `min_date` and `max_date`, because render passes all three values through `_unlocal_date`.

The new arithmetic does repair the other representation used by this widget. `_on_select` stores `date.toDateString()` as a local date string. In Paris, parsing `"Fri Sep 20 2019"` creates local midnight whose ISO date is September 19; subtracting the negative two-hour offset returns the ISO date September 20. The helper accepts both representations as an undifferentiated `Date`, though, so fixing that case breaks the numeric UTC-midnight case. This is an input-contract problem, not an opportunity for more offset cases.

## Evidence and verification status

The changed file has 129 lines, up from 125, so this change does not raise a file-size or decomposition concern. The implementation adds one calculation and no condition branches, wrappers, or cross-module coupling. Structurally, a short pure date conversion at the representation boundary is sufficient; a new general-purpose timezone abstraction would add unnecessary machinery.

I inspected the Python `Date` serializer in `bokeh/util/serialization.py`, the `DatePicker` property declaration in `bokeh/models/widgets/inputs.py`, and the selection assignment in `_on_select`. I ran this focused Node v24 script outside the checkout, using the PR's offset arithmetic on the relevant date values:

```js
for (const tz of ["UTC", "Europe/Paris", "America/Los_Angeles"]) {
  process.env.TZ = tz
  const d = new Date(Date.UTC(2019, 8, 20))
  const before = d.toISOString().slice(0, 10)
  d.setTime(d.getTime() - d.getTimezoneOffset() * 60000)
  console.log(tz, before, d.toISOString().slice(0, 10))
}
```

The observed UTC-midnight results were UTC: `2019-09-20` → `2019-09-20`; Europe/Paris: `2019-09-20` → `2019-09-20`; America/Los_Angeles: `2019-09-20` → `2019-09-19`. A separate Paris check of `new Date("Fri Sep 20 2019")` produced ISO `2019-09-19` before the adjustment and `2019-09-20` after it. This verifies the representation asymmetry in the helper. It does not execute Pikaday or the browser integration tests.

The added tests in `tests/integration/widgets/test_datepicker.py:42-98` set a Python `datetime` value, but `test_basic` checks only the title and console errors. The JavaScript and server tests select September 16 and assert the selected value; neither asserts that the initially displayed value is September 20. None controls or asserts timezone. Those tests therefore cannot detect the UTC− regression caused by the new conversion. The project's build, Selenium integration suite, browser, and network were unavailable under the run policy; no project tests were run.

## Worked code-judo proposal

Make the input representation explicit before constructing the calendar's local `Date`. A compact normalization boundary can branch on the original model value's actual representation, rather than applying offset arithmetic indiscriminately:

```ts
function calendar_date(value: string | number): Date {
  if (typeof value == "number") {
    const utc = new Date(value)
    return new Date(utc.getUTCFullYear(), utc.getUTCMonth(), utc.getUTCDate())
  } else {
    const local = new Date(value) // `_on_select` writes a local `toDateString()` value
    return new Date(local.getFullYear(), local.getMonth(), local.getDate())
  }
}
```

Use the same boundary for `value`, `min_date`, and `max_date`. Adapt the types to the project's actual wire values; the important invariant is to retain whether the source was a UTC-millisecond value or a local date string until its calendar components are extracted. This removes the offset multiplication and mutation, and makes the conversion direct: UTC fields for serialized Python dates, local fields for the date-only strings generated by Pikaday. If protocol values can arrive in further representations, define and test them explicitly rather than silently normalizing all values with one offset rule.

Tests should assert the input's initial displayed date and the picker bounds for a Python UTC-midnight date in both UTC− and UTC+ environments, and should confirm that selecting a date and rerendering preserves the selected day. These tests target the actual round-trip boundary and catch both the regression and the intended repair.
