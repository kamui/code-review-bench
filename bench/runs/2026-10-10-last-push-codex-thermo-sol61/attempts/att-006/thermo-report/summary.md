Production exploitability is unverified because Vercel's header filtering, routing and cache are unavailable.

## Finding F1: Scope query-path restoration to the ISR transport

In `packages/integrations/vercel/src/serverless/entrypoint.ts:24–25`, the new branch enables `x_astro_path` whenever the request carries `x-vercel-isr: 1`, including in the ordinary `_render` function of a deployment with ISR disabled. Calling that built handler with `/api/public?x_astro_path=/api/private` returns `{"id":"public"}` without the marker and `{"id":"private"}` with it, without a valid middleware secret. The existing security tests only exercise the query and path header separately, so they still pass. This leaks an ISR transport rule into general routing and makes the previous path-override boundary depend on external header filtering that the adapter does not express. Keep ordinary rendering's authenticated-header rule intact and attach query decoding specifically to the `_isr` handler generated by `VercelBuilder.buildISRFolder`, with an explicit internal-path check. Add handler-level tests for the positive ISR case and the marker-plus-query negative case on `_render`. The local routing regression is verified; bypassing Vercel edge authorization or poisoning its cache is not established. Full evidence and the worked restructuring are in [01_isr_transport.md](01_isr_transport.md).

## Remediation sequence

First add a regression test to the existing path-override security suite that combines the ISR marker with the query override on the non-ISR `_render` function. Assert that the public route still renders. Add a corresponding ISR handler test using `/_isr?x_astro_path=/one`, the marker, and the existing ISR fixture.

Then move the ISR decoder to the function boundary already owned by `buildISRFolder`. A generated ISR wrapper can normalize the transport URL and delegate to the existing renderer, while ordinary rendering retains its previous authentication rule. This removes ISR source inference from the shared request flow. A pathname guard in the current shared branch would narrow the problem, but would still leave `_render` interpreting an ISR transport URL; it is not the complete ownership fix.

Preserve authenticated middleware path precedence and check missing or invalid transport metadata explicitly. Run the focused suites once the implementation changes, then verify the generated wrapper and `.vc-config.json` handler selection together. Finally, validate the platform's header handling and a real ISR cache miss before making a deployment-security claim.
