# Thermo-nuclear review: grpc/grpc-go#6919 (migrate to google.golang.org/protobuf)

Range reviewed: `5051eeae537cb2839dd499e1a63a141098a3a03a..b8374114d485b6957b15d8769d7d5d96ddeaafc6` (`git diff main...review-head`, 68 files).

The change swaps `github.com/golang/protobuf` (APIv1) imports for `google.golang.org/protobuf` (APIv2) across the repository. For messages produced by a current `protoc-gen-go` the two APIs are interchangeable, and most of the diff is a faithful mechanical rename: I checked `ptypes.Is` against `Any.MessageIs`, `ptypes.UnmarshalAny` against `Any.UnmarshalTo` (including the RBAC, fault and router filter parsers and the HCM network filter), `ptypes.MarshalAny` against `anypb.New`, and the v1/v2 `Marshal`, `Unmarshal`, `Equal` and `Clone` call sites, and found them equivalent.

The problems are at the three places where the swapped `proto` import changes the meaning of a runtime type assertion or of a returned value for user-supplied messages. `proto.Message` used to mean `protoiface.MessageV1` (`Reset`/`String`/`ProtoMessage`) and now means `protoreflect.ProtoMessage` (`ProtoReflect`). Messages that only implement APIv1 (code generated by `protoc-gen-go` older than v1.20, gogo/protobuf output, hand-written v1 messages) satisfied the old interface and do not satisfy the new one. Such a message exists in this repository: `reflection/grpc_testing_not_regenerate/testv3.go`.

How this was checked: `go build ./...` and `go vet ./...` pass on the root module at head, and the focused tests of the changed packages pass (`status`, `internal/binarylog`, `encoding/proto`, `internal/testutils`, `xds/internal/httpfilter/fault`, `xds/internal/xdsclient/xdsresource/...`, `xds/internal/clusterspecifier/rls`, `xds/internal/xdsclient/xdslbregistry`, `balancer/rls/...`, `xds/internal/xdsclient/transport`, `binarylog`, `xds/csds`, `reflection`). Findings 1, 2, 3 and 6 were reproduced with a scratch test that uses the in-repo legacy message `pbv3.SearchRequestV3`, run against head through a `-overlay` file and against an extracted copy of `main`; every case passes on `main` and fails (or changes behaviour) on head. Not checked: the nested modules that need dependencies missing from the offline module cache (`gcp/observability`, `interop/observability`, `stats/opencensus`, `security/*`) could not be compiled, `staticcheck`/`vet.sh` could not be run, and the `test/tools` module could not be resolved offline.

## Findings

### 1. [High] Default proto codec now rejects APIv1-only messages, so every RPC that uses them fails

File: `encoding/proto/proto.go`, lines 27 and 40-54.

The only change in this file is the import (`github.com/golang/protobuf/proto` to `google.golang.org/protobuf/proto`), but the codec body is `vv, ok := v.(proto.Message)` followed by `proto.Marshal(vv)` / `proto.Unmarshal(data, vv)`. With the v2 import the assertion requires a `ProtoReflect` method. A message that implements only APIv1 used to pass the assertion and be marshaled through golang/protobuf's legacy wrapping; it now fails the assertion and the codec returns `failed to marshal, message is %T, want proto.Message` (and the matching unmarshal error).

Evidence: with the in-repo legacy service `SearchServiceV3` and a real client and server, on `main` `codec.Marshal(&pbv3.SearchRequestV3{Query: "q"})` returns `[10 1 113]` and the unary RPC succeeds. On head the same calls return `failed to marshal, message is *grpc_testing_not_regenerate.SearchRequestV3, want proto.Message`, `failed to unmarshal, message is ... want proto.Message`, and the RPC fails with `rpc error: code = Internal desc = grpc: error while marshaling: failed to marshal, message is *grpc_testing_not_regenerate.SearchRequestV3, want proto.Message`. `rpc_util.go:633-635` turns the codec error into that `Internal` status; the receive path fails the same way in `Unmarshal`.

Impact: this is the default codec for all of gRPC-Go. Any application whose request or response types are gogo/protobuf messages or come from pre-APIv2 generated code compiles unchanged and then fails every RPC at runtime after upgrading, on both client and server. Nothing in the diff signals that support for these messages is being dropped, and the existing tests only use APIv2 messages, so nothing catches it. The codec needs to keep accepting `protoadapt.MessageV1` and convert it with `protoadapt.MessageV2Of` before marshaling or unmarshaling.

### 2. [Medium] `Status.Details()` returns an internal wrapper instead of the caller's type for APIv1-only detail messages

File: `internal/status/status.go`, lines 152-166 (the loop at 157-164).

The old code decoded each detail with `ptypes.UnmarshalAny(any, &ptypes.DynamicAny{})` and appended `detail.Message`, which golang/protobuf unwraps back to the concrete registered Go type. The new code appends the result of `any.UnmarshalNew()` directly. For a legacy message type the registry's `MessageType.New().Interface()` is `*impl.messageIfaceWrapper`, not the user's struct.

Evidence: `status.New(codes.Internal, "x").WithDetails(&pbv3.SearchRequestV3{Query: "q"})` followed by `Details()` yields `*grpc_testing_not_regenerate.SearchRequestV3` on `main` and `*impl.messageIfaceWrapper` on head. The wrapper has no `String`/`ProtoMessage` methods, so it does not satisfy the v1 `proto.Message` interface either.

Impact: the public `status.Status.Details()` is documented and used as `switch d := detail.(type) { case *mypb.Foo: ... }`. For APIv1-only detail types that switch silently stops matching and callers lose their error details with no error and no compile failure. `WithDetails` still accepts these types (its parameter is `protoadapt.MessageV1`), so the round trip is asymmetric: the type put in is not the type that comes out. Details built from current generated code are unaffected. Passing the decoded message through `protoadapt.MessageV1Of` before appending restores the previous type for both kinds of message.

### 3. [Low] Binary logging records an empty payload for APIv1-only messages

File: `internal/binarylog/method_logger.go`, lines 242-251 (`ClientMessage.toProto`) and 282-291 (`ServerMessage.toProto`).

Both functions do `if m, ok := c.Message.(proto.Message); ok { data, err = proto.Marshal(m) } else if b, ok := c.Message.([]byte) ... else { grpclogLogger.Infof("binarylogging: message to log is neither proto.message nor []byte") }`. With the v2 import a legacy message falls through to the last branch and the entry is written with `Length: 0` and no data.

Evidence: `NewTruncatingMethodLogger(1<<20, 1<<20).Build(&binarylog.ServerMessage{Message: &pbv3.SearchRequestV3{Query: "q"}})` produces `len=3 data=[10 1 113]` on `main` and `len=0 data=[]` on head; `ClientMessage` behaves the same.

Impact: most call sites pass already-encoded bytes, but the unary server path passes the handler's reply object (`server.go:1470-1472`, `Message: reply`). With the default codec finding 1 fails that RPC first, so this is reachable for servers that register their own codec for legacy or gogo messages: their unary response entries in the binary log silently lose the payload, with only an info-level log line to show for it. Low because it is limited to that combination and affects only observability data.

### 4. [Low] Invalid `load_reporting_interval` error always prints `<nil>`

File: `xds/internal/xdsclient/transport/loadreport.go`, lines 173-177.

The new code is `if rInterval.CheckValid() != nil { return nil, 0, fmt.Errorf("invalid load_reporting_interval: %v", err) }`. The result of `CheckValid()` is discarded; `err` is the variable from `resp, err := stream.Recv()` at line 165, which is necessarily nil at this point because the function returned earlier otherwise. The old code formatted the error returned by `ptypes.Duration`.

Impact: when the management server sends a missing, out-of-range or sign-mismatched interval, the warning logged at line 124 reads `Reading from LRS stream failed: invalid load_reporting_interval: <nil>`, so the reason is lost. Control flow is unchanged (the stream is still abandoned and retried), which is why this is low. The fix is to capture the `CheckValid()` error and format that.

### 5. [Low] `test/tools/go.mod` downgrades `golang.org/x/tools` from v0.17.0 to v0.14.0

File: `test/tools/go.mod`, lines 7 and 16 (with the matching `test/tools/go.sum` changes).

Besides replacing `github.com/golang/protobuf` with `google.golang.org/protobuf` as the direct requirement (which the `tools.go` import change needs), the diff changes `golang.org/x/tools v0.17.0` to `v0.14.0`, re-adds `golang.org/x/sys v0.13.0 // indirect`, and moves `golang.org/x/sync` in `go.sum` from v0.6.0 to v0.4.0. The base commit of this very range, `5051eeae` "grpc: Update go mod (#6939)", had just raised x/tools from v0.15.0 to v0.17.0, so head ends up below both values. Nothing in the protobuf migration needs an older x/tools; the head commit is titled "resolve conflicts and add changes", which points to a merge resolution that kept the branch's stale side.

Impact: `vet.sh` installs `goimports` from this module (lines 35-39), so CI and developers would silently go back to a three-release-old `goimports`, and the dependency bump from #6939 is partly reverted without that being the purpose of the change. I could not resolve this module offline, so I have not confirmed whether the downgraded set builds or is tidy; the finding is the unintended revert itself.

### 6. [Low] Typed-nil messages are now marshaled as empty messages instead of being rejected

Files: `encoding/proto/proto.go`, line 45; `internal/status/status.go`, line 141.

golang/protobuf's `proto.Marshal` returned `proto: Marshal called with nil` for a typed nil pointer such as `(*pb.Resp)(nil)`. The v2 `proto.Marshal` and `anypb.New` treat a typed nil as an empty message and succeed.

Evidence: `codec.Marshal((*testpb.SimpleRequest)(nil))` returns `proto: Marshal called with nil` on `main` and `[], <nil>` on head. `status.New(codes.Internal, "x").WithDetails((*testpb.SimpleRequest)(nil))` returns that error on `main` and succeeds on head.

Impact: `encode` in `rpc_util.go:629-635` only filters an untyped nil ("typed nils will not be caught by this check"), so a handler that returns `(*pb.Resp)(nil), nil`, or a client that sends a typed-nil request, used to fail the RPC with `Internal: grpc: error while marshaling: proto: Marshal called with nil` and now puts an empty message on the wire. A programming error that was loud becomes a successful RPC carrying default values. This is a side effect of the library swap rather than a stated goal, so it should be either accepted explicitly or guarded in the codec.
