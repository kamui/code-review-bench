# Thermo-nuclear review: grpc/grpc-go#6919 (migrate to google.golang.org/protobuf)

Range reviewed: `5051eeae537cb2839dd499e1a63a141098a3a03a..b8374114d485b6957b15d8769d7d5d96ddeaafc6` (`git diff main...review-head`, 68 files).

The migration is mostly a mechanical import swap and that part is sound, but it changes runtime behaviour in three places that users can reach. The serious one is that the default `proto` codec now rejects every message that implements only the old golang/protobuf (APIv1) interface, so RPCs carrying such messages fail with `codes.Internal`.

How this was checked: the root module and the `examples` module build and vet clean at head, and the existing tests for the touched packages pass (reflection, status, encoding, internal/binarylog, internal/testutils, xds httpfilter/xdsresource/xdslbregistry/clusterspecifier/csds/transport, binarylog). Findings 1 to 4 were reproduced at head with throwaway probe tests injected through `go test -overlay` from the work directory; the clone was not modified. Base behaviour was established from the golang/protobuf v1.5.3 source and by calling the same golang/protobuf functions the base code called. The other sub-modules (gcp/observability, stats/opencensus, security/*, interop/observability) could not be built offline; none of their Go files import `github.com/golang/protobuf`.

## Findings

### 1. [High] Default proto codec now rejects APIv1-only messages, failing every RPC that uses them

**File:** `encoding/proto/proto.go`, lines 40-54 (caused by the import swap on line 27)

**Evidence.** The only edit in this file is the import: `github.com/golang/protobuf/proto` became `google.golang.org/protobuf/proto`. The codec body is unchanged, so `v.(proto.Message)` on lines 41 and 49 silently changed meaning. It used to assert the APIv1 interface (`Reset`/`String`/`ProtoMessage`), which every generated message satisfies. It now asserts the APIv2 interface, which requires `ProtoReflect()`. The old `proto.Marshal`/`proto.Unmarshal` wrapped v1-only messages through `MessageV2` internally; the new code never reaches that point, because the assertion fails first and nothing adapts the value (for example with `protoadapt.MessageV2Of`).

Messages that have no `ProtoReflect()` include code generated by protoc-gen-go older than v1.20, gogo/protobuf output, and hand-written v1 messages. The repository itself ships such a service: `reflection/grpc_testing_not_regenerate/testv3.go` (`SearchServiceV3`).

Reproduced at head:

- `encoding.GetCodec("proto").Marshal(&pbv3.SearchRequestV3{Query: "hello"})` returns `failed to marshal, message is *grpc_testing_not_regenerate.SearchRequestV3, want proto.Message`, while `golang/protobuf` `proto.Marshal` on the same value (what the base codec called) returns `0a0568656c6c6f`.
- `Unmarshal` into the same type fails with the matching `failed to unmarshal ...` error.
- A real unary call over a loopback listener to `SearchServiceV3.Search` fails with `rpc error: code = Internal desc = grpc: error while marshaling: failed to marshal, message is *grpc_testing_not_regenerate.SearchRequestV3, want proto.Message`.

**Impact.** Any client or server whose request or response types are APIv1-only stops working after upgrading: every send fails with `Internal` and every receive fails to decode. This is the default codec, so no opt-in is involved, and it compiles cleanly, so the break appears only at runtime. No existing test covers it (the reflection tests never send these messages over the wire), so CI stays green. The fix is to adapt v1 messages before marshalling and unmarshalling, accepting both `protoadapt.MessageV1` and `protoadapt.MessageV2`.

### 2. [Medium] `status.Details()` returns an opaque wrapper instead of the concrete type for APIv1-only detail messages

**File:** `internal/status/status.go`, lines 157-164

**Evidence.** `Details()` used `ptypes.UnmarshalAny(any, &ptypes.DynamicAny{})` and appended `detail.Message`, which golang/protobuf unwraps back to the registered Go type. It now appends the result of `any.UnmarshalNew()` directly (line 163). For a message type registered through the legacy v1 path, that value is the protobuf runtime's internal `*impl.messageIfaceWrapper`, not the user's type.

Reproduced at head with `status.New(codes.Internal, "x").WithDetails(&pbv3.SearchRequestV3{Query: "q"})`:

- new `Details()[0]` has type `*impl.messageIfaceWrapper`; the assertion to `*pbv3.SearchRequestV3` is false, and so is the assertion to golang/protobuf `proto.Message`.
- the old `ptypes.DynamicAny` path on the same `Any` yields `*grpc_testing_not_regenerate.SearchRequestV3`.

`WithDetails` on line 134 still takes `protoadapt.MessageV1`, so such messages are accepted on the way in but do not come back out as the same type.

**Impact.** The documented way to consume details is a type switch or assertion on the elements of `st.Details()`. For APIv1-only detail types that code stops matching, with no error and no compile failure, so error details are silently ignored on the client. Types that implement both APIs (all current protoc-gen-go output, including `errdetails`) are unaffected, which is why the existing tests pass. Passing the result through `protoadapt.MessageV1Of(detail)` before appending restores the old return types.

### 3. [Low] A typed-nil message now encodes as an empty message, so a handler returning `nil, nil` succeeds instead of failing

**File:** `encoding/proto/proto.go`, lines 40-46

**Evidence.** golang/protobuf `proto.Marshal` returned `ErrNil` (`proto: Marshal called with nil`) for a nil message pointer. `google.golang.org/protobuf/proto.Marshal` treats it as an empty message and returns no error. `encode` in `rpc_util.go` (line 630) only filters untyped nil, as its own comment says, so a typed nil reaches the codec.

Reproduced at head: `codec.Marshal((*testpb.SimpleResponse)(nil))` returns `[]` with a nil error, where the golang/protobuf call the base codec made returns `proto: Marshal called with nil`. End to end, a `UnaryCall` handler that returns `nil, nil` now gives the client an empty `SimpleResponse` with a nil error. At base the same handler produced `codes.Internal` (`grpc: error while marshaling: proto: Marshal called with nil`).

**Impact.** A server bug that used to surface as an explicit `Internal` error now reaches the client as a successful, zero-valued response. The same applies to `SendMsg` with a nil message pointer on streams. This is a silent wire-visible behaviour change that the PR does not mention; if it is intended it should be stated, otherwise the codec needs an explicit nil check.

### 4. [Low] Binary logging records an empty payload for APIv1-only messages

**File:** `internal/binarylog/method_logger.go`, lines 242 and 282 (caused by the import swap on line 31)

**Evidence.** Same mechanism as finding 1. `ClientMessage.toProto` and `ServerMessage.toProto` test `c.Message.(proto.Message)`, which is now the APIv2 interface. An APIv1-only message matches neither that branch nor the `[]byte` branch, so the function logs `binarylogging: message to log is neither proto.message nor []byte` and emits an entry with no data.

Reproduced at head with a hand-written v1 message: `(&ServerMessage{Message: m}).toProto()` and the `ClientMessage` equivalent both give `length=0` and empty `data`, while golang/protobuf marshals the same value to `0a0568656c6c6f`.

The message object, as opposed to already-encoded bytes, is passed at `server.go:1470` (`binarylog.ServerMessage{Message: reply}`), the unary server response path. The other call sites pass bytes and are unaffected.

**Impact.** For unary server responses whose type is APIv1-only, the binary log entry silently loses its payload and length. With the default codec this is masked by finding 1, because the RPC fails first. It is reachable on its own when a custom codec is registered (the usual setup for gogo-generated messages), and it remains after finding 1 is fixed unless this assertion is adapted too.

### 5. [Low] Invalid LRS `load_reporting_interval` error always prints `<nil>` instead of the cause

**File:** `xds/internal/xdsclient/transport/loadreport.go`, lines 173-176

**Evidence.** The new code is:

```go
rInterval := resp.GetLoadReportingInterval()
if rInterval.CheckValid() != nil {
	return nil, 0, fmt.Errorf("invalid load_reporting_interval: %v", err)
}
```

The result of `CheckValid()` is discarded. The `err` that is formatted is the one from `stream.Recv()` on line 165, which is already known to be nil here because line 166 returned otherwise. The old code formatted the error returned by `ptypes.Duration`.

**Impact.** When the management server sends a first `LoadStatsResponse` with a missing or out-of-range interval, the warning logged by the caller (`Reading from LRS stream failed: ...`, line 124) reads `invalid load_reporting_interval: <nil>`. The stream is still rejected correctly, so this is a loss of diagnostics only. Capture the `CheckValid()` error and format that.

### 6. [Low] `test/tools` pins `golang.org/x/tools` back from v0.17.0 to v0.14.0

**File:** `test/tools/go.mod`, line 7 (and matching lines in `test/tools/go.sum`)

**Evidence.** At the base, `test/tools/go.mod` requires `golang.org/x/tools v0.17.0`, set by the immediately preceding commit `5051eeae` ("grpc: Update go mod (#6939)"). At head it requires `v0.14.0`, and `golang.org/x/sys v0.13.0 // indirect` reappears because the older x/tools still needs it. `go.sum` drops the v0.17.0 hashes and moves `golang.org/x/sync` from v0.6.0 to v0.4.0. The downgrade arrives in the final merge commit (`b8374114`, "resolve conflicts and add changes") and has nothing to do with the protobuf migration. The other edits in this module (protobuf becoming a direct requirement, `tools.go` importing `google.golang.org/protobuf/cmd/protoc-gen-go`) are correct and match what `regenerate.sh` already installs.

**Impact.** `vet.sh` installs `goimports` from this module, so CI and contributors go back to a three-release-older x/tools, undoing part of #6939. Nothing breaks immediately; this looks like an accidental conflict-resolution revert and should be restored to v0.17.0. Whether `go mod tidy` is clean for this module could not be confirmed offline.

## Checked and not raised

- `ptypes.Is` to `Any.MessageIs` and `ptypes.UnmarshalAny` to `Any.UnmarshalTo` in the xDS LDS, filter-chain, fault, RBAC, router and RLS cluster-specifier code are equivalent for these proto3 messages, including nil `Any` handling. No validation was loosened on the RBAC path.
- `internal/pretty.ToJSON` switching the v1 branch from `jsonpb` to `protojson` only affects log output; the non-logging callers pass Go structs and take the `json` branch.
- `status.WithDetails` taking `protoadapt.MessageV1` is type-identical to the old golang/protobuf `proto.Message`, so the public signature does not break callers.
- `balancer/rls` `convertDuration` no longer rejects durations beyond the `time.Duration` range (about 292 years); `AsDuration` saturates instead. Probed and confirmed, but only reachable with absurd config values, and `max_age` is clamped anyway.
- `WithDetails` with a typed-nil detail now succeeds instead of returning `ErrNil`; same root cause as finding 3 and of negligible impact.
- `examples/go.mod` moving golang/protobuf to indirect is consistent: no example imports it, and the module vets clean.
