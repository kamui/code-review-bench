# Thermo Nuclear Review — django/django#17914 "Refs #33497 -- Added connection pool support for PostgreSQL."

Range reviewed: `bcccea3ef31c777b73cba41a6255cd866bf87237..fad334e1a9b54ea1acb8cce02a25934c5acfe99f` (`git diff main...review-head`).

The change adds an opt-in `OPTIONS["pool"]` for the PostgreSQL backend backed by `psycopg_pool.ConnectionPool`. The pool is held in a class-level dict keyed by alias, is created lazily from `get_connection_params()`, uses `DatabaseWrapper._configure_connection` as the pool `configure` hook, and `_close()` returns pooled connections with `putconn()`. I traced every new code path against the base wrapper (`connect`, `close`, `ensure_connection`, atomic handling), the test-database lifecycle in `django/db/backends/base/creation.py`, the parallel test runner, the settings-change signal handler, and the installed `psycopg_pool` implementation (`pool.py`: `_connect`, `getconn`, `putconn`, `open`, `close`). No PostgreSQL server is available, so I verified the behavioural claims below by driving the real `psycopg_pool.ConnectionPool` with a fake psycopg connection class (scripts in `clone-work/repro_assume_role.py` and `clone-work/repro_stale_pool.py`).

Four actionable findings follow, ordered by priority.

## Finding 1 — `OPTIONS["assume_role"]` combined with `OPTIONS["pool"]` can never connect: the pool's configure hook re-enters the Django wrapper and dead-locks on the pool itself

Priority: High

Files and lines: `django/db/backends/postgresql/base.py` lines 98–104 (`ensure_role`), 228–234 (pool created with `configure=self._configure_connection`), 369–383 (`_configure_connection`), 345–348 (`get_new_connection` pool branch); unchanged but relied upon: `django/db/backends/postgresql/operations.py` lines 192–193 (`compose_sql`) and `django/db/backends/postgresql/psycopg_any.py` lines 20–22 (`mogrify`).

Evidence: the new module-level `ensure_role(connection, ops, role_name)` builds the `SET ROLE` statement with `ops.compose_sql(...)`. `DatabaseOperations.compose_sql` is `mogrify(sql, params, self.connection)`, and `mogrify` does `with connection.cursor() as cursor:` where `connection` is the **Django `DatabaseWrapper`**, not the psycopg connection passed to `ensure_role`. The comment at lines 370–373 says the hook must "not access anything on self aside from variables", but `self.ops.compose_sql` does exactly that. When a pool is configured, `_configure_connection` is invoked by `ConnectionPool._connect()` from a pool worker thread (`AddConnection` tasks are always run by workers; see `psycopg_pool/pool.py` `_start_initial_tasks`, `_maybe_grow_pool`, `_add_connection`). From that thread `wrapper.cursor()` → `_cursor()` → `ensure_connection()`; `wrapper.connection` is still `None` because the main thread is blocked inside `get_new_connection()` waiting on `self.pool.getconn()`, so the worker calls `connect()` itself, which calls `get_new_connection()` → `self.pool.getconn()` and queues behind the main thread. No connection ever finishes configuration, so nothing is ever added to the pool; every worker and the main thread wait until `timeout` (default 30 s) and raise `PoolTimeout`. Workers then reschedule with backoff for `reconnect_timeout` (5 min) and give up. I reproduced this with the real `psycopg_pool` and a fake psycopg connection: `connection.connect()` with `{"pool": {...}, "assume_role": "some_role"}` fails after exactly the pool timeout with `psycopg_pool.PoolTimeout: couldn't get a connection after 3.00 sec`, the trace shows `compose_sql()` executing in thread `pool-1-worker-0` with `wrapper.connection is None`, and no `SET ROLE` was ever executed. Even in the rarer case where the wrapper already holds a connection when a replacement connection is configured, the worker thread would fail `validate_thread_sharing()` with "DatabaseWrapper objects created in a thread can only be used in that same thread", so the pool can never add a connection either way. Side effects: `connect()` running on the worker thread also resets the main thread's transaction bookkeeping (`in_atomic_block`, `savepoint_ids`, `needs_rollback`, `health_check_*`) concurrently, and each failed `_connect` leaks the raw psycopg connection object until garbage collection because the exception is raised after `connect()` succeeded.

Failure: any project that uses the documented `assume_role` option (docs/ref/databases.txt ~line 243) and turns on the new `pool` option gets a database that is unreachable: every first query of every request hangs for the pool timeout and then raises `django.db.utils.OperationalError` (the wrapped `PoolTimeout`). The new tests do not catch this because `test_connect_role_invalid_credentials` and `test_connect_pool*` never combine the two options. The hook should build `SET ROLE` without going through the wrapper (for example with `psycopg.sql.SQL("SET ROLE {}").format(sql.Identifier(role_name)).as_string(connection)` or a parameterised `SELECT set_config('role', %s, false)`), or `compose_sql` must be given the raw connection.

## Finding 2 — the pool freezes connection parameters and is keyed only by alias, so `settings_dict` changes made by the test-database machinery are silently ignored and a pre-existing pool keeps serving the original database

Priority: Medium

Files and lines: `django/db/backends/postgresql/base.py` lines 202–241 (`pool` property: `connect_kwargs = self.get_connection_params()` captured once, cached in class-level `_connection_pools[self.alias]`), 345–348 (`get_new_connection` ignores its `conn_params` argument when a pool exists), 243–246 (`close_pool`); `django/db/backends/postgresql/creation.py` lines 58–61 and 89–91 (only `_clone_test_db` and `_destroy_test_db` close the pool); relied upon: `django/db/backends/base/creation.py` lines 64–66 (`create_test_db` does `self.connection.close()` then rewrites `settings_dict["NAME"]`), 107–112 (`set_as_test_mirror`), 377–384 (`setup_worker_connection`).

Evidence: without a pool, every `connect()` re-reads `settings_dict` via `get_connection_params()`, which is what `create_test_db()`, `set_as_test_mirror()` and `setup_worker_connection()` rely on: they only call `self.connection.close()` and mutate `settings_dict["NAME"]` in place. With a pool, `get_new_connection()` discards the freshly computed `conn_params` and takes a connection from the pool whose `kwargs` were captured when the pool object was first created. Nothing invalidates the pool when `NAME` (or `USER`, `PASSWORD`, `HOST`, `PORT`, other `OPTIONS`) changes; the PR only handles `TIME_ZONE`/`USE_TZ` (via `ensure_timezone()` → `close_pool()`), cloning and destruction. Reproduced with the fake connection class: connect with `NAME="production_db"`, `close()`, set `settings_dict["NAME"] = "test_production_db"`, connect again: `get_connection_params()["dbname"]` is `test_production_db` but the physical connection handed out is the same object with `dbname='production_db'`. The precondition is that something opened a pooled connection for the alias before `create_test_db()` runs. In Django's own `runtests.py`/`DiscoverRunner` flow nothing does so (I checked `build_suite`, `get_databases`, `setup_databases`, and the import-time code of the test suite), but in user projects it is common for `AppConfig.ready()` or module-level code to query the database during `django.setup()`, which `manage.py test` runs before `setup_databases()`.

Failure: in that situation the test run creates `test_<name>` but then runs `migrate`, `createcachetable`, fixture loading, every test query and, for `TransactionTestCase`, the `flush` (TRUNCATE of all tables) against the **original** configured database, because every `connections[alias].connect()` is served by the stale pool. The same mechanism silently breaks `set_as_test_mirror()` for a mirror alias whose pool already exists. `create_test_db()` (and `set_as_test_mirror()`) need to close/discard the alias's pool alongside `self.connection.close()`, or the pool must be keyed on (alias, connection params) / recreated when `get_connection_params()` changes.

## Finding 3 — the process-global pool survives `fork()` without its worker threads; forked children (including `--parallel` test workers) are handed the parent's live sockets or time out

Priority: Low

Files and lines: `django/db/backends/postgresql/base.py` line 200 (`_connection_pools = {}` class attribute), 345–348 (`self.pool.open()` then `getconn()`); `django/db/backends/base/creation.py` lines 377–384 (`setup_worker_connection` only calls `close()`), `django/test/runner.py` lines 402–442 (`_init_worker`).

Evidence: `_connection_pools` is a class attribute, so it is copied into every forked child together with the `ConnectionPool` object. `psycopg_pool` is not fork-aware: in the child `_closed` is still `False`, so `ConnectionPool.open()` returns immediately from `_open()` (`if not self._closed: return`) and never respawns the scheduler or worker threads, which do not exist after `fork()`. `getconn()` then either pops an idle connection from the inherited deque — a psycopg connection object whose socket is shared with the parent and every sibling child — or, if the deque is empty, queues an `AddConnection` task that no worker will ever run and raises `PoolTimeout` after `timeout` seconds. I reproduced this with `os.fork()`: after `connection.close()` and changing `NAME` (exactly what `setup_worker_connection()` does), the child's `connect()` returned the very same connection object the parent had used (`pool kwargs dbname: production_db`) with `threading.enumerate()` showing only `MainThread`. The precondition is that a pool for the alias is open in the parent at fork time. Django's own parallel runner closes the pools during `_clone_test_db`, and `run_checks` does not open a connection for the default alias in the current code, so Django's suite is not affected today, but any project whose `AppConfig.ready()`, custom test runner or pre-fork server setup (gunicorn `--preload`, uWSGI, Celery prefork) touches the database before forking will be.

Failure: forked workers share one PostgreSQL socket between processes (protocol desynchronisation, "another command is already in progress", corrupted results) or hang for the pool timeout and fail with `OperationalError`. The non-pooled backend has no equivalent problem when the parent closed its connection before forking, so this is a regression specific to the pool option. At minimum `setup_worker_connection()` should call `close_pool()`, and the pool property should detect a PID change (compare `os.getpid()` recorded at creation) and discard an inherited pool.

## Finding 4 — documentation contradicts the implementation: `pool` is not "ignored with psycopg2", it raises `ImproperlyConfigured`, and the `CONN_MAX_AGE` restriction is undocumented

Priority: Low

Files and lines: `docs/ref/databases.txt` lines 270–271; `django/db/backends/postgresql/base.py` lines 290–292 (`get_connection_params` raises "Database pooling requires psycopg >= 3") and 209–212 (`pool` raises "Pooling doesn't support persistent connections" when `CONN_MAX_AGE != 0`).

Evidence: the new docs paragraph says "This option requires ``psycopg[pool]`` or :pypi:`psycopg-pool` to be installed and is ignored with ``psycopg2``." The code does the opposite: with psycopg2 any truthy `pool` makes `get_connection_params()` raise `ImproperlyConfigured`, and the PR's own `test_connect_pool_setting_ignored_for_psycopg2` asserts that `connect()` raises. Separately, enabling `pool` with a non-zero or `None` `CONN_MAX_AGE` raises `ImproperlyConfigured` lazily on first connect, but neither the `pool` section nor the `CONN_MAX_AGE`/persistent-connections section mentions the incompatibility.

Failure: a project on psycopg2 that follows the documentation and sets `pool` expecting a no-op fails to start with an `ImproperlyConfigured` error on the first database access; a project with persistent connections configured (a very common production setting) that adds `pool: True` likewise fails at first connect with no documentation pointing at the cause. Either the docs should say the option raises on psycopg2 and requires `CONN_MAX_AGE = 0`, or the code should match the documented "ignored" behaviour.

## Reviewed and not reported

- `BaseDatabaseWrapper.ensure_connection()` now raises `ProgrammingError` when `in_atomic_block and closed_in_transaction`. With a pool `_close()` sets `self.connection = None` inside an atomic block, so without this guard a nested query would silently open a fresh pooled connection outside the transaction; the guard is correct and `Atomic.__exit__` still handles `closed_in_transaction` by setting `connection.connection = None`. Non-pooled backends keep `self.connection` set in that state so their behaviour is unchanged.
- `_close()` returns the connection to `self.connection._pool` rather than `self.pool`; this is deliberate so that a connection checked out from a pool that was later closed by `ensure_timezone()` gets closed by `putconn()` instead of being pushed into a new pool. Verified against `ConnectionPool.putconn` → `_maybe_close_connection`.
- Pool connections are created with `autocommit=True` and `_configure_connection` only runs `SET`/`set_config` statements, so psycopg_pool's post-configure `transaction_status == IDLE` check passes (modulo Finding 1). `connect()` re-applies `set_autocommit()` and `isolation_level` on every checkout, so state left on a returned connection is reset where Django cares about it.
- `close_if_health_check_failed()` short-circuiting for pools is consistent with installing `check=ConnectionPool.check_connection` only when `CONN_HEALTH_CHECKS` is true; the `django_test_skips` additions match.
- The `pool` property is thread-safe enough for production: `setdefault()` ensures one winner, and unopened loser pools spawn no threads. `close_pool()` can raise `KeyError` if two threads close concurrently, but it is only reached from test-only paths (`ensure_timezone()` signal handler, test DB creation).
- `_nodb_cursor()` connections use `NO_DB_ALIAS` and correctly bypass the pool, so `CREATE/DROP DATABASE` from the postgres maintenance database is unaffected; `_clone_test_db`/`_destroy_test_db` correctly close the pool first so the template/test database has no lingering sessions.
- The other `connection.copy()` call sites in the suite (`select_for_update`, `delete_regress`, `backends/tests.py`, `test_utils`) do not mutate connection parameters, so sharing the alias's pool is harmless for them.
