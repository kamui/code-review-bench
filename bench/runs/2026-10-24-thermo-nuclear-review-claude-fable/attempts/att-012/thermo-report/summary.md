# Thermo Nuclear Review: grpc/grpc-go#6919 (migrate to google.golang.org/protobuf)

Range reviewed: `5051eeae537cb2839dd499e1a63a141098a3a03a..b8374114d485b6957b15d8769d7d5d96ddeaafc6` (`git diff main...review-head`, 68 files, +165/-174).

The change swaps `github.com/golang/protobuf` (APIv1) imports for `google.golang.org/protobuf` (APIv2) across the repository, replacing `ptypes` helpers with `durationpb`/`timestamppb`/`anypb` methods, and changes `status.WithDetails` to take `protoadapt.MessageV1`. I read the full diff, traced each changed non-test call site into its callers and into the dependency sources in the module cache, compiled the root module (`go build ./...`, `go vet` on every changed package), ran the unit tests of every affected package (all pass), and ran one overlay probe test against the new codec. The clone was left unchanged (tree `73b0ffd6…` before and after).

What I verified as safe and am not reporting: the public `(*Status).WithDetails` signature moving from `github.com/golang/protobuf/proto.Message` to `protoadapt.MessageV1` is not an API break, because both are aliases of `protoiface.MessageV1` (confirmed in `golang/protobuf@v1.5.3/proto/proto.go:50` and `protobuf@v1.32.0/protoadapt/convert.go:15`). `anypb.Any.MessageIs`/`UnmarshalTo` are semantically equivalent to `ptypes.Is`/`ptypes.UnmarshalAny` (same suffix-after-slash matching, same reset-then-unmarshal), and no test in the repo asserts on the changed error strings. `timestamppb.Now()` and `durationpb.New` are drop-in replacements. `pretty.ToJSON` with `protojson.MarshalOptions{Indent}` keeps multiline output because a non-empty `Indent` implies `Multiline`. `examples/go.mod` moving `github.com/golang/protobuf` to indirect is correct: no non-generated file under `examples/` imports it any more.

## Findings

### 1. High — `encoding/proto` default codec no longer accepts APIv1-only messages (gogo/protobuf and pre-1.4 protoc-gen-go output)

File: `encoding/proto/proto.go`, lines 41-53.

Evidence: at the base revision the codec did `v.(proto.Message)` with `proto` = `github.com/golang/protobuf/proto`, so `proto.Message` was `protoiface.MessageV1` (`Reset/String/ProtoMessage`) and `proto.Marshal`/`proto.Unmarshal` went through `protoimpl.X.ProtoMessageV2Of(m)` (`golang/protobuf@v1.5.3/proto/proto.go:61`, `wire.go:22,56`), which wraps any struct-tagged legacy message into an APIv2 message. At HEAD the import is `google.golang.org/protobuf/proto`, so `proto.Message` is now `protoreflect.ProtoMessage` (requires a `ProtoReflect()` method) and the assertion at lines 41 and 49 fails for any message that only implements the v1 interface. Nothing re-adds the v1 path: the file has no `protoadapt.MessageV1` branch, and `grep` shows no other adapter in the package.

I confirmed this empirically with an overlay test (not added to the clone) defining a struct-tagged type with `Reset/String/ProtoMessage` but no `ProtoReflect`. `proto.Marshal(protoadapt.MessageV2Of(msg))` succeeds, demonstrating the legacy wrap path the base codec relied on works, while the HEAD codec returns:

```
failed to marshal, message is *proto.legacyMsg, want proto.Message
failed to unmarshal, message is *proto.legacyMsg, want proto.Message
```

Failure: every gRPC user whose request/response types are generated by `gogo/protobuf` or by `protoc-gen-go` older than v1.4.0 (both implement only the v1 interface) will have every RPC fail at the codec with `codes.Internal` "grpc: error while marshaling" / "grpc: failed to unmarshal the received message", on both client and server, with no migration path other than registering a custom codec. This is a silent compatibility break in the default codec of a library with strict backward-compatibility guarantees; the PR intent (import migration) does not imply dropping v1 message support. The fix is to accept both interfaces, e.g. switch on `protoadapt.MessageV1` (wrap via `protoadapt.MessageV2Of`) and `protoadapt.MessageV2`.

### 2. Medium — `recvFirstLoadStatsResponse` reports the wrong variable in the invalid-interval error

File: `xds/internal/xdsclient/transport/loadreport.go`, lines 173-177.

Evidence: the new code is

```go
rInterval := resp.GetLoadReportingInterval()
if rInterval.CheckValid() != nil {
    return nil, 0, fmt.Errorf("invalid load_reporting_interval: %v", err)
}
interval := rInterval.AsDuration()
```

`err` here is the `stream.Recv()` error declared at line 164, which is necessarily `nil` at this point (the function returned early otherwise). The result of `rInterval.CheckValid()` is discarded. Before the change `ptypes.Duration` returned the validation error and it was logged.

Failure: when a management server sends a nil or out-of-range `load_reporting_interval`, the LRS stream still fails (control flow is correct), but the returned error, which `reportLoad` logs as the reason the stream was torn down, reads `invalid load_reporting_interval: <nil>`, hiding the actual validation failure. Functional behavior is unchanged; this is a diagnostics regression introduced by the rewrite and should be `err := rInterval.CheckValid(); err != nil`.

### 3. Low — `internal/binarylog` silently drops payloads of APIv1-only messages

File: `internal/binarylog/method_logger.go`, lines 242-243 and 282-283.

Evidence: `ClientMessage.toProto` and `ServerMessage.toProto` do `c.Message.(proto.Message)` with the import switched from v1 to v2 `proto`. As in finding 1, a message implementing only `Reset/String/ProtoMessage` no longer satisfies the assertion, falls to the final `else`, logs `binarylogging: message to log is neither proto.message nor []byte` at Info level, and produces a `GrpcLogEntry` with `Length: 0` and empty `Data`.

Failure: for users of legacy-generated messages who enable binary logging (`GRPC_BINARY_LOG_FILTER`), message payloads vanish from the log without an error. In practice finding 1 already fails such RPCs at the codec, so this is subordinate to it, but it needs the same `protoadapt` handling if finding 1 is fixed.

### 4. Low — `test/tools` downgrades `golang.org/x/tools` from v0.17.0 to v0.14.0 and the module may not be tidy

File: `test/tools/go.mod`, lines 7-9 and 16; `test/tools/go.sum`.

Evidence: the PR's stated purpose is to swap `github.com/golang/protobuf/protoc-gen-go` for `google.golang.org/protobuf/cmd/protoc-gen-go`, but the diff also rewrites the unrelated `golang.org/x/tools v0.17.0` requirement to `v0.14.0`, adds `golang.org/x/sys v0.13.0 // indirect`, and swaps `golang.org/x/sync v0.6.0` for `v0.4.0` in `go.sum`. The last commit in the range is titled "resolve conflicts and add changes", which is consistent with a stale merge resolution rather than an intentional downgrade. `vet.sh` installs `goimports` and `staticcheck` from this module (lines 36-40) and runs `go mod tidy -compat=1.19` in every module and fails on any resulting diff (lines 109-120). I could not run `go mod tidy` for this module offline because the cache does not contain `golang.org/x/tools@v0.14.0` or its graph, so tidiness is unverified.

Failure: the vet toolchain regresses three minor versions of `goimports` with no explanation, and if the hand-edited `go.sum` is not exactly what `go mod tidy` produces, the `vet.sh` tidy check will fail CI. This is a devex concern, not a runtime one; restoring `v0.17.0` and re-running `go mod tidy` in `test/tools` resolves it.

### 5. Low — duration overflow is now silently saturated instead of rejected

Files: `balancer/rls/config.go`, line 310; `xds/internal/xdsclient/transport/loadreport.go`, lines 174-177.

Evidence: `ptypes.Duration` (`golang/protobuf@v1.5.3/ptypes/duration.go:26-37`) returned `duration: %v is out of range for time.Duration` for valid protobuf Durations whose value exceeds the ~292-year `time.Duration` range. The replacements `d.CheckValid()` only validate the protobuf range (±10000 years), and `d.AsDuration()` documents that it "uses saturation arithmetic" and clamps to `math.MaxInt64`/`math.MinInt64` (`durationpb/duration.pb.go:63-65,171-184`). `convertDuration` also now returns the saturated value alongside the error rather than `0`; all three callers (lines 210, 222, 226) check the error first, so that part is harmless.

Failure: an RLS `lookup_service_timeout`/`max_age`/`stale_age` or an LRS `load_reporting_interval` of, say, 10^10 seconds was previously a rejected config and is now accepted as `math.MaxInt64` nanoseconds. The practical impact is negligible (a ~292-year timer), so this is noted only so the author is aware the validation surface shrank.

## Not findings, checked

- `internal/testutils/marshal_any.go` and `internal/testutils/xds/e2e/clientresources.go` narrowed their parameter to APIv2 `proto.Message`; all in-repo callers pass generated APIv2 types (compile verified).
- The remaining `github.com/golang/protobuf` imports (`channelz/service`, `credentials`, `xds/internal/xdsclient/bootstrap`, `internal/pretty`, `reflection/grpc_testing_not_regenerate`) are untouched by this PR, so the root `go.mod` direct requirement remains correct.
- `vet.sh`'s existing ptypes-rename check (line 97) is unaffected by the diff.
