# Thermo Nuclear Review: grpc/grpc-go#6919 (`5051eeae..b8374114`)

The branch migrates most call sites from `github.com/golang/protobuf` (APIv1) to `google.golang.org/protobuf` (APIv2): `proto.Marshal`/`Unmarshal`/`Equal`, `ptypes.UnmarshalAny` → `Any.UnmarshalTo`, `ptypes.Is` → `Any.MessageIs`, `ptypes.Duration`/`DurationProto` → `durationpb`, `ptypes.TimestampProto` → `timestamppb.Now`, `jsonpb` → `protojson`, plus the `test/tools` and `examples` module files. The `channelz` package is intentionally left on APIv1 (commit "revert changes in channelz"), and `internal/pretty` keeps the `protov1` import for its v1 branch.

What I verified: `go build ./...` and `go vet ./...` on the root module succeed with the pinned module cache; `go test` passes for every touched package I could run (`encoding/...`, `status`, `balancer/rls/...`, `balancer/grpclb`, `internal/binarylog`, `internal/testutils/...`, `binarylog`, `orca`, `stats`, `xds/csds`, `xds/internal/httpfilter/...`, `xds/internal/clusterspecifier/...`, `xds/internal/resolver`, `xds/internal/xdsclient/{transport,xdsresource,xdslbregistry,bootstrap}`, `internal/xds/rbac`). I also traced the semantic equivalence of each replaced helper against the vendored `github.com/golang/protobuf@v1.5.3` and `google.golang.org/protobuf@v1.32.0` sources: `Any.MessageIs`/`UnmarshalTo` perform the same type-URL check and required-field validation as `ptypes.Is`/`UnmarshalAny`; `durationpb.New`/`timestamppb.Now` produce identical protos; the `balancer/rls` `convertDuration` callers all check the returned error before using the value; `anypb.New(protoadapt.MessageV2Of(detail))` yields the same `type.googleapis.com/` URL as `ptypes.MarshalAny`. The `test/tools/tools.go` switch to `google.golang.org/protobuf/cmd/protoc-gen-go` matches what `regenerate.sh` already installs. I could not build the `examples` or `test/tools` modules because their dependencies are not in the offline module cache.

Two of the changes do alter observable behaviour for messages generated by pre-APIv2 tooling (protoc-gen-go < v1.20, or gogo/protobuf), which the base code supported. I confirmed both empirically with a Go overlay test (kept outside the clone) that defines a minimal APIv1-only message type with `Reset`/`String`/`ProtoMessage` methods and `protobuf:"..."` struct tags and registers it via `github.com/golang/protobuf/proto.RegisterType`.

## Findings

### [High] Default `proto` codec now rejects every APIv1-only message type (`encoding/proto/proto.go:27,41-53`)

File: `encoding/proto/proto.go`, lines 27 and 41-53. The codec's import changed from `github.com/golang/protobuf/proto` to `google.golang.org/protobuf/proto`, so the type assertion `v.(proto.Message)` in `codec.Marshal` (line 41) and `codec.Unmarshal` (line 49) now checks for `protoreflect.ProtoMessage` (requires a `ProtoReflect()` method, see `google.golang.org/protobuf@v1.32.0/proto/proto.go:24`) instead of `protoiface.MessageV1` (`Reset`/`String`/`ProtoMessage`, see `github.com/golang/protobuf@v1.5.3/proto/proto.go:50`). At the base revision the v1 `proto.Marshal` accepted both generations of messages because `marshalAppend` (`github.com/golang/protobuf@v1.5.3/proto/wire.go:32-36`) wraps the value with `MessageV2(m)` before delegating to APIv2; the new code has no such fallback, and APIv1-only types do not implement `ProtoReflect()`. Evidence: with an overlay test defining a legacy message, `encoding.GetCodec("proto").Marshal(&legacyMsg{})` returns `failed to marshal, message is *status_test.legacyMsg, want proto.Message` and `Unmarshal` returns the matching `failed to unmarshal ...` error, while `github.com/golang/protobuf/proto.Marshal` on the same value succeeds. Consequence: any application whose request/response types were generated by protoc-gen-go older than v1.20, or by gogo/protobuf, and that relies on gRPC's default codec (the overwhelmingly common case) has every RPC fail: clients get `codes.Internal` "grpc: error while marshaling: failed to marshal, message is *T, want proto.Message" from `encode` (`rpc_util.go:629-636`) and servers fail to decode every incoming request. This is a silent breaking change in grpc-go's most central path, is not part of the stated intent (an import migration), and is avoidable: the codec should accept `protoadapt.MessageV1` values and wrap them with `protoadapt.MessageV2Of` (and accept `protoadapt.MessageV2` directly), the way `internal/status/status.go` `WithDetails` now does.

### [Medium] `Status.Details()` returns an internal wrapper type instead of the concrete message for APIv1-only detail types (`internal/status/status.go:158-163`)

File: `internal/status/status.go`, lines 158-163 (exported through `status.Status`, whose `Details()` doc at lines 150-151 promises "a slice of details messages"). The base code decoded each `Any` via `ptypes.DynamicAny`, whose `Empty` path (`github.com/golang/protobuf@v1.5.3/ptypes/any.go:68-78`) returns `proto.MessageV1(mt.New().Interface())`, i.e. it unwraps back to the registered Go type. The new code appends `any.UnmarshalNew()` directly. For messages that lack `ProtoReflect()`, `MessageInfo.New()` (`google.golang.org/protobuf@v1.32.0/internal/impl/message.go:225-231`) falls into `mi.MessageOf(m)`, and `messageReflectWrapper.Interface()` (`internal/impl/message_reflect_gen.go:140-145`) returns `(*messageIfaceWrapper)(m)` rather than the original pointer. Evidence: in the overlay test, `status.New(codes.Internal, "x").WithDetails(&legacyMsg{...})` succeeds (the new `protoadapt.MessageV2Of` wrapping in `WithDetails` is correct), but `st.Details()[0]` has dynamic type `*impl.messageIfaceWrapper`, so the assertion `ds[0].(*legacyMsg)` fails; at the base revision the same call returned `*legacyMsg`. Consequence: callers that type-switch on `Details()` results (the documented usage pattern for rich errors) silently stop matching for any detail type generated by pre-APIv2 protoc-gen-go or gogo/protobuf, with no error returned. The `WithDetails` side explicitly kept APIv1 compatibility by taking `protoadapt.MessageV1`, so the asymmetric `Details()` behaviour looks unintended. Converting the decoded message back with `protoadapt.MessageV1Of(detail)` (or keeping the v1 unwrap for non-`ProtoReflect` types) would preserve the previous contract.

### [Low] LRS interval validation error reports a stale `err` instead of the actual `CheckValid` error (`xds/internal/xdsclient/transport/loadreport.go:173-175`)

File: `xds/internal/xdsclient/transport/loadreport.go`, lines 173-175. The rewrite drops the result of `rInterval.CheckValid()` and formats the enclosing function's `err` variable, which at that point is the `nil` returned by `stream.Recv()` on line 164 (the function would already have returned if it were non-nil). The base code formatted the error returned by `ptypes.Duration`. Consequence: when a management server sends a `load_reporting_interval` that fails validation (for example out-of-range seconds or nanos, `durationpb.CheckValid`), the LRS stream still terminates correctly, but the logged/returned error reads `invalid load_reporting_interval: <nil>`, hiding the reason. The code compiles only because `err` happens to be in scope, which is why neither `go vet` nor the existing tests catch it. The `if` should capture the error: `if err := rInterval.CheckValid(); err != nil { ... }`.

### [Low] `test/tools` module silently downgrades `golang.org/x/tools` from v0.17.0 to v0.14.0 (`test/tools/go.mod:7`, `test/tools/go.sum`)

File: `test/tools/go.mod`, line 7, and the corresponding `test/tools/go.sum` entries. The merge-base (`5051eeae`, "grpc: Update go mod (#6939)") pins `golang.org/x/tools v0.17.0`; the head's "resolve conflicts and add changes" commit replaces it with `v0.14.0`, drops the `golang.org/x/sync v0.6.0` and `x/tools v0.17.0` sums, and adds `golang.org/x/sync v0.4.0`/`golang.org/x/sys v0.13.0`. `vet.sh -install` installs `goimports` and `staticcheck` from exactly this module (`vet.sh:35-41`), so CI and local vet runs would go back to three-minor-versions-older tooling. Nothing in the branch's intent (migrating protobuf imports) calls for this; it is a stale branch state that won the conflict resolution. I could not run `go mod tidy` for this module offline (its dependencies are not in the module cache), so I cannot say whether vet.sh's tidy-and-clean-tree check (`vet.sh:116-118`) would additionally fail; the dependency regression itself is the finding. The `x/tools` requirement should be restored to `v0.17.0` and the sums regenerated.

## Checked and found acceptable

- `balancer/rls/config.go` `convertDuration`: `d.AsDuration(), d.CheckValid()` returns a non-zero duration alongside an error for invalid input (the base returned 0), but all three callers (lines 210, 222, 226) return on error before using the value.
- `internal/pretty/pretty.go`: `protojson.MarshalOptions{Indent}` on `protov1.MessageV2(ee)` is equivalent to the previous `jsonpb.Marshaler{Indent}` for logging purposes; the `Any` resolution failure fallback is retained.
- `internal/binarylog/method_logger.go`: `timestamppb.Now()` and `durationpb.New` match the removed `ptypes` helpers; the `Timeout > 0` guard is preserved.
- xds `unwrapHTTPFilterConfig`/`processHTTPFilterOverrides`/`processNetworkFilters` and the filter/cluster-specifier parsers: `Any.MessageIs`/`UnmarshalTo` reproduce `ptypes.Is`/`UnmarshalAny` semantics, including nil safety (`GetTypeUrl()` on a nil `*Any`).
- `internal/transport/{http2_server,handler_server}.go` and `internal/binarylog/sink.go`: `proto.Marshal` targets (`*spb.Status`, `*binlogpb.GrpcLogEntry`) are APIv2-generated.
- `status_test.go` expected-error change to `protoimpl.X.NewError("invalid empty type URL")` matches `anypb.UnmarshalNew` (`any.pb.go:302-303`) and the `status` tests pass.
- `examples/go.mod` moving `github.com/golang/protobuf` to indirect: no non-generated file under `examples/` imports it any more.
- `WithDetails(details ...protoadapt.MessageV1)`: `protoadapt.MessageV1` is the same `protoiface.MessageV1` type the old `proto.Message` alias resolved to, so the exported signature is unchanged.
