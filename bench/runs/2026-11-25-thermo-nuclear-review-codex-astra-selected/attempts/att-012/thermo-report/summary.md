**[P1] Invalidate the cached pool when switching to the test database**

django/db/backends/postgresql/base.py:345–348. When a pool has been initialized before test database setup, this checkout ignores the newly computed connection parameters and keeps using the pool for the original database. BaseDatabaseCreation.create_test_db() closes the wrapper and changes NAME before calling migrate, but the new _close() only returns the connection to the pool; it neither closes nor invalidates that pool. This also occurs without any application startup query: if access to the postgres maintenance database is denied, _nodb_cursor() falls back to an application-database wrapper with the same alias, creating and retaining that alias’s pool during CREATE DATABASE. The subsequent migrations and tests therefore run against the original application database, where test writes and TransactionTestCase flushes can alter or delete application data. An offline reproduction exercised the actual fallback and create_test_db() path with fake driver connections: at the migrate call, settings NAME was test_application while the checked-out connection still targeted application. Close/invalidate the pool before test database name transitions, and keep maintenance fallback connections outside the application pool.

**[P1] Avoid reopening the Django wrapper from the pool configure callback**

django/db/backends/postgresql/base.py:98–102. With both pool and assume_role enabled, ensure_role() calls ops.compose_sql() from a pool worker. DatabaseOperations.compose_sql() passes the Django wrapper to psycopg_any.mogrify(), which calls that wrapper’s cursor(). During initial pool creation the wrapper has no connection yet, so this re-enters ensure_connection() and waits on getconn() from the same pool that the worker is still configuring. No initial connection can finish configuration, and requests time out instead of connecting. A reproduction using the real psycopg_pool worker and queue with fake driver connections recorded two checkout requests for one initial connection and raised Django OperationalError after the configured timeout. Compose SET ROLE using the raw connection supplied to the configure callback, without accessing a cursor on the owning Django wrapper.

**[P2] Accept an empty dictionary as pool configuration**

django/db/backends/postgresql/base.py:204–206. The documented dictionary form of OPTIONS["pool"] includes an empty dictionary, which should pass no overrides to ConnectionPool and use its defaults. The truthiness check instead returns None for {}, so get_new_connection() opens ordinary direct connections and close() destroys them. An application using OPTIONS={"pool": {}} therefore silently receives no pooling at all, including no default bound on the number of pooled connections. The offline check confirmed that this configuration returns no pool. Distinguish an absent or explicitly disabled option from an empty options dictionary.

**[P3] Correct the documented psycopg2 behavior**

docs/ref/databases.txt:270–271. The statement that pool is ignored with psycopg2 contradicts the new get_connection_params() branch at postgresql/base.py:290–292, which raises ImproperlyConfigured("Database pooling requires psycopg >= 3") for a truthy pool option. The added psycopg2 test explicitly expects that exception as well. Following this compatibility statement and leaving pool=True in settings for a psycopg2 environment prevents database connections instead of falling back to unpooled operation. Document that enabling pooling requires psycopg 3 and must be disabled when using psycopg2.
