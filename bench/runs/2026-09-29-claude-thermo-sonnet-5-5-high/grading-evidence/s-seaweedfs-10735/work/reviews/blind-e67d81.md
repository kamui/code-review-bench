# Review blind-e67d81

### Item 1
Location: weed/filer/redis2/universal_redis_store.go:205-219
Claim: **1. Two divergent stale-member reaping policies now live side by side in one loop (`weed/filer/redis2/universal_redis_store.go`, lines 205-219).** In `ListDirectoryEntries` the not-found branch calls the new `removeOrphanedDirectoryListMember`, which does ZREM, then EXISTS, then a conditional ZAddNX. Ten lines below, the logical-expiry branch does a bare `Del` on the value followed by a bare `ZRem`, both with results discarded and no restore. The PR description itself admits the expiry branch has the same race with a worse outcome (a concurrent insert loses the value, not just the index membership). So the reader of this loop must now hold two mental models of "reap a dead entry", one of which the author knows to be unsafe, and the two sit in adjacent branches of the same `if`. This is the missed code-judo opportunity: introduce a single `reapStaleEntry`-style helper that owns both cases (value already gone, value logically expired) and make the loop body a plain call. The expiry case would then get its fix in one place instead of remaining a documented known bug next to a fixed sibling. If the author does not want to touch the expiry semantics in this PR, at minimum the helper should be named and placed so the expiry branch can adopt it, and a TODO with the failure scenario should sit on the expiry branch.

### Item 2
Location: weed/filer/redis2/universal_redis_store.go:237-252
Claim: **2. The compensating restore protocol is a hand-rolled, non-atomic three-step sequence that swallows every error (`universal_redis_store.go`, lines 237-252).** `removeOrphanedDirectoryListMember` issues ZREM, then EXISTS, then ZAddNX as three independent round trips. Every failure is silently dropped: a failed ZREM returns quietly, a failed ZAddNX is not even inspected, and nothing is logged. The PR description says errors "are no longer discarded outright", but the function has no return value and no logging, so an operator cannot tell a repair was attempted or failed; only the pre-existing `glog.V(0)` "not found" line is emitted, and it fires before any cleanup, so it still logs once per orphan even though the repair is now the point. The protocol also has a residual window that the comment does not mention: a `DeleteEntry` that lands between the EXISTS (value present) and the ZAddNX will DEL the value and ZREM the member, after which the ZAddNX re-adds an orphan. That is benign because the next listing reaps it, but it shows the sequence is a convergence argument rather than an invariant, which is a lot for a reader to verify from a 15-line function. The signature also carries redundant inputs: `dirListKey`, `path`, and `fileName` all describe one directory child, and `path` is used only to rebuild a key. Return an error (or take a logger) so the caller decides, log at a level that shows the repair, and derive the keys inside the helper from `(dirPath, fileName)`. A simpler alternative that deletes the whole compensation dance is worth weighing: have `UpdateEntry` (which currently only calls `doInsertEntry`) also `ZAddNX` the member for non-super-large directories. That makes membership self-healing on any write, the race becomes harmless by construction, and the restore step, the extra EXISTS read, and the helper's second half all disappear, at the cost of one extra round trip on updates.

### Item 3
Location: weed/filer/redis2/universal_redis_store.go:86
Claim: **3. The physical-versus-logical TTL mismatch that produces the orphans is left in place, so the fix is a permanent repair loop on the read path (`universal_redis_store.go`, lines 86 and 214-219).** The description shows that Redis drops the key at `set_time + TtlSec` while the logical check fires at `Crtime + TtlSec`, so under TTL workloads the logical-expiry branch is effectively dead code and every TTL entry is reaped by the not-found repair path, at the price of an extra ZREM plus EXISTS round trip per dead member (the restore check runs even though the value is known gone). The author deliberately excluded the alternative of setting the physical TTL slightly later than the logical one. That is a reasonable scope call, but it means the PR converts the intended design (logical expiry deletes both value and member) into an accidental one (physical expiry, then listing-time repair) and blesses it with tests. The remedy is to file the follow-up and reference it at the `Set` call site so the accidental path is not mistaken for the design.
