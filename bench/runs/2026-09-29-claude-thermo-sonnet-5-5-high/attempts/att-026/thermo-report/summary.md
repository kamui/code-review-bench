# Thermo-nuclear code quality review: jonhadfield/soba#195 "refactor: resolve SonarQube findings"

Range reviewed: `c77f548..136a485` (`git diff main...review-head`), 4 files, +312/-305, one commit. The PR was already merged; this review is written against the head commit as if it were still open.

## Verdict

Not approved as a structural refactor, though nothing in it is a correctness regression. The behaviour-preservation claim holds up: `go build`, `go vet` and `go test ./internal/ -count=1` all pass offline in this checkout, and reading the diff line by line I could not find a log line, exit path or provider ordering that changed. No file crosses 1000 lines: `internal/backup.go` grows from 729 to 774 lines and `internal/backup_test.go` is 989 lines after the change.

The problem is that the PR is a metric-driven refactor. It satisfies the SonarQube cognitive-complexity rule by cutting long functions into pieces, and it mostly does not delete any complexity. The five provider blocks of `displayStartupConfig` became five near-identical functions. The "env var is set and non-empty" predicate is still hand-written in about fifteen places. The package-global `job` is still assigned as a side effect, now from inside a helper. `createWorkingDir` re-implements a helper that already exists in the same file. The PR did add one good abstraction, the shared `logProvider*` helpers, and stopped short of the obvious next step. It also carried forward two small defects on lines it rewrote, a typo in a log message and a stray invisible character in the notification titles.

The detail file `01_internal_backup_and_notify.md` carries the evidence, commands and worked proposals for every finding below. `02_docker_and_tests.md` covers the Dockerfile and the test file.

## Findings

**1. The five `display*StartupConfig` functions are the same function five times (`internal/backup.go:233-293`).** `displayGitHubStartupConfig`, `displayGiteaStartupConfig`, `displayGitLabStartupConfig`, `displayBitBucketStartupConfig` and `displayAzureDevOpsStartupConfig` each open with "return unless this provider's token env var is set and non-empty" and then call some subset of `logProviderOrgs`, `logProviderBackupsToKeep`, `logProviderCompareMethod` and `logProviderBackupLFS` with a label and an env var name. The PR correctly found the shared pieces and then stopped one step short: the remaining difference between providers is pure data, namely the label, the gating env var, and which of orgs, backups-to-keep, compare and LFS env vars exist. A single table of provider descriptors (label, gate variable, optional orgs, backups, compare and LFS variables) plus one loop would replace roughly sixty lines of function bodies and five function names with about twenty lines, and adding a provider would be one table row. The same table could feed `collectProviderBackupResults` and `enabledProviderAuth`, which currently encode the same "provider to env var" knowledge in three separate places. As written the refactor lowers each function's complexity score but leaves the reader holding the same number of concepts; the special cases (GitHub's skip-user-repos line, GitLab's minimum access level, the mixed-case "Gitlab backup LFS" label) are still scattered rather than expressed as data.

**2. The "variable is defined and non-empty" predicate is copy-pasted about fifteen times, and the new Bitbucket helpers are not reused where they should be (`internal/backup.go:97-139, 233-293, 348-395`).** Every provider gate is spelled `if v, ok := GetEnvOrFile(x); ok && v != ""` (or the inverted `!ok || v == ""`), the Bitbucket helpers spell it four more times, and `checkJustTokenProvider` and `checkUserAndPasswordProvider` each spell a slightly different `strings.Trim(val, " ") == ""` variant. A one-line `envDefined(name string) bool` in `envfile.go`, next to `GetEnvOrFile`, would remove every one of those two-variable temporaries and make `bitbucketAPITokenDefined` a single boolean expression. The PR also introduced `bitbucketAPITokenDefined` and `bitbucketOAuthDefined` but left `displayBitBucketStartupConfig` gated on `SOBA_BITBUCKET_EMAIL` alone, so an OAuth-only Bitbucket user, for whom `collectProviderBackupResults` does run a backup, still gets no Bitbucket startup logging. That mismatch existed before the PR, but the refactor was the moment to notice it because the correct predicate now sits a few lines away.

**2b. (Question) Is the Bitbucket startup gating on email only intentional?** If OAuth-only configurations are supported, which `collectProviderBackupResults` implies, then `displayBitBucketStartupConfig` should gate on `bitbucketAPITokenDefined() || bitbucketOAuthDefined()`. If it is intentional, a comment saying so would stop the next reader from "fixing" it.

**3. `createWorkingDir` duplicates `resolveWorkingDir` (`internal/backup.go:140-146, 473-485`).** `resolveWorkingDir(backupDir)` already implements "use `GIT_WORKING_DIR` if set, otherwise `<backupDir>/<workingDIRName>`", and `runProviderBackups` and `cleanupWorkingDir` use it. The freshly extracted `createWorkingDir` re-implements the same three lines inline, including the same environment lookup and default. Two copies of the rule that decides which directory gets created and which gets deleted is exactly the sort of pair that drifts apart, and the delete side has a safety check. Replace the body with `workingDIR := resolveWorkingDir(backupDIR)` and the function becomes four lines.

**4. `runScheduledJob` hides a write to the package-global `job`, which `execProviderBackups` reads to decide whether to `os.Exit(1)` (`internal/backup.go:35-38, 525-540, 737`).** The extracted helper assigns `job, err = s.NewJob(...)` and the exit decision in `execProviderBackups` and the "next run" banner in `runProviderBackups` both read `job` to learn whether the process is scheduled. Before the PR this was visible in `Run`; now it is a side effect buried in a helper with a signature that looks pure. It is also an ordering hazard that the interval path makes real: `gocron.WithStartImmediately()` starts the first run on a scheduler goroutine as soon as `s.Start()` is called, and `job` is only assigned when `NewJob` returns, so the scheduled job can observe `job == nil` (a data race on an unsynchronised global). If the first run has any failed provider in that window, `execProviderBackups` takes its one-shot branch and exits the whole long-running process. The race predates the PR, but the PR moved the assignment into a helper without touching the design. The clean shape is to give `execProviderBackups` an explicit `oneShot bool` (the `default:` branch calls `execProviderBackups(true)`, the scheduled task closes over `false`) and have `runProviderBackups` take the next-run banner as a return value or callback, so the global can be deleted outright.

**5. `Run` decomposition is by line ranges, not by concept (`internal/backup.go:396-520`).** `validateStartupConfig` returns `(string, error)` and mixes validation with derivation of the trimmed backup directory, so the caller gets a "backup dir" out of a function named `validate...`. `logRequestTimeout` is a logging function whose only reason to return an error is that `getRequestTimeout` can fail parsing, which is validation again. `createWorkingDir` is only that because the working-dir rule was not reused (finding 3). The result is that `Run` reads as a clean sequence but the sequence is validate-log, validate-and-derive, mkdir, schedule; the natural split is a `loadConfig()` that parses and validates everything once and returns a typed config struct (backup dir, working dir, request timeout, interval, cron), after which logging, mkdir and scheduling take that struct instead of each re-reading the environment. That would also let `getBackupInterval` and `os.Getenv(envGitBackupCron)` stop being re-read inside `scheduleBackups`.

**6. The success/partial/failure classification now exists twice, and the PR fixed only the copy Sonar flagged (`internal/backup.go:74-81`, `internal/notify.go:31-39`).** `backupStatusTitle` turns `(succeeded, failed)` into one of three states for notifications, while `runProviderBackups` runs its own three-way `switch` over the same two integers for the log line (with the odd `succeeded == 0 && failed >= 0` guard). A small `backupStatus(succeeded, failed)` returning an enum with a `String()` and a `Title()` would give both callers one definition of the three outcomes. As shipped, changing what "completed with errors" means requires editing two switches in two files. Separately, `backupStatusTitle` has no doc comment while every other helper the PR added does.

**7. The rewritten log helper bakes in the "Organistations" typo, and two of the new title constants begin with a stray U+FE0F (`internal/backup.go:205`, `internal/notify.go:26-28`).** `logProviderOrgs` now emits `"%s Organistations: %s"`. The old code had the typo in three separate strings and the PR centralised it into one, so fixing it is now a one-character edit that the PR left undone while claiming "log output unchanged" as a virtue. If anyone greps logs for the misspelling that is a fair reason to defer, but it should have been called out. In `notify.go`, `titleBackupsErrors` and `titleBackupsFailed` start with the invisible variation selector U+FE0F (bytes `EF B8 8F`) before the emoji, which the original inline strings also had. Moving them into named constants was the moment to notice and drop it, since a leading variation selector with no base character is at best ignored and at worst rendered as a blank glyph in Telegram, ntfy or Slack titles. The automated review raised the typo; the U+FE0F was not raised.

**8. `TestGiteaOrgsRepositoryBackup` still resets backups twice per iteration and the helpers repeat the same paths (`internal/backup_test.go:600-680`).** Each `switch` arm calls `resetBackups()` and the loop body calls it again after the switch, so every iteration resets twice. The old test had the same double call and the automated review flagged it; the PR rewrote these exact lines, kept both calls, and the resulting `switch` is now the only remaining reason for the loop to be a `switch`. The two `assertGitea...` helpers are each a straight-line sequence that rebuilds `path.Join(os.Getenv(envGitBackupDir), "gitea.lessknown.co.uk", <org>)` several times. A table of `{org, expected map[string][]string}` (org directory to required repo-name prefixes) with one assertion helper and a single `resetBackups()` at the end of the loop would delete the `switch`, both wrappers and the duplicate reset, and make the "wildcard also backs up org one" expectation a data row rather than a code path. Deleting `TestPublicGitLabRepositoryBackup2` was correct; it was byte-for-byte identical to its neighbour apart from the name.

**9. Dockerfile: the merged `RUN` keeps a no-op cleanup and redundant flag (`docker/Dockerfile:6-9`).** `rm -f "/var/cache/apk/*"` quotes the glob, so it deletes a file literally named `*` and does nothing, and `apk add --no-cache` already leaves no cache; `--update` is likewise redundant beside `--no-cache`. The PR rewrote this exact instruction to satisfy S7031 and S7018 and preserved both. Dropping the `rm` and `--update` is a pure deletion. I could not build the image in this environment, so this is verified by reading only.

## Proposed remediation sequence

First do the deletions that cannot change behaviour: reuse `resolveWorkingDir` in `createWorkingDir` (finding 3), drop the second `resetBackups()` and the two Dockerfile leftovers (findings 8 and 9), and fix the typo and the leading U+FE0F once each (finding 7). Second, add `envDefined` and convert the gates and Bitbucket helpers (finding 2), and decide the Bitbucket startup-gating question. Third, replace the five `display*StartupConfig` functions with the provider descriptor table and have `collectProviderBackupResults` read the same table (finding 1). Fourth, remove the `job` global by passing an explicit scheduled flag, which also removes the start-immediately race (finding 4). Fifth, introduce `backupStatus` and share it between the log switch and the notifier titles (finding 6). Last, if there is appetite, move `Run` onto a typed config struct (finding 5); this is the largest change and should follow the smaller ones.
